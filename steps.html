Interview Q&A

Why set up CI/CD and repo structure before writing any feature code?
It's cheap to get right at the start and expensive to retrofit — branch protection, .gitignore scope, and commit hygiene all get harder to fix once history exists. Doing it first also means every subsequent step has something real to point to in the commit log during an interview walkthrough.
Why keep study/reference docs out of the repo instead of just gitignoring them?
Gitignore only prevents a future accidental git add from succeeding silently — it doesn't prevent someone from force-adding the file, and it still leaves the content sitting inside the same folder tree as the public repo. Keeping it in a physically separate folder removes the mistake as a category, not just as a default.
Why run git log/ls-remote before touching anything, instead of just re-running the fix?
A push failure can come from several unrelated causes — read-only commands confirm which one you actually have before you act. Here it ruled out "no commit exists" and "repo doesn't exist / bad auth" in under a minute, narrowing it to a branch-name mismatch, which meant a one-line fix instead of redoing work that was never actually lost.

Interview Q&A

Is a Java annotation the same thing as a Python decorator?
They look similar (@Something) but work differently. A Python decorator actually executes and wraps the function at the moment Python runs that line. A Java annotation doesn't execute anything by itself — it's metadata that other tools (here, Spring's startup process) scan for and react to. @SpringBootApplication doesn't "run" — Spring's bootstrap code looks for it and configures itself accordingly.
What does Maven's scope=runtime mean, and why does the Postgres driver use it?
It means the dependency is needed when the app runs, but not to compile it — our own code never directly imports Postgres driver classes; Hibernate looks the driver up and uses it internally once the app is running. Compare to the default scope (compile, needed for both) and test scope (only present when running tests).
The generated test method (contextLoads()) has an empty body — what does it actually test?
It's a smoke test: the method body does nothing, but @SpringBootTest forces the entire Spring application to actually start up for this test. If startup fails for any reason — bad config, broken wiring, in Step 2's case a bad database connection — this test fails even though it never makes an explicit assertion. Trivial right now with almost nothing to start; becomes meaningful the moment real configuration (like a DB connection) exists to break.

Interview Q&A

How did you know the second failure was a networking/publishing problem and not a wrong username/password?
The exact exception mattered: Connection to localhost:5432 refused is a TCP-level failure — nothing was even listening to accept the connection attempt. A wrong username/password would instead connect successfully at the network level and fail later with a Postgres authentication error. Reading the specific exception type, not just "it failed," is what pointed straight at the port-publishing issue instead of the credentials.
docker stop vs. docker compose down — why did only one fix the stale container?
stop halts a container's process but leaves the container object (and its original config) intact — restarting it brings back the exact same, still-broken configuration. down deletes the container entirely, so the next up builds a genuinely new one from the compose file, correctly re-applying the port-publish. When a container's own configuration is the problem, only removal and recreation actually fixes it.

Interview Q&A

Why give Claims Service its own database instead of just adding tables to move_entitlement_db?
Database-per-service is standard microservices practice, even when services share the same physical Postgres container — it keeps each service's schema genuinely independent, so one service's migration or schema change can't accidentally break another. Sharing infrastructure (one container) for cost/simplicity is fine; sharing a schema across two independently-deployable services is the coupling that actually causes problems later.
How does Postgres's Docker image know to run a CREATE DATABASE script automatically?
The official Postgres image's own startup script checks a fixed path, /docker-entrypoint-initdb.d, every time it boots, and runs any .sql/.sh files found there — but only on a completely empty data directory, i.e. genuinely first-time startup. A bind mount (./infra/postgres-init:/docker-entrypoint-initdb.d) is what makes a local file on the host actually visible at that path inside the container in the first place.

Interview Q&A

Why @ConfigurationProperties instead of a simpler @Value("${claims.approval.supervisor-threshold}") injection?
@Value works for a single property, but doesn't scale cleanly to a group of related settings, isn't type-checked as a cohesive unit, and is easy to typo without the IDE catching it. @ConfigurationProperties binds a whole related group onto one class with real fields — better for anything beyond a single standalone value, and it's what this project will keep reaching for as more configuration groups show up.

Why did Mockito fail a test whose actual logic was correct?

Interview Q&A

Why does a message queue need CORS configuration, but a REST API between two backend services doesn't?
CORS is enforced by the browser, not by servers talking to each other. RabbitMQ publishing happens entirely server-side (Java calling RabbitMQ directly) — no browser is ever involved, so CORS never applies there. It only became relevant in this phase because the React dashboard (running in a browser) calls the Java REST API directly, and that's a cross-origin request the browser polices.
If a message gets published to an exchange with no queue bound to it, where does it go?
Nowhere — it's accepted and immediately discarded. RabbitMQ doesn't hold unrouted messages by default (unless the exchange is configured with an "alternate exchange" fallback). This is exactly what happened in Step 66: finding.detected published successfully, visible in the management UI's publish counter, with zero consumers and zero durability — a real, working publish with nothing downstream yet.
Why did the exact same Jackson dependency problem take three separate fixes to fully resolve?

Interview Q&A

Why did the same "advertised listener" bug show up twice in this phase, from two different services?
Because it's really one misconfiguration with two independent victims. Kafka only had a single advertised address (kafka:9092), correct for anything inside Docker's network but meaningless to anything outside it. The Go service (in Docker) broke first when that address was wrong for containers; fixing it for containers then broke the integration test (on the bare host) the opposite way. The real fix wasn't patching each symptom — it was giving Kafka two separate advertised listeners, one per audience.
Why did publishing to Kafka keep working the whole time the single-broker offsets bug was active, while every consumer silently failed?
Producing a message to a normal topic doesn't need __consumer_offsets at all — the producer just writes to the topic's own partitions directly. Consumer groups specifically need that internal topic to track "which member has read up to where." Since it could never finish being created (blocked on an impossible 3-replica requirement with 1 broker), every group-coordinator-dependent path silently stalled, while the completely separate write path kept working the entire time — which is exactly what made this bug so confusing to isolate.

STEP 109 Real failures found under live testing, fixed, merged Done

Why this step exists separately: the previous 8 steps all passed their own local tests, but running the real system end to end — real tunnel, real containers, real Docker networking — surfaced three genuine design gaps none of the earlier tests could have caught.

Real bug — UDP retries caused duplicate database rows
A single client run produced 3 identical Postgres rows, not 1. The client resends a ping if it doesn't get an ack quickly enough, but the server had no way to tell "this is a retry" from "this is a new ping." Root cause: the first UDP round trip through the tunnel took longer than the client's short ack-wait window, triggering retries even though the server had already succeeded each time. Fixed with a RequestID the client reuses across retries and a small server-side dedup cache that still re-acks a duplicate without reprocessing it. Full story on Raw Sockets & WireGuard → Raw listeners in Go.
Real bug — a "successful" TCP delivery that never actually happened
Testing the TCP fallback by stopping the service produced a false positive: the client reported success even though the real container was down. Docker Desktop's port-publishing proxy was still listening and accepted the connection independently of the backend's state — a successful Write() only proves the local kernel accepted the bytes, not that the real application received them. Fixed by requiring a genuine application-level ack the client must read back before declaring success.
Real bug — the ack fix above then broke on a second, unrelated Docker quirk
The first ack implementation had the client half-close its connection (CloseWrite) to signal "done sending," so the server's read would finish. Docker Desktop's proxy doesn't pass that half-close through correctly — it tears down the whole connection on the client's FIN, so the ack written afterward never arrived. Fixed by switching to a 4-byte length-prefixed message, which needs no half-close at all — more robust in general, not just a workaround for this one proxy.
A fourth fix, found the same way — Kafka publish wasn't actually non-blocking
handlePing's Kafka publish already only logged a failure instead of returning one — the intent was clearly "don't let Kafka block the response." But the call was still synchronous, and timed at 2.7 seconds against an unreachable broker — long enough to make an ack window time out. Fixed by firing the publish in a goroutine, matching what the code already claimed to do.

How to check: the failover client, run once normally and once with UDP disabled; cross-check both outcomes directly against Postgres.

Final verification: a real UDP ping landed with a matching timestamp; with UDP disabled, a genuine TCP failover produced a real ack and a real row with its own matching timestamp — confirmed by reading the actual database rows, not just trusting the client's printed output.
