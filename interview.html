From the Steps page

Why set up CI/CD and repo structure before writing any feature code?
It's cheap to get right at the start and expensive to retrofit — branch protection, .gitignore scope, and commit hygiene all get harder to fix once history exists. Doing it first also means every subsequent step has something real to point to in the commit log during an interview walkthrough.

↳ Steps → Step 0

Why keep study/reference docs out of the repo instead of just gitignoring them?
Gitignore only prevents a future accidental git add from succeeding silently — it doesn't prevent someone from force-adding the file, and it still leaves the content sitting inside the same folder tree as the public repo. Keeping it in a physically separate folder removes the mistake as a category, not just as a default.

↳ Steps → Step 0

Why run git log/ls-remote before touching anything, instead of just re-running the fix?
A push failure can come from several unrelated causes — read-only commands confirm which one you actually have before you act. Here it ruled out "no commit exists" and "repo doesn't exist / bad auth" in under a minute, narrowing it to a branch-name mismatch, which meant a one-line fix instead of redoing work that was never actually lost.

↳ Steps → Step 0

Is a Java annotation the same thing as a Python decorator?
They look similar (@Something) but work differently. A Python decorator actually executes and wraps the function at the moment Python runs that line. A Java annotation doesn't execute anything by itself — it's metadata that other tools (here, Spring's startup process) scan for and react to. @SpringBootApplication doesn't "run" — Spring's bootstrap code looks for it and configures itself accordingly.

↳ Steps → Step 1

What does Maven's scope=runtime mean, and why does the Postgres driver use it?
It means the dependency is needed when the app runs, but not to compile it — our own code never directly imports Postgres driver classes; Hibernate looks the driver up and uses it internally once the app is running. Compare to the default scope (compile, needed for both) and test scope (only present when running tests).

↳ Steps → Step 1

The generated test method (contextLoads()) has an empty body — what does it actually test?
It's a smoke test: the method body does nothing, but @SpringBootTest forces the entire Spring application to actually start up for this test. If startup fails for any reason — bad config, broken wiring, a bad database connection — this test fails even though it never makes an explicit assertion. Trivial right now with almost nothing to start; becomes meaningful the moment real configuration (like a DB connection) exists to break.

↳ Steps → Step 1

How did you know the second failure was a networking/publishing problem and not a wrong username/password?
The exact exception mattered: Connection to localhost:5432 refused is a TCP-level failure — nothing was even listening to accept the connection attempt. A wrong username/password would instead connect successfully at the network level and fail later with a Postgres authentication error. Reading the specific exception type, not just "it failed," is what pointed straight at the port-publishing issue instead of the credentials.

↳ Steps → Step 2

docker stop vs. docker compose down — why did only one fix the stale container?
stop halts a container's process but leaves the container object (and its original config) intact — restarting it brings back the exact same, still-broken configuration. down deletes the container entirely, so the next up builds a genuinely new one from the compose file, correctly re-applying the port-publish. When a container's own configuration is the problem, only removal and recreation actually fixes it.

↳ Steps → Step 2

Why give Claims Service its own database instead of just adding tables to move_entitlement_db?
Database-per-service is standard microservices practice, even when services share the same physical Postgres container — it keeps each service's schema genuinely independent, so one service's migration or schema change can't accidentally break another. Sharing infrastructure (one container) for cost/simplicity is fine; sharing a schema across two independently-deployable services is the coupling that actually causes problems later.

↳ Steps → Step 4

How does Postgres's Docker image know to run a CREATE DATABASE script automatically?
The official Postgres image's own startup script checks a fixed path, /docker-entrypoint-initdb.d, every time it boots, and runs any .sql/.sh files found there — but only on a completely empty data directory, i.e. genuinely first-time startup. A bind mount (./infra/postgres-init:/docker-entrypoint-initdb.d) is what makes a local file on the host actually visible at that path inside the container in the first place.

↳ Steps → Step 4

Why @ConfigurationProperties instead of a simpler @Value("${claims.approval.supervisor-threshold}") injection?
@Value works for a single property, but doesn't scale cleanly to a group of related settings, isn't type-checked as a cohesive unit, and is easy to typo without the IDE catching it. @ConfigurationProperties binds a whole related group onto one class with real fields — better for anything beyond a single standalone value, and it's what this project will keep reaching for as more configuration groups show up.

↳ Steps → Step 6

Why did Mockito fail a test whose actual logic was correct?
Mockito's default strict stubbing checks that every stub you set up actually gets used somewhere in that test — an unused stub usually means the test setup doesn't match what the code under test really does, which is worth knowing even when the assertion itself would have passed. It's a test-design smell detector, not just an exception-matcher.

↳ Steps → Step 8

A mid-step fix landed after the PR's commit — how did you catch it, and how did you land it?
git status before starting the next piece of work, as a habit, not just when something looks wrong — it showed a modified file sitting uncommitted on main that shouldn't have been there. Since the original PR was already merged and the branch deleted, reopening it wasn't an option — a small, separately-scoped follow-up PR (its own issue, branch, and merge) is the honest way to land a fix after the fact, same process as any other change.

↳ Steps → Step 21

A commit landed on the wrong branch and got rejected by branch protection — was that a problem?
The opposite — it's exactly what branch protection is for. The commit itself wasn't lost (still sitting safely in local history), and the rejection is what surfaced the mistake immediately instead of it silently landing on main unreviewed. cherry-pick moved it to the correct branch without redoing any work.

From Git & GitHub

What's the difference between staged and committed?
Staged means the file is in the draft area (git add ran), waiting to be included in the next snapshot. Committed means that snapshot was actually saved to history (git commit ran). You can stage and unstage freely without touching history.

↳ Git & GitHub

Why write .gitignore before the first commit instead of after?
Once a file is committed, adding it to .gitignore later doesn't remove it from history — it only stops future changes from being tracked. Getting it right before the first git add avoids ever having to scrub a secret or a build folder out of history.

↳ Git & GitHub

Why feature branches + PRs instead of committing straight to main, especially solo?
Two reasons that hold even with one developer: it forces a self-review step — reading your own diff on GitHub's PR view catches things a local git diff in a terminal doesn't — and it keeps main always in a known-good, deployable state, since work-in-progress never lands there directly. On a real team it also adds actual code review and CI gating before merge.

↳ Git & GitHub

Squash-merge vs. a regular merge commit — when would you pick each?
Squash-merge when you want main's history to read as one commit per feature — easy to scan, easy to revert a whole feature in one command. A regular merge commit when you need every intermediate commit preserved — e.g. a long-lived release branch, or a team convention that ties commits to individual review comments. For a single-developer project shipping continuously, squash is the simpler, cleaner default.

↳ Git & GitHub

Doesn't deleting the branch after merge lose the record of what work was done?
No — the branch is just a temporary pointer, not the record. The Pull Request itself is never deleted; every commit, the full diff, and any comments stay permanently viewable at its URL even after merge, and the squashed commit lives forever in main's history regardless. Deleting the branch only removes clutter from the active-branch list — to see what a finished piece of work actually did, you'd look at its closed PR, not a branch name.

↳ Git & GitHub

From Java, Spring & Maven

What's the difference between Spring and Spring Boot?
Spring is the underlying framework (dependency injection, MVC, data access abstractions) — powerful but historically required a lot of manual XML/Java config to wire together. Spring Boot is an opinionated layer on top: auto-configuration, an embedded server, and starter dependencies (spring-boot-starter-web, etc.) that pull in a coherent, working set of versions so you get a running app with minimal config.

↳ Java, Spring & Maven

Why does data.sql need ON CONFLICT DO NOTHING but a Docker Postgres init script doesn't?
They run at different frequencies. A Docker /docker-entrypoint-initdb.d script only runs once, on a genuinely empty data volume — never again after that. Spring's data.sql runs on every application startup by design, so a plain INSERT would hit a duplicate-key error on the second restart. ON CONFLICT DO NOTHING makes it safe to re-run — insert if missing, silently skip if already there.

↳ Java, Spring & Maven

What does ArgumentCaptor prove that a plain verify(mock).method() doesn't?
verify(...) alone only proves a method got called — not what it was called with. ArgumentCaptor grabs the actual argument passed in, so a test can assert on its contents — e.g. proving a change-control log entry recorded the correct old and new values, not just that some record got saved.

↳ Java, Spring & Maven

Why JPA/Hibernate instead of writing raw SQL with JDBC directly?
JPA maps Java objects to rows so most CRUD never needs hand-written SQL, which is faster to write and less error-prone for straightforward access patterns. The tradeoff is less control over the exact query — for a genuinely complex or performance-critical query, dropping to a native query or raw JDBC for that one case is still normal and expected, not a sign JPA was the wrong choice overall.

↳ Java, Spring & Maven

Why not just return the JPA entity directly from a REST endpoint instead of mapping to a DTO?
It couples your public API shape to your database schema — a column rename in the entity becomes a breaking API change for every client. JPA entities can also have lazy-loaded fields that serialize unpredictably. A DTO is a deliberate, separate contract: only what a client actually needs, independent of how the data happens to be stored.

↳ Java, Spring & Maven

You committed to the wrong branch — how do you fix it without losing work?
git cherry-pick <commit-hash> onto the correct branch — it copies that commit's changes without removing it from the original branch first, so nothing is at risk until you explicitly clean up the wrong branch afterward with git branch -D. Safe by construction: the copy exists before the original is ever touched.

↳ Git & GitHub

From Docker & Compose

What's the difference between a Docker image and a container?
An image is a frozen, read-only snapshot — filesystem plus config, like a class. A container is a running (or stopped) instance created from that image — like an object instantiated from that class. One image can produce many independent containers.

↳ Docker & Compose

Why use a named volume instead of just letting the container store data in its own filesystem?
A container's own filesystem disappears the moment the container is deleted — exactly what docker compose down does. A named volume lives independently of any specific container, so the database's actual data survives a full container recreate and is only lost if the volume itself is explicitly removed.

↳ Docker & Compose

Why use a multi-stage Dockerfile instead of one stage that both builds and runs the app?
A single stage would ship the full JDK, Maven's dependency cache, and the source code inside the production image — bigger, slower to deploy, and a larger attack surface (a compiler sitting in production is pure downside). A second stage starting fresh from a JRE-only base image and copying in just the finished jar keeps the final image to only what's needed to run it.

↳ Docker & Compose

Why doesn't localhost work for one container to reach another?
Inside a container, localhost always refers to that container itself, not a sibling. Docker Compose gives every service in the same compose file a private network where they can reach each other by service name instead — that's why this project overrides spring.datasource.url with the hostname postgres (not localhost) via an environment variable specifically for the containerized case, while local dev outside Docker keeps using localhost unchanged.

↳ Docker & Compose

Is CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"] running multiple commands?
No — it's one program (the first array element) plus the arguments passed to it (everything after), written as an explicit array instead of one string Docker would otherwise have to split itself. Same idea as typing uvicorn app.main:app --host 0.0.0.0 --port 8000 on a command line — one process starts, reads its own argument list, and configures itself from it.

↳ Docker & Compose

Why can't you just use $(pwd) as a bind-mount path from a container that reached Docker via a mounted socket?
The command runs inside that container but is executed by the host's Docker daemon — so any path in a bind-mount has to make sense to the host, not to the calling container's own filesystem. $(pwd) resolves to a path inside the calling container, which the host daemon has no knowledge of. The fix is a named Docker volume instead of a bind-mount path — named volumes are daemon-managed, so the same one can be mounted into both containers and they'll genuinely share the same storage.

↳ Docker & Compose

How do you confirm an edit to docker-compose.yml actually took effect?
docker compose config — it prints the fully resolved compose file, with any environment variables and defaults already interpolated, showing exactly what Compose is going to use. More reliable than assuming a saved edit is correct, especially after a repeated error suggests the "fix" didn't actually change anything.

↳ Docker & Compose

From React, Redux & TypeScript

Why use Redux instead of just React's built-in state?
React's useState is local to one component — sharing that value with a distant, unrelated component means manually passing it down through every layer in between ("prop drilling"), which gets unmanageable fast. Redux gives any component direct access to shared state without that chain.

↳ React, Redux & TypeScript

Why Vitest instead of Jest, the more well-known test runner?
Vitest is built specifically to integrate with Vite — it reuses the same fast dev-server machinery, so tests start almost instantly, and understands TypeScript/JSX with zero extra config. Jest predates Vite and needs additional configuration glue to work with a Vite project properly.

↳ React, Redux & TypeScript

Why does an async API call need createAsyncThunk instead of a plain reducer?
Redux reducers must be synchronous, pure functions — no waiting, no side effects. An API call is inherently asynchronous. createAsyncThunk bridges the gap: give it a function returning a Promise, and it automatically dispatches pending/ fulfilled/rejected actions as that promise resolves, so the reducer only ever handles plain, synchronous action objects.

↳ React, Redux & TypeScript

From Python, FastAPI & scikit-learn

What does visiting /docs on a FastAPI service actually show you?
An interactive Swagger UI, generated automatically from the route definitions and Pydantic models — no separate documentation to write. You can expand any route, click "Try it out", fill in a real request, and send it straight from the browser — the same thing curl or Postman would do, with a UI instead of hand-typed JSON.

↳ Python, FastAPI & scikit-learn

What does Field(...) mean in a Pydantic model?
The ... is Python's Ellipsis object, and here it means "this field is required, no default value." A request missing it gets rejected with a 422 before the route function runs. Field can also carry validation constraints like gt=0 or ge=0 alongside that requirement.

↳ Python, FastAPI & scikit-learn

Why doesn't the Python service use a multi-stage Docker build like the Java and Node services do?
Multi-stage builds exist to keep a heavy build toolchain out of the final runtime image — the JDK vs JRE split, or Vite's build tooling vs the static output Nginx serves. Python's dependencies install as prebuilt wheels with no compilation step, so there's no separate "build artifact" a second stage would need to extract. A single python:3.12-slim stage is the correct choice here, not a shortcut.

↳ Python, FastAPI & scikit-learn

What does wrapping preprocessing and the classifier in a scikit-learn Pipeline actually buy you?
It guarantees the exact same preprocessing (the OneHotEncoder for claim_type) runs identically at training time and at prediction time, and lets the whole thing be saved/loaded as one joblib artifact instead of having to remember to apply preprocessing by hand before every prediction.

↳ Python, FastAPI & scikit-learn

Why cache predictions in Redis instead of just recomputing them every time?
The model call itself is cheap here, but the pattern matters more than the raw speed — identical requests (e.g. a retry, or the same claim re-checked) shouldn't pay compute cost twice. It's a standard latency/cost-reduction pattern, and a real interview talking point about caching idempotent, deterministic operations.

↳ Python, FastAPI & scikit-learn

How does pytest compare to the testing tools used elsewhere in this project?
Same underlying concept as JUnit (Java) and Vitest (TypeScript) — write a function, assert on the result, a runner discovers and executes them. pytest's discovery is purely convention-based (files/functions named test_*), with no annotations needed, unlike JUnit's @Test.

↳ Python, FastAPI & scikit-learn

From Go

Why does go run main.go fail with "undefined" errors once you add a second file?
go run main.go only compiles that one named file — it doesn't know any other .go file in the same directory exists, so anything defined elsewhere in the package (like a connectDB function in db.go) shows as undefined. go run . compiles the whole package/directory together and is the correct command once a package spans more than one file.

↳ Go

Why would a Docker build fail with "go.mod requires go >= X, running go Y"?
go.mod's go directive records a minimum required toolchain version — since Go 1.21, this is strictly enforced, not just informational. If the Docker build stage's base image has an older Go version than what go.mod demands, go mod download refuses to run. The fix is bumping the Dockerfile's build-stage image version to match, not lowering what's in go.mod unless there's a real reason to support an older toolchain.

↳ Go

Why does scanning a TIMESTAMPTZ column into a Go string field panic?
The lib/pq driver decodes a TIMESTAMPTZ column into a Go time.Time value, not a string — Scan can't automatically convert time.Time into a *string destination, so it panics with "unsupported Scan." Fix it either by changing the struct field to time.Time, or by casting in the query itself (column::text) so Postgres sends a string instead — the query-cast is the smaller change when the rest of the code already assumes a string.

↳ Go

Why does the in-memory version of this service need a sync.Mutex?
Every HTTP request in Go runs on its own goroutine automatically. Two requests can hit the same handler at the same moment and both try to modify shared state (like an in-memory slice) simultaneously, corrupting it. The mutex ensures only one goroutine touches that shared state at a time — once Postgres replaces the in-memory slice, the database handles concurrent writes safely instead.

↳ Go

Why does the Go service use raw SQL instead of an ORM like the Java services do?
Go doesn't have a dominant, widely-used ORM the way Java has JPA/Hibernate. Raw SQL via the standard library's database/sql package is the idiomatic default in the Go ecosystem — a deliberate ecosystem difference, not a shortcut taken for this project specifically.

↳ Go

How does Go handle errors if it doesn't have exceptions?
Functions that can fail return an extra error value as their last return, checked explicitly with if err != nil at each call site. More verbose than try/catch, but it makes every failure-prone operation visible in the code instead of relying on an exception that might surface several call-frames away from where it was thrown.

↳ Go

What does _ "github.com/lib/pq" do if the package name is never used?
It's a blank import — imported purely for its side effect. The pq package registers itself with database/sql when it loads, via its own init() function. The underscore tells Go's compiler "this unused import is intentional," since Go normally refuses to compile with an unused import.

↳ Go

From Jenkins, Trivy & OWASP ZAP

Why did the ZAP scan stage show green even though it never actually scanned anything?
ZAP refuses to run when a file-output option is given but its expected working directory (/zap/wrk) isn't mounted — it prints usage/help and exits instead of scanning. Combined with a trailing || true (added so ZAP findings wouldn't hard-fail the build), that immediate exit looked like a pass. A green stage proves the shell command exited 0 — it doesn't prove the tool actually did the thing you intended.

↳ Jenkins, Trivy & OWASP ZAP

What's the difference between what Trivy and OWASP ZAP each check for?
Trivy is SCA (Software Composition Analysis) — it inspects what's installed in an image (OS packages, language dependencies) against known-CVE databases, without running anything. ZAP is DAST (Dynamic Application Security Testing) — it sends real HTTP requests at a live, running application, probing for actual exploitable behavior. Trivy catches "known-vulnerable software we shipped"; ZAP catches "the running app actually misbehaves under attack" — different failure modes, which is why a real gate runs both.

↳ Jenkins, Trivy & OWASP ZAP

How does a Trivy scan actually block a build, not just report findings?
--exit-code 1 makes Trivy exit non-zero when it finds a vulnerability at or above the specified severity. Since a Jenkins pipeline stage fails when its shell command exits non-zero, this single flag is what turns "print a report" into "stop the pipeline" — the gate isn't a separate mechanism from the scan, it's one flag away from being purely informational.

↳ Jenkins, Trivy & OWASP ZAP

From SQL Notes

What's the difference between WHERE and HAVING?
WHERE filters individual rows before grouping happens; HAVING filters groups after GROUP BY has run, and can reference aggregate functions like COUNT(...) that don't exist yet at the WHERE stage.

↳ SQL Notes

How do window functions differ from GROUP BY?
GROUP BY collapses multiple rows into one row per group. A window function (ROW_NUMBER(), RANK(), etc. with OVER (...)) computes a value per row while still having access to a related set of rows — you keep every original row and get a ranking/running-total/comparison alongside it, instead of losing row-level detail.

↳ SQL Notes

How do parameterized queries prevent SQL injection?
The query structure and the user-supplied value are sent to the database separately — the database never parses the value as part of the SQL text, so a malicious string like ' OR '1'='1 is treated as a literal value to search for, not executable SQL. String concatenation is what allows injection in the first place, by letting user input become part of the query's actual syntax.

↳ SQL Notes

From AWS Notes

What is Amazon OpenSearch Service, and how does it relate to "Amazon ElasticSearch"?
Same service — Amazon ElasticSearch Service was renamed to Amazon OpenSearch Service in 2021, after AWS forked the open-source Elasticsearch project due to a licensing dispute with Elastic N.V. Functionally it's the same managed search/analytics engine, commonly paired with a database for search or used for log analytics at scale.

↳ AWS Notes

When would you choose DynamoDB over RDS?
DynamoDB when the access pattern is simple key-value/document lookups at very high, elastic scale with single-digit-millisecond latency and you don't need SQL joins or complex relational queries. RDS/Aurora when you need relational integrity, joins, transactions across multiple tables, or existing SQL-based tooling. DynamoDB's schema is defined by query patterns, not by the data's natural relational shape — a real design-time tradeoff, not just a performance one.

↳ AWS Notes

Can a Security Group block a specific malicious IP address?
No — Security Groups only support Allow rules, not explicit Deny, so they can't block one specific IP. Use a Network ACL at the subnet level instead, which supports both Allow and Deny rules.

↳ AWS Notes

What's the difference between Amazon Bedrock and Amazon SageMaker?
SageMaker is for building, training, and deploying your own custom ML models — you manage the training data and process. Bedrock gives managed API access to pre-built foundation models from multiple providers (Anthropic, Meta, Amazon, and others) — no training or infrastructure management, pay per request. Bedrock is the faster path when an existing foundation model already solves the problem; SageMaker is for when you need a model trained on your own proprietary data/task.

↳ AWS Notes

From Agile & SDLC Methodologies Notes

When would you choose Waterfall over Agile, if Agile is generally more flexible?
When requirements are genuinely stable and well understood up front, and the cost of mid-project change is severe — e.g. systems tightly coupled to fixed hardware, or heavily regulated environments where every change needs formal sign-off. Agile's advantage (cheap, continuous change) is wasted effort if change was never going to happen anyway, and Waterfall's upfront planning rigor can be a genuine asset in that specific situation.

↳ Agile & SDLC Methodologies

How do you decide between Scrum and Kanban for a team?
Scrum fits work that can be planned into fixed-length chunks with a clear "done" per sprint — typical product development. Kanban fits continuous, unpredictable work where tasks arrive at any time and priorities can shift immediately — typical of a support/maintenance team, where a 2-week sprint commitment doesn't match how the work actually shows up.

↳ Agile & SDLC Methodologies

What is velocity actually used for in Scrum?
Forecasting how much backlog a team can realistically commit to in a future sprint, based on their historical average story points completed per sprint. It's a planning tool for the team, not a performance metric to compare between teams or individuals — velocity is relative to one team's own estimation habits, not an absolute measure of output.

↳ Agile & SDLC Methodologies

From Linux/Unix Notes

What's the difference between kill and kill -9?
Plain kill sends SIGTERM — a request the process can catch and handle gracefully (close files, finish in-flight work) before exiting. kill -9 sends SIGKILL, enforced immediately by the OS with no chance for cleanup. Always try plain kill first; reserve -9 for a genuinely unresponsive process.

↳ Linux/Unix Notes

What's the difference between du and df?
du reports how much disk space specific files/directories are using — scoped to whatever path you point it at. df reports free/used space at the filesystem or mounted-partition level — a whole-disk view, not a per-file one. A directory can look small under du while df still shows a disk nearly full, if space is consumed elsewhere.

↳ Linux/Unix Notes

When would you use awk instead of grep or sed?
grep finds matching lines. sed transforms text line-by-line (find & replace). awk is for column/field-structured data — extracting a specific column, filtering rows by a field's value, or computing across columns — closer to a lightweight SQL query over a text file than either of the other two.

↳ Linux/Unix Notes

From Redis Notes

Why is Redis so much faster than a traditional database?
Data lives in RAM, not on disk — RAM access is orders of magnitude faster. Redis also executes commands single-threaded, which avoids the lock-contention overhead a multi-threaded database pays for concurrent access to the same data, at the cost of not parallelizing CPU-bound work across cores for a single instance.

↳ Redis Notes

What's the difference between RDB and AOF persistence?
RDB takes periodic full snapshots — compact, fast to restart from, but can lose everything since the last snapshot on a crash. AOF logs every write command and replays it on restart — much less data loss, but a larger file and slower restart. They can run together: RDB for fast recovery, AOF for minimal loss.

↳ Redis Notes

Is Redis Pub/Sub a reliable message queue?
No — it's fire-and-forget. If no client is subscribed when PUBLISH runs, the message is simply lost, with no delivery guarantee or replay. For durable message delivery, use Redis Streams instead, or a dedicated message queue.

↳ Redis Notes

When would you reach for a Sorted Set instead of a plain Set?
Whenever ranking or ordering matters — a leaderboard, a priority queue, "top N most recent/highest-scored" queries. A plain Set only tracks unique membership with no order; a Sorted Set keeps every member ordered by its score, so range queries like "top 10" are a single fast command instead of fetching everything and sorting client-side.

↳ Redis Notes
