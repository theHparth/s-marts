Request & Failure Flow Map

Architecture & Progress shows what exists — every service, every data store, every connection between them. This page shows what actually happens when a real request moves through that system: which service handles it, which port, what it does next, and — for every point where something could go either way — what happens if it succeeds, and what happens if it doesn't. Every branch below is a real thing that happened during this project, not a hypothetical.

How to read these diagrams
  • A plain ▼ arrow means "this step happened, moving straight to the next one."
  • A ├─ branch means a real decision point — something that can go more than one way. Each branch is labeled with the condition and where it leads.
  • FAILURE branches aren't hypothetical edge cases — every one shown here is a real error this project actually hit, with a link to the full explanation and fix.
  • Diagrams in the normal box style below are confirmed built and verified. A diagram in an amber, dashed box is planned — written before the code exists, the same pre-study convention used on the tech reference pages, and gets replaced with the real, confirmed version once that phase is actually built.

Claims triage prediction (Python/FastAPI)

Confirmed built — Steps page → Phase 8. The one flow so far with a genuine performance-driven branch: a cache hit skips the ML model entirely.

Caller — POST :8000/predict { claim features } │ ▼ Pydantic model validates the request shape │ ├─ shape invalid ────────────► FAILURE: HTTP 422 (FastAPI's own automatic validation error) │ ▼ valid build a cache key from the request → check Redis :6379 │ ├─ Cache HIT ─────────────────► return the cached prediction immediately. │ scikit-learn pipeline never runs at all for this request. │ ▼ Cache MISS pandas builds a one-row DataFrame → the loaded scikit-learn pipeline predicts a priority │ ▼ cache the result in Redis (5-minute TTL) → HTTP 200 { priority, confidence }

CI/CD pipeline (Jenkins)

Confirmed built — Phase 5 + Step 67. This is the flow with the real "push code, then watch the pipeline react" loop the project is built around.

You — git push origin your-branch │ ▼ Jenkins UI — click "Build Now" (this project triggers manually, not via webhook) │ ▼ Checkout stage — checkout scm pulls the Jenkinsfile + code from whatever the job's "Branches to build" field currently points at │ ├─ branch renamed/deleted ───► FAILURE: "fatal: couldn't find remote ref ..." │ Real incident: a branch got squash-merged + auto-deleted by │ gh pr merge --delete-branch while Jenkins was still configured │ to build it. Fix: point the field at *staffed*/main instead. │ Full story: git.html#branch-deleted-after-merge │ ▼ checkout succeeds Build stage — docker build the target service's image │ ▼ Trivy Scan stage — trivy image -f json -o trivy-report.json --exit-code 1 --severity HIGH,CRITICAL │ ├─ HIGH/CRITICAL vulnerability found ─► exits 1, caught by "|| echo SEVERE FINDINGS DETECTED" — │ the stage keeps running (doesn't hard-abort the whole │ pipeline) but is now VISIBLY flagged in Console Output. │ This flag-not-abort behavior IS the compliance gate. │ ▼ clean scan, exits 0 Report Findings stage — python3 scripts/report_findings.py unpacks the JSON, POSTs one request per vulnerability to compliance-service │ ├─ compliance-service not reachable ─► connection error printed, caught by "|| true", │ stage still shows green. (Real early-phase state, │ before Step 74 wired the service into the same │ Docker network as Jenkins.) │ ▼ reaches compliance-service — see the findings-ingestion flow below for what happens next ZAP Baseline Scan stage — passive scan against http://dashboard:80 │ ▼ advisory only — WARN-NEW findings never fail the build ("|| true" always continues) Archive Reports stage — archiveArtifacts *-report.html │ ▼ Build marked SUCCESS (the only stage that hard-fails the whole pipeline on a real problem is the Docker build itself — everything after it is designed to flag, not block)

Findings ingestion — the severity branch

Confirmed built — Step 65 / Step 66. This is the exact decision that determines whether RabbitMQ ever hears about a finding at all.

Jenkins's report_findings.py — POST :8010/findings { source, severity, title, target } │ ▼ Pydantic Finding model validates │ ├─ shape invalid ────────────► FAILURE: HTTP 422 │ ▼ valid db.findings.insert_one(doc) — MongoDB :27017 │ ▼ always succeeds — Mongo has no schema to violate, unlike a SQL insert should_publish(severity)? │ ├─ severity in (LOW, MEDIUM) ─► NO — nothing published. Finding is stored, permanently │ queryable via GET /findings, but silent otherwise. │ └─ severity in (HIGH, CRITICAL) ─► YES — publish_finding_detected() sends to RabbitMQ :5672, "compliance" exchange, routing key finding.detected. No queue is bound to that exchange yet — the message publishes successfully and is currently discarded with nowhere to go. That's expected at this point (future work), not a bug — see rabbitmq-mongodb.html#rabbitmq-concepts. │ ▼ HTTP 200 { id } (returned either way — publishing is fire-and-forget, never blocks the response)

Common failure signatures — cross-cutting reference

The same handful of failure shapes keep recurring across totally different technologies. This table is the fast way to recognize which one you're looking at.

What you seeWhere it happensReal causeFull explanation
Failed to fetch in the browser consoleReact calling any Java/Python service directlyMissing CORS configuration on the serverjava-spring.html#cors-config
nginx 404 page on a direct URL or refreshThe dashboard containerNo SPA fallback rule in nginx's configreact-redux.html#spa-nginx-routing
HTTP 405 Method Not AllowedAny REST frameworkTesting a method (GET) before that route existed yet — the path is real, the method isn'texpected mid-build sequencing, not a bug
HTTP 400 / 422Validation layer (Pydantic / @Valid)Input genuinely fails a real rule (e.g. a past date on a @FutureOrPresent field)working as designed
Python traceback / connection refused calling another serviceAny container reaching another by service nameTarget service not yet on the same Docker network, or not running/built yetdocker.html#docker-outside-docker
pip: not foundJenkins containerBase Jenkins image has no Python installedjenkins.html#python-in-jenkins-image
fatal: couldn't find remote refJenkins Checkout stageBranch was renamed or deleted — often because it was already squash-mergedgit.html#branch-deleted-after-merge
NoClassDefFoundError on app startupJava service using a hand-built message converterA newer library API called than what's actually resolved on the classpathrabbitmq-mongodb.html#java-jackson-gotchas

How this page grows with each new phase

This page follows the same rule as Architecture & Progress: at the start of every new phase, a new flow diagram gets added here in the amber/planned style below — describing what the new service is expected to do, before any of it is built. Once that phase is confirmed working, the diagram gets replaced with the normal style, corrected to match what was actually built (including whatever real failure branches got hit along the way, the same as every flow above).
