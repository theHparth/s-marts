Request & Failure Flow Map

Architecture & Progress shows what exists — every service, every data store, every connection between them. This page shows what actually happens when a real request moves through that system: which service handles it, which port, what it does next, and — for every point where something could go either way — what happens if it succeeds, and what happens if it doesn't. Every branch below is a real thing that happened during this project, not a hypothetical.

How to read these diagrams
  • A plain ▼ arrow means "this step happened, moving straight to the next one."
  • A ├─ branch means a real decision point — something that can go more than one way. Each branch is labeled with the condition and where it leads.
  • FAILURE branches aren't hypothetical edge cases — every one shown here is a real error this project actually hit, with a link to the full explanation and fix.
  • Diagrams in the normal box style below are confirmed built and verified. A diagram in an amber, dashed box is planned — written before the code exists, the same pre-study convention used on the tech reference pages, and gets replaced with the real, confirmed version once that phase is actually built.

SOAP legacy adapter — hand-sent request, no automated client

Confirmed built — Steps page → Phase 7. Full concept explanation on SOAP & Spring-WS Raw Sockets & WireGuard. This flow reads as linear on purpose — unlike Kafka's dual-write or WebSocket's independently-running consumer, every step here genuinely depends on the one before it finishing (parse the XML, translate it, call REST, wait for the response, translate that back) — there's no point where one value gets consumed twice by independent downstream actions, so no box-and-branch notation applies here. Also unlike every other flow on this page, nothing else in MoveTrack Ops actually triggers this one automatically — see SOAP & Spring-WS → Why this phase is standalone.

Fixed with .toXMLFormat(), not .toString(). │ Full story: tech/soap.html#qa-soap-xmlgregoriancalendar │ ▼ toRestDto(request) — maps SOAP fields into a plain Map (no shared DTO class with Move & Entitlement, deliberately — keeps the adapter from needing a compile-time dependency on that service's internals) ▼ RestTemplate.postForObject(...) │ ▼ move-entitlement-service : 8082 (unchanged — has no idea a SOAP client exists) │ same REST path the React dashboard already calls ▼ PostgreSQL : 5432 — INSERT INTO move_requests, entitlement calculated ▼ toSoapResponse(restResponse) — maps the REST JSON response back into SubmitMoveRequestResponse ▼ PowerShell — receives a well-formed SOAP response envelope: <id>19</id> <entitlementLbs>7000</entitlementLbs> │ ├─ printing the response object directly shows only "Envelope" ─► not a failure, PowerShell's │ Invoke-RestMethod auto-parses XML and hides nested content on direct print. │ $response.OuterXml reveals the real values. Full story: tech/soap.html#verifying-the-round-trip │ ▼ cross-checked independently docker compose exec postgres psql ... SELECT id, service_member_name, rank FROM move_requests ORDER BY id DESC LIMIT 1 → same id=19, same Jane Doe / E5 — proves the SOAP response reflects a real database write, not just an echoed/faked value

Raw sockets + WireGuard failover — planned

Planned — Steps page → Phase 13, in progress. Full concept explanation on Raw Sockets & WireGuard. This diagram uses a ├─ decision branch, not box-and-branch notation — UDP failing over to TCP is a genuine sequential retry (try UDP, then conditionally try TCP), not two independent actions consuming the same value simultaneously the way Kafka's dual-write or WebSocket's independent consumer are.

Device (simulated) — inside the WireGuard tunnel │ │ sends ping via raw UDP → shipment-ingestion : 8091 ▼ shipment-ingestion (Go) — UDP listener │ handlePing(raw) — same shared validate/persist/publish function REST and Kafka already use ▼ PostgreSQL : 5432 — INSERT INTO shipment pings ▼ UDP ack datagram sent back to device │ ├─ ack received within timeout ─► done, delivered via UDP (the normal case — │ most pings never touch TCP at all) │ ├─ no ack after N attempts ─► device falls back to TCP :8092 for this ping │ (device-driven decision — the server never orchestrates the fallback, │ it just exposes both listeners) │ ▼ │ shipment-ingestion (Go) — TCP listener │ │ same handlePing(raw) — identical downstream behavior regardless of transport │ ▼ │ PostgreSQL : 5432 — INSERT INTO shipment pings │ TCP's own handshake success/failure IS the delivery confirmation — │ no separate ack scheme needed on top of it ▼ Either path: a real ping lands in Postgres, encrypted end-to-end by the WireGuard tunnel the entire way — raw UDP/TCP never touch the open network
