Terraform, VPC & EKS Phase 15

Written from zero — assumes no prior Terraform or Kubernetes experience, but does assume the general AWS service definitions (VPC, EC2, IAM, RDS, ALB) already covered on AWS Notes. This page focuses on what that page doesn't: Terraform itself, Kubernetes itself, and how this specific project wires them together. For when each piece was introduced, see the Steps page → Phase 15.

Phase 15 is starting now — this is by far the largest phase in the project (VPC, EKS, RDS, Kubernetes manifests, HPA all in one phase). Everything on this page reflects the planned implementation — read it now to build the fundamentals before touching real AWS, then it gets corrected/confirmed once each step is really built and (deliberately, to control cost) torn back down.

Why this phase exists, what it does, where it fits

QuestionAnswer
Why does this project need this at all?Everything built so far runs on one machine via docker compose up — a real production system runs on real cloud infrastructure, with real scaling, real networking isolation, and a real managed database. This phase is the difference between "a demo that runs on my laptop" and "a system deployed the way a real company would deploy it."
What does it actually do?Provisions a real AWS VPC, a real EKS (managed Kubernetes) cluster, and a real RDS Postgres instance — all via Terraform, not clicked together by hand — then deploys every existing service onto that cluster, replacing local Docker Compose with real Kubernetes orchestration.
Where does it sit in the system?Underneath everything, the same way Docker Compose did — except now "underneath everything" means a real VPC with public/private subnets, an EKS control plane, and worker nodes running the same container images already built in every prior phase.
When would you reach for this pattern in a real job?The moment a project needs to run anywhere other than a developer's own machine — Terraform for anything provisioning real cloud infrastructure, Kubernetes for anything beyond a handful of services on a single host.

The story, in plain terms — three separate new ideas, stacked

This phase is really three distinct new concepts layered on top of each other, and it's worth keeping them separate in your head before diving into any one of them:

1. Infrastructure as Code (Terraform) Instead of clicking around the AWS Console to create a VPC/EKS cluster/RDS instance by hand, you write a text file describing what you want, and a tool creates exactly that. 2. Container orchestration (Kubernetes / EKS) Docker Compose runs containers on ONE machine. Kubernetes runs containers across MANY machines (nodes), deciding which node each container runs on, restarting it if it dies, and scaling the number of copies up or down. 3. This project's specific architecture decisions Which pieces move to managed AWS services (Postgres → RDS) vs. stay self-hosted on Kubernetes (Kafka, RabbitMQ, MongoDB, Redis) — a real, deliberate tradeoff, not a default.

Terraform fundamentals

TermPlain-language meaning
HCLHashiCorp Configuration Language — the syntax Terraform files (.tf) are written in. Declarative: you describe the end state you want, not the steps to get there.
ProviderA plugin that knows how to talk to a specific API — the aws provider knows how to create VPCs, EKS clusters, RDS instances, etc. via AWS's API.
ResourceOne real thing Terraform manages — resource "aws_vpc" "main" { ... } declares one real VPC.
StateTerraform's own record of what it already created (resource IDs, current config) — how it knows the difference between "create this" and "this already exists, update it" on the next run.
ModuleA reusable, packaged group of resources — write the VPC once as a module, reuse it, instead of copy-pasting the same 15 resources every time you need a VPC.

The core workflow

terraform init      # downloads the aws provider plugin, sets up the backend
terraform plan      # shows exactly what would change, without changing anything yet
terraform apply     # actually creates/updates the real AWS resources
terraform destroy   # tears everything down — the step that actually matters for cost control here
Why plan before apply matters, specifically for this project
terraform plan is a dry run — it shows exactly which resources would be created, changed, or destroyed, with no real AWS API calls that create anything. Given this phase deliberately spins real infrastructure up and back down to control cost, reading the plan output carefully before every apply (and especially before every destroy) is the actual safety mechanism — not a formality.

A minimal real example — one S3 bucket

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_s3_bucket" "example" {
  bucket = "movetrack-ops-example"
}

Three blocks: which provider(s) this configuration needs, how to configure that provider (which AWS region), and one real resource. terraform apply against just this file creates one real S3 bucket — the same pattern scales up to the VPC/EKS/RDS resources this phase actually needs, just with many more resource blocks and references between them.

Why state needs a remote backend, not a local file

By default, Terraform writes its state to a local terraform.tfstate file — fine solo, but it's a single point of failure (lost laptop = lost record of what's real) and can't be safely shared if more than one person ever runs Terraform against the same infrastructure.

Local state (default): terraform.tfstate sits on your machine only — no locking, no sharing, easy to lose Remote state (this project's plan): S3 bucket: stores the actual state file, versioned DynamoDB table: holds a lock while an apply is in progress, so two simultaneous applies can't corrupt the state

Kubernetes fundamentals — the concepts EKS is built on

AWS Notes → Containers already covers what EKS is (AWS's managed Kubernetes control plane) — this section covers what Kubernetes itself actually does, since nothing in this project has used it yet.

TermPlain-language meaning
ClusterThe whole system — a control plane (the "brain," managed by AWS in EKS) plus worker nodes (real EC2 instances that actually run your containers).
NodeOne worker machine (an EC2 instance) — has some amount of CPU/memory capacity, and runs however many Pods fit in it.
PodThe smallest deployable unit — one or more containers that always run together, on the same node, sharing network/storage. Almost always exactly one container per Pod in practice.
DeploymentDeclares "I want N copies of this Pod running, always" — Kubernetes continuously works to keep that true, replacing a Pod automatically if it crashes.
ServiceA stable network identity for a set of Pods — Pods get replaced constantly (new IP each time), a Service gives other things a fixed name/address to reach whichever Pods are currently alive.
IngressRoutes external HTTP(S) traffic into the cluster, to the right Service, based on path/hostname — this project's equivalent of what nginx did for the dashboard locally.
ConfigMap / SecretKubernetes-native ways to inject configuration/env vars into a Pod — the cluster-native replacement for docker-compose's environment: block and the local .env file.
StatefulSetLike a Deployment, but for things that need stable identity and storage across restarts — the right choice for self-hosted Kafka/RabbitMQ/MongoDB/Redis, since a plain Deployment assumes Pods are fully interchangeable and stateless.
HPA (Horizontal Pod Autoscaler)Watches a metric (usually CPU%) and automatically changes a Deployment's replica count to match real load — the Kubernetes-native version of an AWS Auto Scaling Group, but scaling Pod count instead of EC2 instance count.

Docker Compose → Kubernetes, term by term

docker-compose.yml conceptKubernetes equivalent
One service's build:/image:A container image, pushed to ECR, referenced in a Deployment's Pod spec
environment:A ConfigMap (plain config) or Secret (sensitive values), referenced by the Deployment
ports:A Service exposing the Pod's container port inside the cluster
depends_on:No direct equivalent — Kubernetes doesn't guarantee startup order the way Compose's depends_on implies; services are expected to retry their own dependencies (a real, deliberate philosophy difference, not a missing feature)
One docker compose up for everythingOne Deployment + Service (+ sometimes Ingress) YAML file per service, applied individually or together

A minimal real Deployment + Service

apiVersion: apps/v1
kind: Deployment
metadata:
  name: move-entitlement-service
spec:
  replicas: 2
  selector:
    matchLabels: { app: move-entitlement-service }
  template:
    metadata:
      labels: { app: move-entitlement-service }
    spec:
      containers:
        - name: move-entitlement-service
          image: <account-id>.dkr.ecr.us-east-1.amazonaws.com/move-entitlement-service:latest
          ports: [{ containerPort: 8082 }]
          envFrom:
            - configMapRef: { name: move-entitlement-config }
---
apiVersion: v1
kind: Service
metadata:
  name: move-entitlement-service
spec:
  selector: { app: move-entitlement-service }
  ports: [{ port: 8082, targetPort: 8082 }]

replicas: 2 is the whole point of moving to Kubernetes over Compose — two independent copies of this service run simultaneously, on whichever nodes have capacity, and Kubernetes keeps that true automatically if either one crashes.

This project's specific decisions

Why Postgres moves to RDS, but Kafka/RabbitMQ/MongoDB/Redis stay self-hosted on EKS
Self-hosting a stateful database on Kubernetes is genuinely operationally hard — storage, backups, failover, and upgrades all become your problem instead of AWS's. Real companies almost universally use RDS/Aurora over self-hosted Postgres-on-K8s for exactly that reason, which makes it the single most common "why not just run it in a pod" interview question in this space. Migrating every data service to its AWS managed equivalent (MSK for Kafka, Amazon MQ for RabbitMQ, DocumentDB for MongoDB, ElastiCache for Redis) would demonstrate the same underlying idea five times over, at real added cost and complexity — so this phase migrates the one that best makes the point (Postgres → RDS) and keeps the rest as Kubernetes StatefulSets, with the reasoning for why they'd move too in a real company documented here rather than actually provisioned.

Interview Q&A

Why use Terraform instead of just creating resources through the AWS Console?
Infrastructure as Code makes the environment reproducible, reviewable, and versioned the same way application code is — a teammate can see exactly what infrastructure exists by reading the .tf files, changes go through the same pull-request review process as code, and rebuilding an identical environment (or a second one) is a command, not a multi-hour manual click-through that's easy to get subtly wrong.
Why does Terraform state need a remote backend instead of a local file?
Local state is a single point of failure (lost laptop = lost record of what's actually real) and can't be safely used by more than one person — two people running apply simultaneously against the same local-state setup can corrupt it. A remote backend (S3 for the state file itself, DynamoDB for a lock) makes the state durable and shared, and the lock table prevents two concurrent applies from racing each other.
When would you use a StatefulSet instead of a Deployment?
A Deployment assumes every Pod is fully interchangeable and stateless — any replica can be killed and replaced with a fresh one with no consequence. A StatefulSet is for workloads that need stable network identity and persistent storage tied to a specific Pod across restarts — a database is the textbook example, since replacing "database Pod #2" needs to come back with the same data and identity, not a blank new instance.
Why not just run Postgres in a Kubernetes StatefulSet instead of using RDS?
You technically can, but it shifts real operational burden onto your own team — storage provisioning, backup scheduling, failover, and version upgrades all become manual/self-managed problems instead of AWS's. RDS handles all of that as a managed service. Most real companies choose RDS/Aurora for exactly this reason; self-hosting a database on Kubernetes is usually reserved for cases with a specific reason a managed service doesn't fit (cost at extreme scale, a database engine RDS doesn't support, or a deliberate multi-cloud/portability requirement).
