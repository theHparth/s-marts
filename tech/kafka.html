Kafka Phase 10

Written from zero — this page assumes you've never touched Kafka before. For when each piece was introduced, see the Steps page → Phase 10.

Status: written ahead of the build
Phase 10 (Kafka) is starting now. Everything on this page reflects the planned implementation — read it now to get familiar with the tool before writing code, then it gets corrected/confirmed once each step is really built and tested.

Why this phase exists — the plain version, as a story

You already built RabbitMQ in Phase 4 — think of it as a mailroom. An envelope gets handed to a mailbox; the moment someone picks it up, it's gone. That's perfect for "make sure this one task happens exactly once" (a move got created, a claim got filed).

Shipment tracking is a completely different shape of problem. A single shipment might send a location ping every few seconds, for days. Nobody wants those thrown away the instant one reader sees them — a dashboard should be able to show live pings AND a report should be able to go back and look at yesterday's full history. That needs something that remembers everything, in order, forever (or for a configured retention window) — not a mailroom, a permanent, ever-growing log.

RabbitMQ (Phase 4) — a mailroom: Producer -> Exchange -> Queue -> Consumer reads it -> message is GONE Great for: "do this exact task once" Kafka (this phase) — a newspaper archive / a DVR recording: Producer -> Topic (a permanent, ordered shelf) -> message STAYS Any number of readers can each read the same shelf, at their own pace, even re-read old entries. Nothing is removed just because someone read it. Great for: "record a high-volume stream that many different things need to watch"
Why THIS project specifically needed it
Phase 6's Go Ingestion Service already receives shipment location pings and stores them in Postgres — but Postgres is a database you have to actively query. Nothing gets notified the instant a new ping arrives. This phase adds that: every ping also gets written to a Kafka topic, so future work (Phase 9's live dashboard feed, Phase 8's ML pipeline) can react to pings the moment they happen, without polling the database over and over.

What each piece is, in one line

TermPlain-language meaning
BrokerOne Kafka server — the "warehouse" that actually stores and serves the data. This project runs a single broker.
TopicThe name of one particular subject/stream — this phase creates exactly one, shipment.tracking. Think of it as one dedicated shelf.
PartitionA topic isn't one single shelf — it's split into multiple parallel shelves so writes and reads can happen at once. Each partition keeps its own strict order.
OffsetEvery message on a partition has a position number, starting at 0 and counting up forever. It's how a reader remembers "I've read up through position 42."
ProducerAnything that writes new messages onto a topic — the Go Ingestion Service, in this phase.
ConsumerAnything that reads messages off a topic — the demo Python consumer built this phase.
Consumer GroupA named team of consumers splitting the work — each partition is read by only one member of the group at a time, so a group processes a topic faster in parallel without any two members reading the same message.
Replication factorHow many extra copies of each partition Kafka keeps on other brokers, for durability if one broker dies. This project's single-broker dev setup uses a replication factor of 1 (no redundancy) — a real production cluster would use 3.
KRaftKafka's own modern built-in coordination system. Older Kafka required a separate tool called ZooKeeper to manage the cluster; KRaft mode removes that extra moving part entirely — one less thing to run.

Topics, partitions, and offsets — how ordering actually works

Topic: shipment.tracking, split into 3 partitions Partition 0: [msg@0] [msg@1] [msg@2] [msg@3] ... (strict order within this partition) Partition 1: [msg@0] [msg@1] [msg@2] ... Partition 2: [msg@0] [msg@1] ... A producer picks which partition a message goes to (often by hashing a key, e.g. shipment_id) — so every ping for the SAME shipment always lands on the SAME partition, keeping that one shipment's history in order. Kafka only guarantees order WITHIN a partition, never across partitions.
QuestionAnswer
Why split into partitions at all?Parallelism — multiple consumers in a group can each work on a different partition simultaneously, instead of one consumer processing everything one message at a time
Why does the same shipment always land on the same partition?Producers key messages by shipment_id — Kafka hashes that key to consistently pick one partition, so one shipment's pings are never processed out of order
What happens if a consumer crashes and restarts?It resumes from its last committed offset — Kafka remembers exactly where that consumer group left off, per partition

Kafka vs. RabbitMQ — restated from the Kafka side

RabbitMQKafka

Kafka in Docker — KRaft mode, no ZooKeeper

Modern Kafka images support running as a single self-contained broker with no separate ZooKeeper container — the simplest possible setup for local development.

  kafka:
    image: apache/kafka:3.8.0
    container_name: movetrack-kafka
    ports:
      - "9092:9092"
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093

Creating a topic explicitly (rather than relying on auto-creation) makes the partition count and replication factor a deliberate decision, not an accident of whichever client happened to touch it first:

docker exec -it movetrack-kafka /opt/kafka/bin/kafka-topics.sh \
  --create --topic shipment.tracking \
  --bootstrap-server localhost:9092 \
  --partitions 3 --replication-factor 1

Publishing from Go (kafka-go)

segmentio/kafka-go is pure Go — no C library dependency, which matters for this project since the Go Ingestion Service compiles to a single static binary in a minimal Docker image (see Go → Containerizing for why that mattered for the Postgres driver choice too).

import "github.com/segmentio/kafka-go"

writer := &kafka.Writer{
    Addr:     kafka.TCP("kafka:9092"),
    Topic:    "shipment.tracking",
    Balancer: &kafka.Hash{}, // key-based partitioning — same shipment_id, same partition
}

err := writer.WriteMessages(context.Background(), kafka.Message{
    Key:   []byte(ping.ShipmentID),
    Value: pingJSON,
})

kafka.Hash{} is what makes the "same shipment always lands on the same partition" guarantee from the concepts section above actually happen — it hashes the Key to consistently choose a partition.

Consuming from Python (kafka-python)

A small standalone script, not a web service — its only job is to prove the whole pipeline works end-to-end by printing every message it receives.

from kafka import KafkaConsumer
import json

consumer = KafkaConsumer(
    "shipment.tracking",
    bootstrap_servers="kafka:9092",
    group_id="demo-consumer",
    value_deserializer=lambda v: json.loads(v.decode("utf-8")),
    auto_offset_reset="earliest",
)

for message in consumer:
    print(f"partition={message.partition} offset={message.offset} value={message.value}")
ArgumentWhat it controls
group_idNames this consumer's group — Kafka tracks this group's progress separately from any other group reading the same topic
auto_offset_reset="earliest"The very first time this group connects (no committed offset yet), start from the beginning of the topic instead of only new messages going forward

Interview Q&A

Why does Kafka split a topic into partitions instead of just one ordered log?
A single log can only be written to and read from sequentially — that caps throughput at whatever one disk/one process can handle. Splitting into partitions lets multiple producers write and multiple consumers (in a group) read in parallel, each working on a different partition — trading "one global order" for "strict order per partition, plus much higher throughput."
If a topic has 3 partitions and you add a 4th consumer to the group, what happens?
It sits idle. Kafka assigns each partition to exactly one consumer within a group at a time — with 3 partitions, at most 3 consumers in that group can be doing work simultaneously. The partition count is the real ceiling on a consumer group's parallelism, decided up front when the topic is created.
How would you replay a topic's history from the very beginning?
Start a consumer with a brand-new group_id (one Kafka has never seen before) and auto_offset_reset="earliest" — since that group has no committed offset yet, Kafka starts it at the oldest retained message. This is the core capability RabbitMQ's mailroom model doesn't have at all — a consumed RabbitMQ message is simply gone.
