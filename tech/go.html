Language basics

Go's syntax is deliberately small — this is close to the entire core language.

package main               // every executable Go program starts with package main

import (
    "fmt"
)

func main() {               // the entry point — same role as Java's public static void main
    var name string = "MoveTrack"  // explicit type
    count := 5                      // := infers the type — shorthand for var count int = 5

    fmt.Println(name, count)
}
SyntaxMeaning
var x Type = valueExplicit variable declaration
x := valueShort declaration — type inferred from the value. Only usable inside a function, not at package level.
func name(args) ReturnType { ... }Function definition — return type comes after the parameter list, opposite of Java/TypeScript order
if err != nil { ... }Go's error-handling idiom — see the dedicated section below
&x / *xAddress-of / dereference — Go has pointers (unlike Java), used constantly (e.g. rows.Scan(&p.DeviceID, ...))
[]TypeA slice — Go's dynamic array, closest equivalent to a Java List<T>
Error handling — no exceptions, no try/catch
Go doesn't have exceptions for ordinary error handling. Functions that can fail return an extra error value as their last return, and you check it explicitly every time: 
db, err := sql.Open("postgres", dsn)
if err != nil {
    log.Fatal(err)
}
This is verbose compared to Java's try/catch or Python's exceptions, but deliberate — every place an operation can fail is visible in the code, not hidden behind an invisible throw that might surface three call-frames away.

No separate runtime to install
Once compiled, a Go binary runs standalone — no JVM, no Python interpreter, no Node runtime needed on the machine it runs on. This is the direct cause of Phase 6's Dockerfile needing almost nothing in its final stage — see Containerizing below.

HTTP server & routing

net/http is Go's standard-library web server — no framework install needed, unlike Spring (spring-boot-starter-webmvc) or Python (FastAPI).

mux := http.NewServeMux()
mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintln(w, `{"status":"ok"}`)
})
mux.HandleFunc("POST /ingest", handleIngest)

http.ListenAndServe(":8090", mux)
PieceRole
http.NewServeMux()The router — maps a method+path to a handler function. Same job as Spring's @GetMapping/@PostMapping or FastAPI's @app.get/@app.post.
"GET /health"Go 1.22+'s combined method-and-path routing pattern — before 1.22 you had to check r.Method by hand inside the handler.
http.ListenAndServeStarts the server and is the whole app in one call — Go has no separate "app definition vs. server" split the way FastAPI (Uvicorn) or Spring Boot (Tomcat, though bundled) do.

Structs as DTOs

type ShipmentPing struct {
    DeviceID  string  `json:"device_id"`
    Latitude  float64 `json:"latitude"`
    Longitude float64 `json:"longitude"`
    Timestamp string  `json:"timestamp"`

The backtick text after each field is a struct tag — metadata encoding/json reads to map the Go field name to a JSON key. Without it, JSON output would use the Go field name ("DeviceID") as-is.

Concurrency — goroutines & sync.Mutex

Every incoming HTTP request in Go runs on its own goroutine automatically — a lightweight concurrent unit, far cheaper than an OS thread, that net/http spins up for you with zero configuration.

Why that means shared state needs a lock
Two requests can hit the same handler at literally the same moment. If both try to modify a shared in-memory value (like an in-memory slice of pings) at once, the result is corrupted data — a data race. 
var (
    pings   []ShipmentPing
    pingsMu sync.Mutex
)

pingsMu.Lock()
pings = append(pings, p)
pingsMu.Unlock()
sync.Mutex ensures only one goroutine touches pings at a time. Contrast: Node sidesteps this with a single-threaded event loop; Java has the same underlying risk with shared state, usually hidden behind Spring-managed, request-scoped beans. Go makes you handle it explicitly — once Postgres replaces the in-memory slice (Step 45), the database itself handles concurrent writes safely and the mutex is no longer needed for that particular piece of state.

Database — database/sql, no ORM

import (
    "database/sql"
    _ "github.com/lib/pq"
)

db, err := sql.Open("postgres", dsn)

rows, err := db.Query(`SELECT device_id, latitude, longitude FROM shipment_pings`)
for rows.Next() {
    var p ShipmentPing
    rows.Scan(&p.DeviceID, &p.Latitude, &p.Longitude)
}
PieceWhat it does
database/sqlGo's standard database interface — same role as Java's JDBC: driver-agnostic, a separate package plugs in the actual database support.
_ "github.com/lib/pq"A blank import — the package is never referenced by name in the file, only imported for its side effect (registering itself with database/sql on load). The underscore tells Go this is intentional, not an accidental unused import.
$1, $2, ...Postgres-style positional query placeholders — same purpose as JDBC's ?, prevents SQL injection by never string-concatenating user input into a query.
rows.Scan(&p.DeviceID, ...)Reads one row's columns into struct fields, in SELECT order. Needs pointers (&) since Scan writes into the given variables.
Why no JPA/Hibernate-style ORM
Go doesn't have a dominant, widely-used ORM the way Java has JPA/Hibernate. Raw SQL via database/sql is the idiomatic default in the Go ecosystem — worth naming this contrast directly if asked "how does data access differ between the Java and Go services in this project."

General SQL reference (joins, subqueries, indexes, and more) lives on the SQL Notes page.

How this maps to the layers you already know

Go doesn't enforce a framework-level Controller/Service/Repository split the way Spring does — there's no @RestController/@Service/@Repository annotation system. This project's shipment ingestion service still separates concerns, just by plain file/function organization instead of framework-enforced layers:

Spring layerThis Go service's equivalent
@RestController (routes + request handling)handleIngest/handleListIngest functions in main.go
@Service (business logic)validatePing and similar plain functions
@Repository/JpaRepository (data access)insertPing/listPings in db.go, hand-written SQL
DTOShipmentPing struct — used as both the request/response shape and passed straight into the SQL functions, no separate DTO-vs-entity split for a service this small

The lesson: Spring's layered architecture is a framework convention, not a law of software — Go achieves the same separation of concerns with far less ceremony, at the cost of more manual wiring (no dependency injection container, no auto-configuration).

Testing — testing package & table-driven tests

Same underlying concept as JUnit/Vitest/pytest, a 4th toolchain now. Discovery: functions named TestXxx(t *testing.T) in files named *_test.go.

func TestValidatePing(t *testing.T) {
    cases := []struct {
        name    string
        ping    ShipmentPing
        wantErr bool
    }{
        {"valid ping", ShipmentPing{DeviceID: "truck-1"}, false},
        {"missing device id", ShipmentPing{}, true},
    }

    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) {
            err := validatePing(c.ping)
            if (err != nil) != c.wantErr {
                t.Errorf("got %v, wantErr %v", err, c.wantErr)
            }
        })
    }
}
Table-driven tests — the idiomatic Go pattern
Instead of one test function per case (JUnit/pytest style), Go convention is a slice of cases run through one loop via t.Run, which creates a named sub-test per case — a failure reports exactly which row in the table broke.

net/http/httptest gives the same "slice test" idea as @WebMvcTest/React Testing Library/FastAPI's TestClient — build a fake request, call the handler function directly, no real server or socket involved.

req := httptest.NewRequest(http.MethodPost, "/ingest", body)
w := httptest.NewRecorder()
handleIngest(w, req)
// assert on w.Code, w.Body

Containerizing — an even smaller final image than Java's

FROM golang:1.23-alpine AS build
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o shipment-ingestion .

FROM alpine:3.20
WORKDIR /app
COPY --from=build /app/shipment-ingestion .
EXPOSE 8090
CMD ["./shipment-ingestion"]
Why this is more extreme than Java's JDK→JRE split
Go compiles to a single, statically-linked binary — the final image needs no runtime at all, not even a JVM or interpreter. CGO_ENABLED=0 disables Go's C-interop, forcing a fully static binary with zero dynamic library dependencies — what makes it safe to run on Alpine (a minimal distro with a different C library than most) without a missing-library error. The final stage could even be FROM scratch (a completely empty, zero-OS image) for the absolute minimum size; this project uses alpine instead specifically to keep a shell available for docker exec -it ... sh debugging.

Interview Q&A

Why does the in-memory version of this service need a sync.Mutex?
Every HTTP request in Go runs on its own goroutine automatically. Two requests can hit the same handler at the same moment and both try to modify shared state (like an in-memory slice) simultaneously, corrupting it. The mutex ensures only one goroutine touches that shared state at a time — once Postgres replaces the in-memory slice, the database handles concurrent writes safely instead.
Why does the Go service use raw SQL instead of an ORM like the Java services do?
Go doesn't have a dominant, widely-used ORM the way Java has JPA/Hibernate. Raw SQL via the standard library's database/sql package is the idiomatic default in the Go ecosystem — a deliberate ecosystem difference, not a shortcut taken for this project specifically.
How does Go handle errors if it doesn't have exceptions?
Functions that can fail return an extra error value as their last return, checked explicitly with if err != nil at each call site. More verbose than try/catch, but it makes every failure-prone operation visible in the code instead of relying on an exception that might surface several call-frames away from where it was thrown.
What does _ "github.com/lib/pq" do if the package name is never used?
It's a blank import — imported purely for its side effect. The pq package registers itself with database/sql when it loads, via its own init() function. The underscore tells Go's compiler "this unused import is intentional," since Go normally refuses to compile with an unused import.
