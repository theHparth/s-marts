Docker & Compose

Fundamentals + how this project actually uses it. For when each piece was introduced, see the Steps page.

Why Docker is here, what it does, where it fits

QuestionAnswer
Why does this project use Docker at all?Every service in this project is a different language/runtime (Java, Python, Go, Node) — Docker is what lets all of them run together, on the same machine, without each one's dependencies conflicting with the others.
What does it actually do here?Packages each service into a self-contained image (its own runtime + code, nothing borrowed from the host), and Docker Compose starts/networks all of them together with one command.
Where does it sit in the system?Underneath everything — every service, database, and infra tool in this project (Postgres, Mongo, RabbitMQ, Kafka, Jenkins, all 5 backend services, the dashboard) runs as a container.
When did this project start using it, and why not later?From Step 2 (Phase 1) — a local Postgres via Compose, before any real backend code existed. Reproducibility mattered from day one: the exact same setup works on any machine, not just "it works on mine."

What each one is, in one line

TermWhat it is
DockerRuns an app inside an isolated container — its own filesystem, processes, network — without a full virtual machine.
ImageA frozen snapshot (filesystem + config) a container is created from — e.g. postgres:17-alpine.
ContainerA running (or stopped) instance of an image.
Docker ComposeDefines multiple containers, their config, and how they connect, in one YAML file — docker compose up starts the whole set together instead of one long docker run command per container.
DockerfileThe recipe for building one image — what base image, what files to copy in, what command starts the app. Used by docker build.
Dockerfile vs. docker-compose.yml — different jobs
Dockerfile = the recipe card for one dish. docker-compose.yml = the whole dinner party plan — which dishes get served together, how the table's arranged (networking), what's in the fridge (volumes). This project's postgres service uses a pre-built image (image: postgres:17-alpine, pulled from Docker Hub — no Dockerfile needed, we didn't write Postgres). Our own services use build: ./services/<service> instead, pointing at a Dockerfile we wrote, since there's no pre-made image for code we haven't built yet.

Where Docker actually stores things

  • Same physical computer, different filesystem. On Windows, Docker Desktop runs a lightweight Linux VM via WSL2, and every image/container lives inside one large virtual disk file (%LOCALAPPDATA%\Docker\wsl\data\ext4.vhdx) — a complete filesystem packed inside one opaque file Windows can't browse directly. Not remote, not cloud — just not a normal folder tree.
  • COPY without --from= pulls from your real project folder (the build context — whatever folder you ran docker build from) into the image being built. A one-time snapshot: editing your real files afterward doesn't change an already-built image.
  • COPY --from=<stage-name> pulls from an earlier build stage's own filesystem instead — Docker talking to itself, your computer not involved at all for that specific line. This is what makes multi-stage builds work (next section).
  • Every service gets a fully separate build. Claims Service and Move & Entitlement Service each have their own Dockerfile, built with their own separate docker build run from their own folder — one build process can't see the other service's files at all, since the build context defines the entire universe of files that build has access to.

Multi-stage builds

This project's service Dockerfiles all follow the same two-stage pattern:

FROM eclipse-temurin:25-jdk AS build
WORKDIR /app
COPY .mvn/ .mvn/
COPY mvnw pom.xml ./
RUN ./mvnw dependency:go-offline
COPY src ./src
RUN ./mvnw clean package -DskipTests

FROM eclipse-temurin:25-jre AS run
WORKDIR /app
COPY --from=build /app/target/<service>-*.jar app.jar
EXPOSE <port>
ENTRYPOINT ["java", "-jar", "app.jar"]
StageBase imageHas
buildFull JDKCompiler, Maven wrapper, source code, dependency cache — everything needed to produce the jar
runJRE only, no compilerJust the final .jar, copied from stage 1 via COPY --from=build
Why two stages instead of one
The final image only contains stage 2's contents — none of stage 1's build tools, source code, or Maven cache ship to production. Smaller image, faster to pull/deploy, smaller attack surface (no compiler sitting in a production container). Copying pom.xml before src/, and running dependency:go-offline in between, is also deliberate — Docker caches each instruction as a layer, so dependencies only re-download when pom.xml actually changes, not on every source edit.

.dockerignore (same idea as .gitignore) keeps target/, IDE files, and .git/ out of the build context entirely, so they're never even candidates for the COPY in stage 1.

The Node/Nginx variant — a static frontend, not a running process

FROM node:24-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

FROM nginx:alpine AS run
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80

Same multi-stage idea as the Java services, applied to a different kind of artifact:

  • COPY package*.json ./ → RUN npm install → COPY . . is the same layer-caching trick as pom.xml/mvnw dependency:go-offline — copy just the dependency manifest first so the install step is cached and skipped when only source changes, not the manifest.
  • What COPY . . actually does: first . = source = the build context on the host (everything in the folder you ran docker build from); second . = destination = the current WORKDIR inside the image (/app). It re-copies package.json too (harmless, identical bytes) along with everything else that wasn't copied yet.
  • Why stage 2 is Nginx, not a JRE: npm run build produces only static files (HTML/CSS/JS) — there's no running program left, unlike a Spring Boot jar. Nginx's only job is serving those files to a browser over HTTP.
  • Why /usr/share/nginx/html specifically: Nginx's own default document root, baked into the official nginx image with zero config from us — documented directly on that image's Docker Hub page as the intended "drop your static site here" location. General habit: an official image's Docker Hub page almost always documents this kind of default path.
EXPOSE is documentation, not an action
EXPOSE 80 does not publish the port or make it reachable from the host — it's purely metadata, telling anyone reading the Dockerfile which port the container's process listens on internally. The actual publish step is docker-compose.yml's ports: line (e.g. "3000:80") — EXPOSE documents, ports: publishes. Two different jobs that look related.

The compose file

This project's docker-compose.yml lives at the repo root (not inside any service folder) since it's meant to eventually orchestrate every backend service, not just one:

services:
  postgres:
    image: postgres:17-alpine
    container_name: movetrack-postgres
    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
KeyWhat it does
imageWhich snapshot to build the container from — -alpine variants are the small/minimal-OS flavor, common default for services that don't need much beyond the software itself.
container_nameA fixed, predictable name (movetrack-postgres) instead of Compose's auto-generated <project>-<service>-<n> pattern.
environmentEnv vars passed into the container. ${POSTGRES_DB} syntax pulls the value from a .env file automatically — Compose reads one in the same folder without being told to.
ports: "5432:5432"host:container — maps port 5432 on your actual machine to port 5432 inside the container. Without this, the container's port is only reachable from other containers, not from your laptop.
volumesA named volume (postgres_data) persists the database's files outside the container's own filesystem — survives docker compose down, only lost if the volume itself is explicitly deleted.
Best way to remember
No top-level version: key needed — that field is deprecated in current Compose and safe to leave out entirely, even though a lot of older tutorials still show it.

Multiple databases, one container

  • The limit: the POSTGRES_DB environment variable only creates one database, the very first time the container starts on an empty volume. A second service needing its own database in the same container needs a different mechanism.
  • The mechanism: Postgres's own official image runs a startup script that checks a fixed path, /docker-entrypoint-initdb.d, every time it boots — any .sql/.sh files found there get executed, in alphabetical order, but only on a genuinely empty data directory (true first-time initialization).
  • Getting a local file into that path: a bind mount — host-folder:container-path, same syntax as ports but for folders. A container can't see the host filesystem at all unless a mount explicitly exposes part of it.
# infra/postgres-init/init-claims-db.sql
CREATE DATABASE claims_db;
# docker-compose.yml, postgres service
volumes:
  - postgres_data:/var/lib/postgresql/data
  - ./infra/postgres-init:/docker-entrypoint-initdb.d
Init scripts don't run on an already-initialized volume
Adding the mount alone does nothing if postgres_data already has data in it from a previous docker compose up — Postgres only treats a completely empty data directory as "first boot." Forcing a genuine fresh start requires deleting the volume, not just the container: docker compose down -v (note the -v — this project's every earlier down omitted it deliberately) followed by docker compose up -d. Only safe to do casually before any real data exists.

Checking what actually exists inside the container

docker exec -it movetrack-postgres psql -U movetrack -l

docker exec -it runs a command inside an already-running container — here, launching psql (Postgres's own CLI) and asking it to list every database (-l). Prompts for the password set in .env.

Official docs: psql

Container networking — service names, not localhost

  • Compose automatically creates a private network shared by every service in the same docker-compose.yml. Each service can reach the others by service name — like a hostname — but not by localhost. From inside a container, localhost means that container itself, not a sibling container.
  • This project's services keep localhost in application.properties (for running via mvnw spring-boot:run directly on the host, where Postgres's port is published to localhost) and override it in docker-compose.yml for the containerized case:
claims-service:
    build: ./services/claims-service
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/claims_db

postgres here is the Postgres service name from the same compose file — resolved by Docker's internal DNS to the actual Postgres container. Spring Boot's relaxed binding maps the env var SPRING_DATASOURCE_URL straight onto the spring.datasource.url property, overriding whatever's in application.properties without touching the file or the code.

Confirmed, not assumed
Verified via docker compose logs <service> — Hibernate's own startup log prints the actual JDBC URL it connected with, e.g. Database JDBC URL [jdbc:postgresql://postgres:5432/claims_db]. Seeing postgres instead of localhost there is direct proof the override actually took effect, not just that the container started.
depends_on is not a readiness check
depends_on: - postgres only controls start order — Compose starts Postgres's container first. It does not wait for Postgres to actually be ready to accept connections; a container can report "started" before the database engine inside it has finished initializing. Not fixed pre-emptively here (no healthcheck yet) — if a dependent service ever fails to connect on first boot because of this, that's the point to add one, not before.

Docker, nginx, and Jenkins — how they actually relate

These three get mentally lumped together because they all showed up around the same time in this project, but they're not peers — they sit in completely different layers, and two of them (nginx and Jenkins) never talk to each other at all.

Your machine ┌────────────────────────────────────────────────────────────┐ │ Docker Engine (the ONE host daemon) │ │ the single program that actually runs every │ │ container in this project │ └───────────────────────────┬────────────────────────────────┘ │ manages, side by side ┌──────────┬───────────┼───────────┬───────────┐ ▼ ▼ ▼ ▼ ▼ postgres mongodb rabbitmq jenkins dashboard :5432 :27017 :5672 :8080 ┌────────┐ │ │ nginx │ :3000→80 │ │ serves │ │ │ React │ │ │ files │ │ └────────┘ │ └── special: reaches back OUT to Docker Engine via a mounted socket ("build this image", "run Trivy", "run ZAP")
What it actually isTalks to
DockerThe engine every container in this project runs on — Postgres, Mongo, RabbitMQ, Jenkins, the dashboard, all of itEverything depends on it; it depends on nothing else here
nginxA small web server whose only job is handing out the React app's built static filesLives entirely inside the dashboard container — never talks to Jenkins or Docker directly
JenkinsThe CI pipeline runner — itself just another container Docker happens to be runningReaches back out to Docker Engine (its own host) through a mounted socket, to spin up sibling containers for builds/scans
The one-sentence version
Docker is the landlord who owns the building and runs every apartment. nginx is one tenant (living inside the dashboard apartment) whose only job is handing out files. Jenkins is a different tenant who happens to have a master key to call the landlord directly and say "build me a new apartment" — completely unrelated to what the nginx tenant does. See below for exactly how that "master key" (the Docker socket mount) works and where it goes wrong.

Docker-outside-of-Docker (DooD) — the socket-mount pattern's real gotcha

Mounting the host's Docker socket into a container (-v /var/run/docker.sock:/var/run/docker.sock, used for Jenkins in Phase 5) lets that container run docker commands — but it's a genuinely common source of confusion about whose filesystem those commands actually operate on.

Jenkins container Host's Docker daemon ┌─────────────────────┐ ┌─────────────────────────┐ │ sh 'docker run │ ── via socket ──►│ actually creates and │ │ -v X:Y ...' │ │ runs the new container │ └─────────────────────┘ └─────────────────────────┘ The command is TYPED inside the Jenkins container, but EXECUTED by the host daemon. "X" in -v X:Y has to mean something to the HOST, not to Jenkins's own filesystem.
Real mistake — $(pwd) inside a DooD container isn't a real host path
A command like docker run -v $(pwd):/target ..., run from inside a container that reached Docker via a mounted socket, resolves $(pwd) to a path inside that container's own filesystem (e.g. /var/jenkins_home/workspace/...) — which means nothing to the host daemon actually creating the new container. The mount silently doesn't do what you'd expect, or the tool being run refuses to start because "nothing is actually mounted there."

Fix used in this project: mount a named Docker volume instead of a bind-mount path. Named volumes are managed by the daemon itself, not tied to any one container's filesystem view — so the same named volume can be mounted into both the Jenkins container (at /var/jenkins_home) and a separately-launched tool container (at whatever path that tool needs), and both genuinely share the same storage. See Jenkins, Trivy & OWASP ZAP → OWASP ZAP for the real example (a ZAP scan writing its report into the same volume Jenkins already has, so Jenkins can find and archive it afterward).

Keeping secrets out of git

  • What: real values live in .env (gitignored — covered by the root .gitignore's .env / .env.* / !.env.example rules). A parallel .env.example, committed, lists the same variable names with empty/placeholder values.
  • Why even for a throwaway local dev password: the habit matters more than this specific value — the same pattern is what prevents a real secret from ever being committed later.
This project's tradeoff, stated honestly
application.properties (inside the service, also committed to git) hardcodes the same local dev values directly rather than reading them from environment variables — a deliberate simplification for local-only development. A real deployed environment (Phase 15, AWS/Terraform) will use actual secrets management instead; not solved today, flagged here so it's not mistaken for the production pattern.

Commands — docker stop vs. docker compose down

CommandWhat it doesContainer still exists after?
docker stop <name>Stops the running process inside the containerYes — docker start <name> brings it back with the exact same config
docker compose downStops and deletes the container(s) + the network Compose createdNo — next up builds fresh ones from the compose file
  • docker stop works on any container by name, one at a time — not Compose-aware.
  • docker compose down / docker compose stop act on every service in that project's compose file at once, using the file as the source of truth.
  • Neither touches a named volume unless down is run with an explicit -v flag.
Why this distinction actually mattered here
A container created during a failed first attempt can end up with broken config baked in (see Steps → Step 2 for the real incident). stop+start just restarts that same broken container. down+up deletes it and builds a genuinely new one — the only way to actually fix a bad container, not just pause it.

-d flag (detached mode)

  • Without it: docker compose up takes over the terminal, streaming live logs; closing the terminal or Ctrl+C stops the containers.
  • With -d: starts the containers in the background and returns the terminal immediately — what this project always uses, since Postgres needs to keep running while work continues elsewhere.
  • To see a detached container's logs later: docker compose logs -f (-f = follow).

Dockerfile CMD — one command, not several

Easy to misread at first glance: CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"] looks like a list of separate things happening one after another. It isn't — it's one program (the first element) plus the arguments passed to it (everything after), written out as an array instead of one plain string.

# these two lines do the exact same thing:
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
CMD uvicorn app.main:app --host 0.0.0.0 --port 8000
FormHow it runs
Exec form — CMD ["a", "b", "c"]Docker runs the process directly, with that array as its argument list. No shell involved.
Shell form — CMD a b cDocker wraps it as /bin/sh -c "a b c" first, then that shell runs the process.
Why exec form is preferred
In exec form, the process you named (e.g. uvicorn) becomes PID 1 inside the container. In shell form, /bin/sh becomes PID 1 instead, with your actual process running underneath it — and a shutdown signal from docker stop goes to PID 1 first. A shell doesn't always forward that signal to its child process, which can mean docker stop has to wait out a timeout and force-kill instead of the app shutting down cleanly.

Telling Compose-managed containers apart from ad-hoc ones
Compose auto-names containers <project>-<service>-<n> (or uses an explicit container_name: override, like movetrack-postgres). A random two-word name like relaxed_leavitt is Docker's own auto-generated name for a container started without --name — a reliable sign it came from a manual docker run, not any project's compose file.

Interview Q&A

Why can't you just use $(pwd) as a bind-mount path from a container that reached Docker via a mounted socket?
The command runs inside that container but is executed by the host's Docker daemon — so any path in a bind-mount has to make sense to the host, not to the calling container's own filesystem. $(pwd) resolves to a path inside the calling container (like /var/jenkins_home/workspace/...), which the host daemon has no knowledge of. The fix is a named Docker volume instead of a bind-mount path — named volumes are daemon-managed, so the same one can be mounted into both containers and they'll genuinely share the same storage.
How do you confirm an edit to docker-compose.yml actually took effect?
docker compose config — it prints the fully resolved compose file, with any environment variables and defaults already interpolated, showing exactly what Compose is going to use. More reliable than assuming a saved edit is correct, especially after a repeated error suggests the "fix" didn't actually change anything.
What's the difference between a Docker image and a container?
An image is a frozen, read-only snapshot — filesystem plus config, like a class. A container is a running (or stopped) instance created from that image — like an object instantiated from that class. One image can produce many independent containers.
Why use a named volume instead of just letting the container store data in its own filesystem?
A container's own filesystem disappears the moment the container is deleted — exactly what docker compose down does. A named volume lives independently of any specific container, so the database's actual data survives a full container recreate (like the one this project's Incident 2 required) and is only lost if the volume itself is explicitly removed.
Why use a multi-stage Dockerfile instead of one stage that both builds and runs the app?
A single stage would ship the full JDK, Maven's dependency cache, and the source code inside the production image — bigger, slower to deploy, and a larger attack surface (a compiler sitting in production is pure downside). A second stage starting fresh from a JRE-only base image and copying in just the finished jar keeps the final image to only what's needed to run it.
Why doesn't localhost work for one container to reach another?
Inside a container, localhost always refers to that container itself, not a sibling. Docker Compose gives every service in the same compose file a private network where they can reach each other by service name instead — that's why this project overrides spring.datasource.url with the hostname postgres (not localhost) via an environment variable specifically for the containerized case, while local dev outside Docker keeps using localhost unchanged.
Is CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"] running multiple commands?
No — it's one program (the first array element) plus the arguments passed to it (everything after), written as an explicit array instead of one string Docker would otherwise have to split itself. Same idea as typing uvicorn app.main:app --host 0.0.0.0 --port 8000 on a command line — one process starts, reads its own argument list, and configures itself from it.
