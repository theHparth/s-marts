Java, Spring Boot & Maven

Fundamentals first. Covers every Java/Spring/Maven service in this project (Move & Entitlement, Claims, the SOAP Legacy Adapter). For when each piece was actually introduced, see the Steps page — this page is organized by concept, not by timeline.

What each one is, in one line

TermWhat it is
JavaThe programming language — compiled to bytecode, run by the JVM (Java Virtual Machine).
MavenThe build tool — reads a pom.xml file to know what dependencies to download, how to compile, test, and package the project into a runnable artifact (a .jar).
Spring BootA framework built on top of plain Spring — auto-configures a working web app/service with sensible defaults, so you're not hand-wiring every component.
Spring InitializrA project generator (web UI or API at start.spring.io) that produces a ready-to-build Maven project skeleton with the dependencies you pick already wired into pom.xml.
Best way to remember
Maven = the contractor that fetches materials and assembles the house. Spring Boot = a pre-fabricated house frame with plumbing and wiring already roughed in, so you're finishing rooms instead of laying a foundation from raw lumber every time.

Generating a new service (Spring Initializr)

Spring Initializr, via curl

  • What it does: hits Spring's own project-generator API and downloads a zipped, ready-to-build Maven project with the chosen dependencies already declared in pom.xml.
  • Windows gotcha: PowerShell aliases plain curl to Invoke-WebRequest, which does not understand -d the way real curl does — use curl.exe explicitly to get the actual curl binary that ships with Windows 10+.
  • Official docs: Spring Initializr

Reusable pattern for every Java service in this project — swap the artifact/package name per service:

curl.exe https://start.spring.io/starter.zip `
  -d dependencies=<comma-separated deps> `
  -d type=maven-project `
  -d language=java `
  -d javaVersion=21 `
  -d groupId=com.movetrackops `
  -d artifactId=<service-name> `
  -d name=<service-name> `
  -d packageName=com.movetrackops.<servicepackage> `
  -o <service-name>.zip

Expand-Archive -Path <service-name>.zip -DestinationPath . -Force
Remove-Item <service-name>.zip
How we use it in this project
Every Java microservice (Move & Entitlement, Claims, the SOAP Legacy Adapter) starts from this same generator call, living in its own services/<service-name>/ folder in the monorepo — only the dependency list, artifactId, and packageName change per service. Move & Entitlement used dependencies=web,data-jpa,postgresql,validation,lombok.

Project structure, once generated

move-entitlement-service/ +-- pom.xml <- Maven's manifest: deps, plugins, build config +-- src/ | +-- main/ | | +-- java/com/movetrackops/moveentitlement/ | | | +-- MoveEntitlementServiceApplication.java <- entry point, main() | | +-- resources/ | | +-- application.properties <- DB connection, port, etc. | +-- test/ | +-- java/com/movetrackops/moveentitlement/ <- JUnit tests mirror main's package structure +-- target/ <- build output (gitignored, regenerated every build)

pom.xml

  • What it is: Maven's project descriptor — XML file declaring the artifact's identity (groupId/artifactId/version), its dependencies, the Java version to compile against, and any build plugins.
  • Best practice: pin dependency versions through spring-boot-starter-parent (already set up by Initializr) rather than hardcoding versions per-dependency — one version bump in the parent keeps every Spring dependency compatible together.
  • Official docs: Introduction to the POM

Maven basics — commands used throughout

CommandWhat it does
mvn clean installDeletes old build output, compiles, runs tests, packages into a .jar in target/
mvn testRuns JUnit tests only, no packaging
mvn spring-boot:runRuns the app directly without building a jar first — fastest loop for local dev
./mvnwThe Maven Wrapper — runs Maven using a pinned version downloaded automatically, so you don't need Maven installed globally or version-matched across machines
Why the Maven Wrapper (mvnw) matters
Spring Initializr generates mvnw/mvnw.cmd automatically. Using .\mvnw.cmd clean install instead of a global mvn install means Jenkins (later in the roadmap) builds with the exact same Maven version as your laptop — a classic "works on my machine" gap this closes for free.

Annotations

  • What they are: metadata tags (@Something) attached to a class, method, or field. Unlike a Python decorator, an annotation doesn't execute or wrap anything by itself — it's inert data that other tools (the compiler, Spring's startup process, Lombok) scan for and react to.
  • Where they show up already: @SpringBootApplication (marks the one entry-point class Spring's bootstrap code looks for), @SpringBootTest (tells the test runner to boot the whole app for this test), @Test (marks a method as a JUnit test).
Best way to remember
A Python decorator is a verb — it does something the moment that line runs. A Java annotation is a label — it does nothing by itself, it just gets read later by whatever's looking for it.

Generated project walkthrough

What Spring Initializr actually produces before any real code is written:

FileWhat it is
MoveEntitlementServiceApplication.javaThe entry point. public static void main is required by Java for any runnable program; SpringApplication.run(...) starts the embedded server and wires up the whole app in one call — roughly comparable to uvicorn.run(app) in FastAPI, but bundling server startup and dependency-wiring together.
application.propertiesFlat key=value configuration file — starts with just spring.application.name=..., grows to hold the database connection once that's added. Comparable to a .env file; Spring also supports a YAML variant (application.yml) for nested config, not used here.
MoveEntitlementServiceApplicationTests.javaOne auto-generated smoke test, contextLoads(), with an empty body. @SpringBootTest forces the entire app to actually start for this test — the empty body means the only thing being verified is "did startup succeed at all." Trivial today, becomes meaningful once real config (a DB connection) exists to break.
Spring Boot 4 renamed some starters — don't be thrown by older tutorials
This project is on Spring Boot 4.1.0 (declared in pom.xml's <parent>). Most tutorials/StackOverflow answers online are written against Spring Boot 3.x and use different artifact names — most notably spring-boot-starter-web is now spring-boot-starter-webmvc (disambiguating it from the reactive -webflux starter), and the old single spring-boot-starter-test is now split into per-feature test starters (-data-jpa-test, -validation-test, -webmvc-test) matched to whatever production starters you actually picked.

spring.jpa.hibernate.ddl-auto=update

PropertyWhat it does
spring.datasource.urlA JDBC URL — protocol (jdbc:postgresql:), host, port, database name. Everything Hibernate/HikariCP needs to open a connection.
spring.datasource.username / .passwordMust match the POSTGRES_USER / POSTGRES_PASSWORD the Docker container was actually started with — a mismatch here fails at authentication, not at the network level (see the interview Q&A on Steps → Step 2 for how those two failure modes look different).
spring.jpa.hibernate.ddl-auto=updateHibernate creates/updates tables automatically from @Entity classes. Convenient for local dev — never used this way in a real deployed environment, where a migration tool (Flyway/Liquibase) owns schema changes instead. Not yet needed here.
spring.jpa.show-sql=truePrints every generated SQL statement to the console — useful while learning to see what Hibernate is actually doing, usually turned off (or routed to a real logger) once that's no longer needed.

Layers — DTO vs. entity vs. repository vs. service vs. config

LayerAnnotationHoldsReal-life equivalent
DTOplain class + @NotBlank etc.What crosses the wire — request in, response outThe intake form / the receipt
Entity@EntityData — one row per instanceThe claim paperwork itself
Repositoryextends JpaRepositoryFetch/save one entity, no logicThe filing cabinet + clerk
Service@ServiceBusiness rules, uses repositoriesThe adjuster following the rulebook
Config@ConfigurationPropertiesValues that shape behavior without touching codeThe sticky-note threshold on the adjuster's desk
Best way to remember
DTO = what the outside world sees. Entity = the thing itself. Repository = how you fetch/save the thing. Service = what you're allowed to do with the thing. Config = the numbers the Service reads to make that decision.
Why a DTO, not the Entity, over the wire
A JPA entity's shape is coupled to the database schema — renaming a column becomes a breaking API change if entities are exposed directly, and lazy-loaded fields can serialize badly. A DTO is a separate, deliberate contract: only what a client needs to send/receive, independent of how the data is actually stored.

Testing layers — how deep does each test go

AnnotationWhat it loadsUsed for
Plain JUnit + @MockNothing — no Spring at allPure business logic, e.g. ClaimApprovalServiceTest — fastest, most isolated
@WebMvcTest(Controller.class)Only the web layer — controllers, Jackson, validationTesting a controller's HTTP behavior without booting the whole app or touching a database
@SpringBootTestThe entire application contextThe generated smoke test (contextLoads()) — proves the whole app, including the real database connection, actually starts

Each is a deliberate trade-off between speed and how much is actually exercised — reach for the narrowest one that still tests what you actually care about.

Spring Boot 4.1 moved things — don't trust older tutorials blindly
Two real, confirmed package changes hit while writing ClaimControllerTest:
  • Jackson itself is now version 3.x, which renamed its base package from com.fasterxml.jackson to tools.jackson (confirmed from a JacksonAutoConfiguration condition-evaluation log naming tools.jackson.databind.json.JsonMapper). A test using the classic com.fasterxml.jackson.databind.ObjectMapper import fails to compile. Simplest fix: avoid the dependency entirely — write request bodies as raw JSON text blocks ("""...""") instead of serializing a DTO.
  • @WebMvcTest moved packages — old Boot 3.x import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest no longer resolves; current path is org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest. Found by cross-referencing a sibling class name already seen in an earlier stack trace, rather than guessing — same reorganization pattern as spring-boot-starter-webmvc (renamed from -web).
  • @MockBean → @MockitoBean — the older annotation (package org.springframework.boot.test.mock.mockito.MockBean) is superseded by org.springframework.test.context.bean.override.mockito.MockitoBean, which registers a Mockito mock as a real Spring bean in a test context (needed for @WebMvcTest, since MockMvc routes through actual Spring wiring — different from plain @Mock, which involves no Spring at all).

Interview Q&A

What's the difference between Spring and Spring Boot?
Spring is the underlying framework (dependency injection, MVC, data access abstractions) — powerful but historically required a lot of manual XML/Java config to wire together. Spring Boot is an opinionated layer on top: auto-configuration, an embedded server, and starter dependencies (spring-boot-starter-web, etc.) that pull in a coherent, working set of versions so you get a running app with minimal config.
Why JPA/Hibernate instead of writing raw SQL with JDBC directly?
JPA maps Java objects to rows so most CRUD never needs hand-written SQL, which is faster to write and less error-prone for straightforward access patterns. The tradeoff is less control over the exact query — for a genuinely complex or performance-critical query, dropping to a native query or raw JDBC for that one case is still normal and expected, not a sign JPA was the wrong choice overall.
Why not just return the JPA entity directly from a REST endpoint instead of mapping to a DTO?
It couples your public API shape to your database schema — a column rename in the entity becomes a breaking API change for every client. JPA entities can also have lazy-loaded fields that serialize unpredictably. A DTO is a deliberate, separate contract: only what a client actually needs, independent of how the data happens to be stored.
