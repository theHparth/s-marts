Jenkins, Trivy & OWASP ZAP Phase 5

Fundamentals + how this project actually uses it. For when each piece was introduced, see the Steps page → Phase 5.

Confirmed — built and verified through Step 62, extended in Phase 4
Phase 5 (Trivy/ZAP/Jenkins compliance gate) is complete. Jenkins runs as a container alongside everything from Phases 1-6, with a working pipeline: checkout → build → Trivy scan (gated) → Report Findings → ZAP baseline scan → archive reports. The Report Findings stage was added in Phase 4 — real Trivy JSON output now gets POSTed automatically to the Compliance Service instead of just sitting archived. This phase hit more real gotchas than any other — every one is documented inline below.

Why this exists — the plain-language version

Before any of the technical terms, the actual problem being solved:

WITHOUT this phase: code change → build it → ship it straight to users (nobody checks whether the build is actually safe) WITH this phase: code change → build it → an automatic inspector checks it → only ships if it passes (Jenkins is the inspector; Trivy and ZAP are what it checks)
TermPlain-language meaning
JenkinsThe inspector itself — shows up automatically every time something new is built, before it's allowed through
TrivyChecks the ingredients — every software package baked into the image, compared against a public "known dangerous" list
OWASP ZAPChecks the running thing itself — actually pokes at the live dashboard the way an attacker would, not just reading a label
The gate (--exit-code 1)What makes a bad finding actually stop the release, instead of just leaving a note nobody reads
Why THIS project specifically needed it
Phase 6 built shipment-ingestion — a real service that gets rebuilt every time its code changes. Without this phase, nothing stood between "someone changes the code" and "that change goes live" — no automatic check for whether the change introduced something genuinely unsafe. Jenkins/Trivy/ZAP is that missing checkpoint, wrapped around exactly that service.

What each piece is, in one line

ToolWhat it is
JenkinsA self-hosted CI/CD automation server — runs a defined sequence of steps (build, test, scan, deploy) every time it's triggered
PipelineJenkins's term for one automated job — defined as code in a Jenkinsfile, not clicked together in a UI
TrivyA vulnerability scanner for container images (and filesystems, git repos) — checks installed packages against known-CVE databases
OWASP ZAPA dynamic web application security scanner — sends real requests at a running application looking for actual exploitable issues
Trivy vs. ZAP — different scan categories, a real interview distinction
Trivy is closer to SCA (Software Composition Analysis) — it inspects what's installed in an image (OS packages, language dependencies) against CVE databases, without running anything. ZAP is DAST (Dynamic Application Security Testing) — it actually sends HTTP requests at a live, running application, probing for real exploitable behavior (SQL injection, XSS, misconfigured headers). Trivy asks "what known-vulnerable things did we ship?" ZAP asks "does the running app actually misbehave when attacked?" — different questions, both worth asking, which is why this phase runs both, not just one.

Jenkins basics — server, jobs, pipelines

  • Jenkins itself runs as a long-lived server process (this project runs it in Docker) with a web UI, default port 8080.
  • First-run setup requires an initial admin password, printed to the container's logs — a one-time unlock step, then you create a real admin account.
  • A Pipeline job points Jenkins at a Jenkinsfile — either pasted directly into the job config, or (the more realistic setup) checked out from this project's own git repo.
Jenkins vs. GitHub Actions — a real comparison, since this project already uses GitHub
JenkinsGitHub Actions
HostingSelf-hosted — you run the serverFully managed by GitHub, no server to run
Config locationJenkinsfile in the repo (or pasted into the job).github/workflows/*.yml in the repo
TriggerManual, polling, or a webhook you configure yourselfNative GitHub event triggers (push, PR, etc.), zero extra setup
Why Jenkins hereDeliberately chosen for this phase specifically because it's still extremely common in real enterprise environments (especially pre-cloud-native shops) — genuinely different skill from GitHub Actions, worth having both on a resume.

The Jenkins UI, step by step — where the real confusion happens

Jenkins's web UI is genuinely unintuitive the first time — every point below is somewhere this project's own build actually got stuck.

ScreenWhat you're doing there
Dashboard (localhost:8080)The home page — lists every job (pipeline) that exists. Empty the first time.
"New Item"Create a new job. Give it a name, choose Pipeline as the type (not "Freestyle project" — Pipeline is the code-defined, Jenkinsfile-based kind used in this project).
Job's "Configure" page → "Pipeline" sectionWhere you tell Jenkins where the Jenkinsfile actually comes from. This is the part that caused real confusion — see the box below.
"Build Now"The button that actually triggers a run, in the left sidebar of a job's page. Every single step in this phase ends with clicking this.
Build number (e.g. #1) → "Console Output"The full log of that specific run — every shell command's real output, in order. This is where you actually verify anything happened, not the pass/fail color alone.
Build number → "Build Artifacts"Files saved by archiveArtifacts — only appears after Step 60, and only if the archive step actually ran.
The "Pipeline" configuration section specifically — a dropdown, not a text field
The "Definition" control at the top of the Pipeline section is a dropdown — default value "Pipeline script," which shows a raw code-editor textarea below it for pasting a Jenkinsfile directly. The setting this project actually uses, "Pipeline script from SCM," has to be selected from that dropdown — typing the words "Pipeline script from SCM" into the textarea below it does nothing useful. Once genuinely selected, the whole form changes: the textarea disappears, replaced by real fields (SCM type, Repository URL, Credentials, Branches to build, Script Path). The "Branches to build" field in particular sits low enough on that form to look missing entirely if you don't scroll down.

Jenkinsfile — declarative pipeline syntax

pipeline {
    agent any

    stages {
        stage('Checkout') {
            steps {
                checkout scm
            }
        }
        stage('Build') {
            steps {
                sh 'docker build -t shipment-ingestion services/shipment-ingestion'
            }
        }
        stage('Scan') {
            steps {
                sh 'trivy image --exit-code 1 --severity HIGH,CRITICAL shipment-ingestion'
            }
        }
    }
}
PieceWhat it does
pipeline { }The whole job, declarative style — the modern, recommended Jenkinsfile syntax over the older "scripted" (raw Groovy) style
agent anyRun on any available Jenkins worker — this project only has one, so this is effectively "run right here"
stages { stage('Name') { steps { ... } } }A pipeline is a sequence of named stages, each with its own steps — the stage names are exactly what shows up in Jenkins's UI as the visual pipeline
sh '...'Runs a literal shell command — this is how Jenkins calls out to Docker, Trivy, and every other CLI tool it doesn't have native syntax for
Why the Jenkins container needs access to Docker itself
Running docker build inside a pipeline step means the Jenkins container needs to be able to run Docker commands — either by mounting the host's Docker socket (/var/run/docker.sock) into the Jenkins container, or running Docker-in-Docker. This project uses the socket-mount approach — simpler, though it does mean the Jenkins container can control the host's whole Docker daemon, worth naming as a real security tradeoff if asked about it.

Trivy — vulnerability scanning

trivy image --exit-code 1 --severity HIGH,CRITICAL shipment-ingestion
FlagWhat it does
imageScan a Docker image (Trivy can also scan filesystems, git repos, Kubernetes clusters)
--severity HIGH,CRITICALOnly report/act on these severity levels — filters out LOW/MEDIUM noise
--exit-code 1The actual gate mechanism — Trivy exits non-zero if it finds a matching vulnerability, which makes the Jenkins sh step fail, which fails the whole pipeline. Without this flag, Trivy just prints a report and exits 0 regardless of findings.
This is the actual "gate" — not a separate concept from the scan itself
A lot of the DevSecOps value here isn't Trivy's scan output — it's the fact that --exit-code 1 turns "here's a report" into "the build stops." Same underlying idea as a failing unit test blocking a merge — a security finding above the threshold is treated exactly like a broken build, not an FYI to read later.

OWASP ZAP — dynamic scanning

ZAP needs something actually running to attack — unlike Trivy, which only inspects a static image. The simplest way to run it in a pipeline is ZAP's own "baseline scan" Docker image, pointed at a running service's URL:

docker run --rm --network movetrack_ops_default -v movetrack_ops_jenkins_home:/zap/wrk/:rw -t zaproxy/zap-stable zap-baseline.py \
  -t http://dashboard:80 \
  -r zap-report.html || true
FlagWhat it does
--network movetrack_ops_defaultPuts the ZAP container on the same Docker network as this project's other containers — same container-networking rule as everywhere else, ZAP reaches the dashboard by service name, not localhost
-v movetrack_ops_jenkins_home:/zap/wrk/:rwSee the gotcha box below — this isn't optional
-t http://dashboard:80The target URL to attack — the dashboard container, by its Compose service name
-r zap-report.htmlWrite an HTML report of findings — requires /zap/wrk to be mounted (see below)
|| trueBaseline findings are reviewed, not hard-gated like Trivy's, for this phase — stops a ZAP finding from failing the whole build

A "baseline" scan is passive/light — it doesn't send genuinely destructive attack payloads, just checks for common misconfigurations and obvious issues. A "full" active scan exists too, but is much slower and more aggressive — baseline is the right default for a CI gate that needs to run on every build.

Real mistake — ZAP refuses to write a report unless /zap/wrk is mounted, and the naive fix doesn't work here
Without a mount at /zap/wrk, ZAP refuses to even start when a file-based option (-r zap-report.html) is given — it prints its own usage/help text and exits instead of scanning anything. Combined with || true, that "quit immediately" looked like a passing build. The obvious fix, -v $(pwd):/zap/wrk:rw, doesn't work here specifically because Jenkins reaches Docker through the host's socket — full explanation of why on Docker & Compose → Docker-outside-of-Docker. The actual fix: mount the same named volume Jenkins itself uses (movetrack_ops_jenkins_home) into the ZAP container too, then copy the resulting report from Jenkins's own view of that volume (/var/jenkins_home/zap-report.html) into the build workspace so archiveArtifacts can find it: 
sh 'cp /var/jenkins_home/zap-report.html "$WORKSPACE"/zap-report.html || true'

Archiving scan reports

stage('Archive Reports') {
    steps {
        archiveArtifacts artifacts: '*-report.html', allowEmptyArchive: true
    }
}

archiveArtifacts saves files from the build workspace as part of that build's permanent record in Jenkins — viewable/downloadable from the build's page in the UI afterward, the same way a GitHub Actions run lets you download build artifacts.

Report Findings stage — installing Python in the Jenkins image

The Jenkins container was built to run docker and git commands — nothing about the base image assumes Python will ever be needed inside it. The first attempt at a Python-based pipeline stage failed immediately:

+ pip install requests --quiet
/var/jenkins_home/.../script.sh.copy: 1: pip: not found

Fix — infra/jenkins/Dockerfile:

FROM jenkins/jenkins:lts-jdk17
USER root
RUN apt-get update && apt-get install -y docker.io python3 python3-pip
USER jenkins
pip vs. pip3
Debian's python3-pip package installs the binary as pip3, not a plain pip — the Jenkinsfile's sh commands needed updating to match (pip3 install requests --quiet --break-system-packages || pip3 install requests --quiet). Rebuilding the image after a Dockerfile change also needs an explicit docker compose build jenkins && docker compose up -d jenkins — editing the Dockerfile alone changes nothing until the image is actually rebuilt and the container restarted from it.

Editing the Jenkinsfile locally doesn't change what Jenkins builds

The Checkout stage (checkout scm) pulls the Jenkinsfile and code straight from GitHub, using whatever the job's Branches to build field points at — it never reads the local working directory at all. A local edit needs a real git push before a fresh Build Now will ever see it.

SituationWhat to set "Branches to build" to
Testing an in-progress feature branch mid-phase*/feature/your-branch-name
Normal, permanent setting once a phase is merged*/main — real CI watches the base branch, not a personal feature branch

See Git & GitHub → A branch disappearing right after merge for what happens if this field gets left pointed at a feature branch after it's already been squash-merged and deleted.

Interview Q&A

Why did the ZAP scan stage show green even though it never actually scanned anything?
ZAP refuses to run when a file-output option is given but its expected working directory (/zap/wrk) isn't mounted — it prints usage/help and exits instead of scanning. Combined with a trailing || true (added so ZAP findings wouldn't hard-fail the build), that immediate exit looked like a pass. A green stage proves the shell command exited 0 — it doesn't prove the tool actually did the thing you intended. Worth checking the actual console output content, not just the pass/fail color, especially around any command with || true.
What's the difference between what Trivy and OWASP ZAP each check for?
Trivy is SCA (Software Composition Analysis) — it inspects what's installed in an image (OS packages, language dependencies) against known-CVE databases, without running anything. ZAP is DAST (Dynamic Application Security Testing) — it sends real HTTP requests at a live, running application, probing for actual exploitable behavior. Trivy catches "known-vulnerable software we shipped"; ZAP catches "the running app actually misbehaves under attack" — different failure modes, which is why a real gate runs both.
How does a Trivy scan actually block a build, not just report findings?
--exit-code 1 makes Trivy exit non-zero when it finds a vulnerability at or above the specified severity. Since a Jenkins pipeline stage fails when its shell command exits non-zero, this single flag is what turns "print a report" into "stop the pipeline" — the gate isn't a separate mechanism from the scan, it's one flag away from being purely informational.
Why use Jenkins here when this project already uses GitHub Actions-style workflows conceptually?
This project doesn't actually use GitHub Actions — it uses `gh` CLI for PRs/issues, which is unrelated. Jenkins is deliberately included as its own phase because it's still extremely common in real enterprise environments, especially ones that predate cloud-native CI, and is a genuinely different skill (self-hosted server, Groovy-flavored Jenkinsfile syntax, plugin ecosystem) worth having independent of GitHub-native tooling.
