Raw Sockets & WireGuard Phase 13

Written from zero — assumes no prior raw-socket or VPN-tunneling experience. For when each piece was introduced, see the Steps page → Phase 13.

Status: written ahead of the build
Phase 13 (raw sockets + WireGuard) is starting now, extending Phase 6's Go service rather than creating a new one. Everything on this page reflects the planned implementation — read it now to get familiar with the tools before writing code, then it gets corrected/confirmed once each step is really built and tested.

Why this phase exists, what it does, where it fits

QuestionAnswer
Why does this project need this at all?Phase 6's REST endpoint assumes every device can make a normal HTTP request — real field-deployed tracking hardware often can't afford that overhead, or needs a transport suited to how often/reliably it can actually reach the network. This phase adds the lower-level transports real tracking devices actually use.
What does it actually do?Adds two new raw socket listeners to the existing shipment-ingestion Go service — UDP for frequent, lightweight, fire-and-forget pings, and TCP as a higher-reliability fallback when a device needs guaranteed delivery. Both travel through a WireGuard-encrypted tunnel instead of the open network.
Where does it sit in the system?Inside the same Go service Phase 6 already built — new listeners, same validation/persistence/Kafka-publish logic. Not a new box in the architecture diagram.
When would you reach for this pattern in a real job?Any IoT/telemetry system with real devices in the field — cheap, unreliable connectivity, battery/bandwidth constraints, and a real security requirement (raw UDP/TCP have zero built-in encryption on their own).

The story, in plain terms

Phase 6 built one door into this service: a REST endpoint, which assumes a full HTTP request/response and a device with enough network stack to speak it comfortably. Real tracking hardware in the field is often cheaper and more constrained than that — it wants to send a tiny burst of bytes as fast and as cheaply as possible, without the overhead of an HTTP request every time.

REST (Phase 6, done): Device → full HTTP request (headers, method, path, JSON body) → :8090/ingest Reliable, but relatively heavy per message. Raw UDP (Phase 13 — the normal case): Device → a few dozen raw bytes, no handshake, no guarantee of arrival → :8091 Cheap and fast. Fine for frequent pings where losing one occasionally is fine. Raw TCP (Phase 13 — the fallback): Device → same data, but TCP's built-in handshake + retransmission guarantees delivery → :8092 Used when a device needs to be sure a specific ping actually arrived — e.g. catching up after being offline, or repeated missed UDP acks. WireGuard (Phase 13 — wraps both): Neither raw UDP nor raw TCP has any encryption of its own. WireGuard creates an encrypted tunnel between device and service first; the raw UDP/TCP traffic travels inside that tunnel, invisible and unreadable to anything sitting on the network between them.

What each piece is, in one line

TermPlain-language meaning
SocketAn operating-system handle representing one end of a network connection — everything (HTTP, UDP, TCP) is ultimately built on sockets; "raw sockets" here just means talking UDP/TCP directly, with no HTTP layer on top.
UDPUser Datagram Protocol — connectionless, no handshake, no delivery guarantee, no ordering guarantee. Send a packet and move on; the OS doesn't tell you if it arrived.
TCPTransmission Control Protocol — connection-oriented, guarantees delivery and ordering via handshakes and retransmission. More overhead than UDP, but reliable.
WireGuardA modern VPN protocol — creates an encrypted point-to-point tunnel between two endpoints using public-key cryptography. Simpler and faster than older VPN protocols (IPsec, OpenVPN), widely used for exactly this kind of device-to-server tunnel.
FailoverAutomatically switching to a backup transport when the primary one isn't working — here, a device falling back from UDP to TCP after enough pings go unacknowledged.

UDP vs. TCP — the real comparison

UDP (primary transport, this phase)TCP (fallback transport, this phase)
ConnectionNone — just send a datagramHandshake required before any data flows (3-way handshake)
Delivery guaranteeNone — a packet can be silently droppedGuaranteed — the OS retransmits until it's acknowledged
OrderingNot guaranteed — packets can arrive out of orderGuaranteed — arrives in the order it was sent
Overhead per messageMinimal — a small header, no handshakeHigher — handshake, acknowledgments, retransmission bookkeeping
Why it's the primary transport hereFrequent location pings can tolerate occasionally losing one — the next ping a few seconds later makes up for it. Paying TCP's overhead on every single ping isn't worth it for that traffic shape.

Raw listeners in Go — planned code

// UDP — connectionless, read one datagram at a time
conn, err := net.ListenUDP("udp", &net.UDPAddr{Port: 8091})
buf := make([]byte, 1024)
for {
    n, addr, err := conn.ReadFromUDP(buf)
    go handlePing(buf[:n])           // same shared handler REST/TCP use
    conn.WriteToUDP([]byte("ACK"), addr)  // UDP has no built-in delivery confirmation —
                                           // this ack is what lets a client detect a drop
}
// TCP — connection-oriented, one goroutine per accepted connection
listener, err := net.Listen("tcp", ":8092")
for {
    conn, err := listener.Accept()
    go func(c net.Conn) {
        defer c.Close()
        data, err := io.ReadAll(c)
        handlePing(data)              // same shared handler
    }(conn)
}

handlePing(...) is the same validate → persist to Postgres → publish to Kafka logic Phase 6 and Phase 10 already built for the REST handler — refactored into one shared function so all three transports (REST, UDP, TCP) feed the identical pipeline instead of three separate, drifting copies of it.

The failover pattern — client-driven, not server-driven

Device sends ping via UDP :8091 │ ├─ ACK received within timeout ─► done, ping delivered │ ▼ no ACK after N attempts (UDP is silently unreliable — could be a dropped packet, a dropped ack, or the link genuinely being down; the device can't tell which, and doesn't need to) Device falls back to TCP :8092 for this ping │ ▼ TCP's own handshake either succeeds or fails outright Delivery confirmed by TCP itself — no separate ack scheme needed on top of it

The decision to fail over lives entirely on the client side — the Go service doesn't orchestrate anything, it just exposes both listeners and lets whichever one gets used, get used. This mirrors how failover actually works in real IoT firmware: the constrained device is the one that has to reason about link quality, not the server.

WireGuard — what actually happens at the network layer

ConceptWhat it is
Key pairEach peer (device, service) has a private/public key pair — WireGuard uses these for both authentication and encryption, no separate certificate infrastructure needed
Peer configEach side lists the other's public key and allowed IP range — WireGuard only accepts traffic from a peer whose key it already trusts
Tunnel interface (wg0)A virtual network interface WireGuard creates — traffic sent to it gets encrypted and wrapped before leaving the real network interface
Why raw UDP/TCP need thisNeither protocol has any encryption of its own — anything sniffing the network between device and service could read a raw ping in plain text without a tunnel wrapping it first

Interview Q&A

Why is UDP the primary transport here instead of TCP, if TCP is more reliable?
Reliability isn't free — TCP's handshake and retransmission bookkeeping cost overhead on every single message. For frequent, low-stakes location pings, occasionally losing one is a non-issue (the next ping a few seconds later supersedes it), so paying TCP's overhead on every message isn't worth it. TCP is kept as a fallback specifically for the cases where losing a message actually matters — the right tool matched to the traffic's actual reliability requirement, not "TCP is always safer."
Why does this need WireGuard specifically, instead of just trusting the network?
Raw UDP and TCP sockets have zero encryption built in — anyone positioned on the network path between a device and this service could read a ping in plain text, or worse, forge one. WireGuard wraps that raw traffic in an encrypted, authenticated tunnel first, so what travels the actual network is opaque and provably from a trusted peer, regardless of what the inner UDP/TCP payload looks like.
Why refactor the ping-processing logic into a shared handler instead of writing it three times?
REST, UDP, and TCP are just three different ways bytes arrive at the service — once parsed, the actual work (validate, persist to Postgres, publish to Kafka) is identical regardless of transport. Writing it three times means three places that can silently drift out of sync as the logic evolves; one shared function called from three thin transport-specific handlers guarantees all three transports behave identically.
