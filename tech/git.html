Git & GitHub

Fundamentals first, grows every time the build introduces a new command. Local git first, GitHub (remote) second. For the actual order things were run in, see the Steps page — this page is organized by concept, not by when it happened.

What each one is, in one line

TermWhat it is
GitThe version control tool — runs entirely on your machine, tracks every change to every file as a history of snapshots (commits).
GitHubA hosting service for git repositories in the cloud — adds a web UI, pull requests, issues, Actions (CI/CD), and a place for other people (or interviewers) to see your commit history.
Repository (repo)A folder git is tracking — contains your files plus a hidden .git folder with the entire history.
RemoteA repo's copy hosted somewhere else (GitHub). Your local repo can push to it / pull from it. The default remote name is origin.
Best way to remember
Git = the engine (local, offline, works with zero internet). GitHub = a garage that stores a copy of your engine and lets other mechanics look at it. You can use git with no GitHub account at all.

Local basics

git init

  • What it does: turns the current folder into a git repo by creating a hidden .git subfolder. Nothing is tracked yet — this just switches tracking on.
  • When/why: run exactly once, the first time, inside the folder you want tracked.
  • Best practice: run it from an otherwise-empty or newly created project folder, before adding a remote or making a commit.
  • Official docs: git-init

git status

  • What it does: shows what's changed since the last commit — untracked files, modified files, staged files.
  • When/why: run it constantly, before every add/commit, so you know exactly what you're about to commit.
  • Official docs: git-status

git add

  • What it does: moves a file from "changed" into the staging area — the draft list of what the next commit will contain.
  • Flags:
    • git add <file> — stage one specific file (safest, most deliberate).
    • git add . — stage everything changed in and below the current folder.
  • Official docs: git-add
Gotcha
git add . stages everything that isn't excluded by .gitignore — always run git status right after, and read the file list, before committing. This is exactly how secrets/env files leak into public repos.

.gitignore

  • What it is: a plain-text file, one pattern per line, listing what git should never track even if it exists in the folder — build output, dependency folders, secrets, IDE settings.
  • When/why: create it before your first git add, so generated files never get a chance to be staged in the first place.
  • Official docs: gitignore
Real mistake made in this project
Created the file as gitignore (no leading dot) instead of .gitignore — git silently treated it as just another tracked text file instead of an ignore rule, so nothing was actually being excluded. git ls-files is what caught it (it showed gitignore sitting right there as a tracked file, which it should never be). Fixed with Rename-Item .\gitignore .gitignore.

git commit

  • What it does: takes everything currently staged and saves it as a permanent, named snapshot in the repo's history.
  • Flags: -m "message" — write the commit message inline instead of opening an editor.
  • Best practice: short, lowercase, human-sounding messages describing what changed — not a formal changelog sentence. add gitignore + readme, not Initialize project repository structure.
  • Official docs: git-commit

Remote basics (GitHub)

gh repo create

  • What it does: GitHub's official CLI tool (gh) creates a new repo on GitHub.com directly from your terminal — no browser needed.
  • Flags used here: --public (visible to anyone, resume-linkable), --source=. (use the current local folder as the repo content), --remote=origin (name the connection origin).
  • Official docs: gh repo create
What actually happened in this project
gh wasn't installed yet the first time this ran, so the GitHub repo was created through the github.com web UI instead ("New repository" button), then linked locally by hand: git remote add origin git@github.com:theHparth/MoveTrack_Ops.git. Both routes end at the same place — gh repo create --source=. --remote=origin just does the "create on GitHub" + "add the remote" steps in one command once gh is set up. gh got installed later (see the CLI install section further down) for issues/PRs going forward.

git remote -v

  • What it does: lists every remote this repo knows about and its URL — confirms origin points where you expect before you push anything.
  • Official docs: git-remote

git push

  • What it does: uploads your local commits to the remote repo.
  • Flags: -u origin main — push to origin's main branch and remember that pairing, so future pushes just need git push.
  • Official docs: git-push
Real error hit: "src refspec main does not match any"
Means git can't find a local branch named main to push. Two different causes can produce this exact message — worth knowing both: (1) no commit exists yet at all, so no branch ref exists period, or (2) a commit exists, but the local branch is still named master (git's old default) while the push targets main. This project hit case (2) — fixed with git branch -M main, which renames the current branch in place.
working directory --git add--> staging area --git commit--> local repo (.git) --git push--> GitHub (origin) (your files) (the draft) (permanent history) (public copy)

Branching & Pull Request Workflow — GitHub Flow

Starting Step 1, every change goes through a branch and a PR — nothing gets committed straight to main again. This is GitHub Flow, the trunk-based workflow most companies actually use day to day (as opposed to heavier models like Git Flow with separate develop/release branches, which mainly show up on projects that ship versioned releases, not continuously-deployed apps).

main ──●───────────────────────────────●───────────────────────●──▶ \ / (squash-merge) \ ●──●──● feat/step1-... ● ●──● feat/step2-... (next branch, off latest main) (issue #1 opened) (PR #1 reviewed + merged, branch deleted, issue auto-closed)
Why one branch per Step by default
Keeps a 1:1 line between the roadmap in the deep spec, the GitHub issue, the branch, the PR, and the entry on the Steps page — anyone (including you, months later) can trace a feature from spec → code → history in one hop. Split a Step into multiple branches only when it genuinely bundles more than one independently-deployable piece (e.g. two separate services) — smaller isn't automatically better; a branch should be one reviewable, coherent unit of work.

Branch naming

PatternExampleUsed for

Real, widely-used convention — a prefix that says what kind of change, then the same short/lowercase/human style already agreed on. Still your call per-commit; this just adds one prefix word.

Squash-merge vs. merge commit

Why squash-merge here
Squash-merge collapses every commit on the branch into one commit on main when the PR merges — your branch can have messy "wip", "fix typo", "actually fix it" commits, and main still gets exactly one clean, readable line per feature. A regular merge commit keeps every individual commit (useful for release-train workflows with multiple teams), which is more history than a solo project needs — squash is GitHub's own recommended default for this shape of project.

Branch protection on main

  • What it does: a repo setting that blocks direct pushes to main — every change must come in through a reviewed PR, even for the repo owner.
  • Why it matters even solo: it's the same guardrail a real team relies on — it makes the PR workflow mandatory instead of optional, so it can't quietly slip back to direct-to-main commits under deadline pressure.
  • Official docs: branch rulesets

Exact click path (Rulesets — GitHub's current recommended way)

  1. Go to github.com/theHparth/MoveTrack_Ops
  2. Top of the repo page → Settings tab
  3. Left sidebar → Rules → Rulesets
  4. New ruleset → New branch ruleset
  5. Ruleset name: main-protection
  6. Enforcement status: Active
  7. Target branches → Add target → Include default branch (this targets main without hardcoding the name)
  8. Under Branch rules, check:
    • ☑ Require a pull request before merging — required approvals can stay at 0, since you're the only reviewer; the checkbox itself is what blocks direct pushes
    • ☑ Block force pushes — usually on by default, leave it on
  9. Leave Bypass list empty — see the gotcha box below for why that matters
  10. Create
Gotcha — bypass list
Repo admins can be granted a bypass on their own rules. If you leave the Bypass list empty when creating the ruleset, it applies to you too — direct pushes to main get rejected even from the owner account, which is what actually makes the PR workflow mandatory instead of a suggestion. Adding yourself to the bypass list defeats the point of turning this on.

GitHub CLI (gh) — install & auth

  • What it is: GitHub's official CLI — creates issues, PRs, and does reviews/merges from the terminal instead of clicking through github.com.
# install (Windows, via winget)
winget install --id GitHub.cli -e

# authenticate once — pick GitHub.com, HTTPS, login with a web browser
gh auth login

Official docs: gh CLI manual

Gotcha — stale PATH after install
A fresh winget install updates the system/user PATH variable, but an already-open PowerShell window doesn't reload it automatically — gh still errors as "not recognized" right after installing. Either open a new terminal window, or refresh the current one without restarting: $env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + [System.Environment]::GetEnvironmentVariable("Path","User").

Auth choices used: GitHub.com → HTTPS → "Authenticate Git with your GitHub credentials?" Yes → "Login with a web browser" (device-code flow: a one-time code, pasted at github.com/login/device, approved in the browser).

Pull Requests

A Pull Request (PR) is a request to merge one branch into another, with a review step in between. Since branch protection is on, this is the only way code reaches main now — direct pushes are blocked, even for the repo owner.

gh pr create

FlagWhat it means
--titleThe PR's headline — what shows in the list of PRs on GitHub
--body "Closes #N"Closes #N is a keyword GitHub recognizes — the referenced issue auto-closes the moment this PR merges, no manual step
--base mainWhich branch to merge into. Usually inferred correctly anyway since main is the default branch — explicit here for clarity

Official docs: gh pr create

issue #N (the ticket) | v feat/some-branch (your branch, all the commits) | | gh pr create v Pull Request <-- read the diff here on github.com, catches things a terminal diff misses | | gh pr merge --squash --delete-branch v main (one clean commit added, branch deleted, issue #N auto-closed)
Why "review your own diff" isn't just ceremony
The PR page shows the whole change as one reviewable block, file by file, with syntax highlighting — a different vantage point than scrolling through terminal output while writing it. This is where an accidentally-included file, a stray debug line, or a formatting mistake tends to actually get noticed.

Why delete the branch after merging

  • The branch is temporary scaffolding, not the record. The PR itself is never deleted — every commit, the full diff, any comments, stay permanently viewable at the PR's URL, even after merge (github.com → repo → Pull Requests → Closed tab).
  • The squashed commit lives forever in main's git log regardless.
  • Deleting on merge keeps the active-branch list meaning exactly one thing — work still in progress. Left undeleted, a long-running project accumulates dozens of stale branch names with no way to tell "still working on this" from "finished weeks ago" at a glance. GitHub's own default repo setting is to auto-delete merged branches, for this exact reason.
  • To see what a finished branch actually did later: go to its closed PR, not the branch.

Per-Step workflow — the template used from Step 1 onward

# 1. open an issue for the step (plain description, no "Step N"/"Phase N" labels — see the gotcha above)
gh issue create --title "<plain description of the work>" --body "<1-2 sentence plain summary>"

# 2. branch off the latest main
git checkout main
git pull
git checkout -b feat/<short-desc>

# 3. work, committing in small, prefixed, human commits as you go
git add <files>
git commit -m "feat: <short description>"
# ...repeat as needed...

# 4. push the branch and open the PR, linking the issue
git push -u origin feat/<short-desc>
gh pr create --title "<plain description of the work>" --body "Closes #<issue-number>" --base main

# 5. review your own diff on github.com (real practice even solo), then merge + clean up
gh pr merge --squash --delete-branch

# 6. sync local main with the squashed merge before starting the next branch
git checkout main
git pull

Interview Q&A

What's the difference between staged and committed?
Staged means the file is in the draft area (git add ran), waiting to be included in the next snapshot. Committed means that snapshot was actually saved to history (git commit ran). You can stage and unstage freely without touching history.
Why write .gitignore before the first commit instead of after?
Once a file is committed, adding it to .gitignore later doesn't remove it from history — it only stops future changes from being tracked. Getting it right before the first git add avoids ever having to scrub a secret or a build folder out of history.
Why feature branches + PRs instead of committing straight to main, especially solo?
Two reasons that hold even with one developer: it forces a self-review step — reading your own diff on GitHub's PR view catches things a local git diff in a terminal doesn't — and it keeps main always in a known-good, deployable state, since work-in-progress never lands there directly. On a real team it also adds actual code review and CI gating before merge.
Doesn't deleting the branch after merge lose the record of what work was done?
No — the branch is just a temporary pointer, not the record. The Pull Request itself is never deleted; every commit, the full diff, and any comments stay permanently viewable at its URL even after merge, and the squashed commit lives forever in main's history regardless. Deleting the branch only removes clutter from the active-branch list — to see what a finished piece of work actually did, you'd look at its closed PR, not a branch name.
Squash-merge vs. a regular merge commit — when would you pick each?
Squash-merge when you want main's history to read as one commit per feature — easy to scan, easy to revert a whole feature in one command. A regular merge commit when you need every intermediate commit preserved — e.g. a long-lived release branch, or a team convention that ties commits to individual review comments. For a single-developer project shipping continuously, squash is the simpler, cleaner default.
