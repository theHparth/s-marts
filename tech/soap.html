Why this phase exists, what it does, where it fits

QuestionAnswer
Why does this project need this at all?Real government/military IT environments are full of decades-old systems that only speak SOAP/XML, not REST/JSON — a legacy scheduling system needing to submit a move request is exactly this scenario. This phase demonstrates translating between the two at a system boundary, a real, common integration pattern.
What does it actually do?Exposes a SOAP endpoint that accepts XML requests shaped like a legacy system would send, translates each one into a real REST call against Move & Entitlement's existing API, and translates the JSON response back into SOAP/XML.
Where does it sit in the system?In front of Move & Entitlement — nothing about that service changes at all. The adapter is a pure translation layer, calling the exact same REST API the React dashboard already calls.
When would you reach for this pattern in a real job?Whenever a legacy system can't be changed (too risky, too old, someone else owns it) but still needs to talk to a modern system — build a thin adapter instead of touching either side.

The story, in plain terms

Every API this project has built so far speaks the same language: JSON over HTTP, a REST-shaped URL for each action. SOAP is an older, different way of doing the same basic job — call a remote operation, get a result back — but everything is wrapped in XML, and the exact shape of every request and response is defined upfront in a formal contract, not discovered by reading code.

REST (everything built so far in this project): POST /api/move-requests Body: { "serviceMemberName": "...", "rank": "E5", ... } (JSON) No upfront contract file required — the DTO classes ARE the contract. SOAP (this phase): POST /ws (one single URL for everything) Body: <soap:Envelope><soap:Body><SubmitMoveRequest>...</SubmitMoveRequest></soap:Body></soap:Envelope> A WSDL file, generated from an XSD schema, formally defines every operation and every field's shape BEFORE any client can call it.

What each piece is, in one line

TermPlain-language meaning
SOAPSimple Object Access Protocol — an XML-based messaging format for calling remote operations, wrapped in a standard envelope structure.
XSDXML Schema Definition — a formal, machine-readable contract describing exactly what fields a request/response can contain and what type each one is. Written by hand, first, before any code.
WSDLWeb Services Description Language — describes an entire SOAP service: what operations exist, what each one's request/response looks like (built from the XSD), and where to send requests. Auto-generated from the XSD in this project, not hand-written.
Spring-WSSpring's library for building SOAP web services — contract-first by design, meaning you write the XSD first and Spring generates the Java classes from it (the opposite order from a typical REST controller, where you write Java first).
@Endpoint / @PayloadRootSpring-WS's equivalent of @RestController/@PostMapping — marks a class as handling SOAP requests, and routes a specific XML element name to a specific method.

SOAP vs. REST — the real comparison

REST (this project's other Java services)SOAP (this phase)
Data formatJSONXML, wrapped in a standard "envelope"
ContractInformal — DTOs and documentation, no single required contract fileFormal — a WSDL/XSD must exist before a client can be built against it, generated first, code second

Contract-first development — the XSD comes first

<xs:element name="submitMoveRequest">
  <xs:complexType>
    <xs:sequence>
      <xs:element name="serviceMemberName" type="xs:string"/>
      <xs:element name="rank" type="xs:string"/>
      <xs:element name="originBase" type="xs:string"/>
      <xs:element name="destinationBase" type="xs:string"/>
      <xs:element name="moveDate" type="xs:date"/>
    </xs:sequence>
  </xs:complexType>
</xs:element>

The org.jvnet.jaxb:jaxb-maven-plugin reads this file at build time and auto-generates matching Java classes — the exact opposite direction from every REST DTO built so far in this project, where the Java class comes first and nothing formally verifies a client matches it ahead of time. With no explicit output package configured, the plugin derives one from the XSD's targetNamespace (http://movetrack.com/soap/moverequest) automatically — it landed on com.movetrack.soap.moverequest, producing SubmitMoveRequest.java and SubmitMoveRequestResponse.java, confirmed by actually inspecting target/generated-sources/xjc rather than guessing the package name ahead of time.

Real mistake — a malformed plugin config, twice
Configuring this plugin's <execution> block needs a nested <goals><goal>generate</goal></goals> — an orphan closing </goals> tag with no matching opening tag (missing the whole <goals><goal>generate</goal> line above it) produced Non-parseable POM ... end tag name </goals> must match start tag name <execution> from Maven. A separate, earlier version of this same file also broke from a literal ... placeholder character sequence landing in the XML by mistake. Both are the same root lesson: a Maven POM is strict, well-formed XML — any incomplete tag pair fails the entire build before a single class compiles, not just the plugin using it.
Not a real error — editor "package does not match" warning
A freshly-added Java file under src/main/java/com/movetrackops/soapadapter/config/ can show The declared package "..." does not match the expected package "main.java...." in an editor's Java language server, even though the file sits in exactly the right place on disk. This means the editor hasn't recognized the new Maven module's src/main/java source root yet — a project reload/reindex fixes it. mvn compile reads the source root from pom.xml directly and was never affected by this at all — confirmed by comparing the physical file path against what the error message implied before assuming anything was actually misplaced.

A SOAP endpoint, translating to REST — the real, working code

@Endpoint
public class MoveRequestEndpoint {

    private static final String NAMESPACE_URI = "http://movetrack.com/soap/moverequest";
    private static final String MOVE_ENTITLEMENT_URL = "http://move-entitlement-service:8082/api/move-requests";

    private final RestTemplate restTemplate;

    public MoveRequestEndpoint(RestTemplate restTemplate) {
        this.restTemplate = restTemplate;
    }

    @PayloadRoot(namespace = NAMESPACE_URI, localPart = "submitMoveRequest")
    @ResponsePayload
    public SubmitMoveRequestResponse submitMoveRequest(@RequestPayload SubmitMoveRequest request) {
        Map<String, Object> dto = toRestDto(request);

        Map<String, Object> restResponse = restTemplate.postForObject(MOVE_ENTITLEMENT_URL, dto, Map.class);

        return toSoapResponse(restResponse);
    }

    private Map<String, Object> toRestDto(SubmitMoveRequest request) {
        Map<String, Object> dto = new HashMap<>();
        dto.put("serviceMemberName", request.getServiceMemberName());
        dto.put("rank", request.getRank());
        dto.put("originBase", request.getOriginBase());
        dto.put("destinationBase", request.getDestinationBase());
        dto.put("moveDate", request.getMoveDate().toXMLFormat());
        return dto;
    }

    private SubmitMoveRequestResponse toSoapResponse(Map<String, Object> restResponse) {
        SubmitMoveRequestResponse response = new SubmitMoveRequestResponse();
        response.setId(Long.parseLong(restResponse.get("id").toString()));
        response.setEntitlementLbs(Integer.parseInt(restResponse.get("entitlementLbs").toString()));
        return response;
    }
}
PieceWhat it does
@PayloadRootRoutes any SOAP request whose XML body's root element matches this namespace+name to this specific method — same routing idea as @PostMapping, different match criteria (an XML element name instead of a URL path). localPart matches the XSD element name exactly (submitMoveRequest, not submitMoveRequestRequest — the generated class name and the payload-root name aren't required to match each other)
@RequestPayload/@ResponsePayloadMarks which parameter is the parsed incoming XML, and that the return value becomes the outgoing XML — Spring-WS handles the actual XML parsing/generation
RestTemplateSpring's classic HTTP client — calls Move & Entitlement's real REST API exactly the same way curl/Invoke-RestMethod would, just from Java code
Raw Map<String, Object> instead of a shared DTO classDeliberate — the adapter shouldn't need a compile-time dependency on Move & Entitlement's internal DTO classes. If a field name ever drifts between the two services, this is the one place that breaks, which is the point of keeping them decoupled
Real mistake — assumed moveDate would generate as a normal date type
JAXB generates xs:date XSD fields as javax.xml.datatype.XMLGregorianCalendar, not java.time.LocalDate or String — confirmed by actually reading the generated SubmitMoveRequest.java rather than assuming. Calling .toString() on it doesn't reliably produce a clean ISO date string; .toXMLFormat() is the correct method for that.
Two build prerequisites the original step plan missed
A working, runnable Spring Boot module needs a @SpringBootApplication main class and an application.properties (for server.port=8083) — neither was part of the original Steps 91-98 plan, since earlier phases' step-by-step docs assumed they'd already exist from an initial scaffold. Caught before it became a runtime failure, not after. Same category of gap as the missing Maven wrapper (mvnw/.mvn/) needed for this module's Dockerfile — copied directly from move-entitlement-service to guarantee the exact same Maven version, rather than regenerating one that might drift.
Real mistake — missing test dependency for MockWebServiceClient
MockWebServiceClient (used for the Step 96 integration test below) lives in org.springframework.ws:spring-ws-test, a separate artifact from the spring-boot-starter-web-services dependency already in the project — not pulled in automatically. Added as a test-scope dependency once the integration test needed it.
Framework-version detail — @MockitoBean, not @MockBean
This project's Spring Boot version (4.1.0) uses @MockitoBean from org.springframework.test.context.bean.override.mockito for mocking a bean inside a @SpringBootTest/@WebMvcTest context — the older @MockBean annotation from earlier Spring Boot versions doesn't apply here. Confirmed by reading MoveRequestControllerTest.java in move-entitlement-service for the pattern this project already uses, rather than assuming the older name still applied.

Verifying the real round trip, end to end

Confirmed with a real SOAP request against the fully containerized service, cross-checked directly against Postgres, not just "the endpoint returned 200":

PowerShell: send a real SOAP envelope ▼ http://localhost:8083/ws (soap-legacy-adapter, inside Docker) ▼ translated to a real REST POST → move-entitlement-service:8082 ▼ PostgreSQL: real row inserted — id=19, service_member_name='Jane Doe', rank='E5' ▼ translated back to SOAP → response received in PowerShell: <id>19</id> <entitlementLbs>7000</entitlementLbs> ▼ Cross-checked independently via: docker compose exec postgres psql -U movetrack -d move_entitlement_db -c "SELECT id, service_member_name, rank FROM move_requests ORDER BY id DESC LIMIT 1;" → same id=19, same Jane Doe / E5 — proves the SOAP response wasn't just echoing input, it reflects a real database write
Not a real error — PowerShell hides the response by default
Invoke-RestMethod auto-parses an XML response body into an object; printing that object directly just shows the root element's tag name (Envelope) instead of the nested content — easy to mistake for an empty or broken response. Assigning the result to a variable and reading $response.OuterXml shows the full raw XML, including the actual <id> and <entitlementLbs> values.

Why this phase is standalone

Unlike every other phase in this project, nothing else in the system calls this adapter — the React dashboard, the other services, the Kafka/RabbitMQ event flows never send it a request. Move & Entitlement's REST API already fully serves every real user flow on its own; the adapter doesn't unlock any new user-facing capability.

That's intentional, not a gap. The value here is the demonstration itself — proof of a real, working protocol-translation adapter in front of an existing REST service, answering a specific, common enterprise/government integration requirement (see Why this phase exists above) — not a piece the rest of MoveTrack Ops' request flow depends on.

Interview Q&A

What does "contract-first" mean, and why does Spring-WS use that order instead of code-first?
Contract-first means the formal shape of a service (its XSD/WSDL) is written before any Java code exists, and the code gets generated from that contract — not the other way around. This matters for SOAP specifically because SOAP clients are often generated automatically from a WSDL by completely separate teams/systems; if the contract could silently drift from whatever the code happens to do, every client generated against an older WSDL version would break. Code-first (like this project's REST APIs) is fine when the API and its one client evolve together — SOAP's traditional use case (loosely coupled legacy systems) specifically assumes they don't.
Is SOAP actually still relevant, or is this just historical trivia?
Still genuinely relevant at real system boundaries — government, banking, insurance, and healthcare systems built 15-20+ years ago standardized on SOAP and are often too risky or expensive to replace outright. A real job in an enterprise environment can absolutely involve building an adapter like this one, translating between an old SOAP-only system and a modern REST-based one, exactly the scenario this phase demonstrates.
Why build a translation adapter instead of just adding SOAP support directly to Move & Entitlement?
Keeps the two concerns fully separate — Move & Entitlement stays a clean REST service with no idea SOAP clients exist at all, and the adapter is the only place that has to know about XML envelopes and WSDLs. If the legacy system is ever retired, the adapter is deleted with zero risk to the real service; if Move & Entitlement's REST API changes, only the adapter's translation logic needs updating, not two different endpoint implementations living in the same service.
Why does a JAXB-generated xs:date field come back as XMLGregorianCalendar instead of LocalDate?
JAXB predates java.time (introduced in Java 8) and has never been updated to generate against it by default — XMLGregorianCalendar is the original, XML-Schema-aligned date/time type it's always used. Converting it cleanly needs .toXMLFormat(), not .toString(), to get a reliable ISO-8601 string. Worth checking the actually-generated code under target/generated-sources before writing translation logic against it, rather than assuming a modern type.
The SOAP endpoint returned an HTTP 200 with a response body — how do you know it actually worked end to end?
A 200 with a response only proves the adapter itself didn't crash — it doesn't prove the REST call underneath it actually reached Move & Entitlement, or that anything was really persisted. Real proof here was cross-checking the SOAP response's id value directly against Postgres (SELECT ... FROM move_requests ORDER BY id DESC LIMIT 1) and confirming it matched — the same "verify against the actual data store, not just the HTTP status" instinct used to confirm Phase 4's RabbitMQ events and Phase 10's Kafka offsets.
