RabbitMQ & MongoDB Phase 4

Fundamentals + how this project actually uses it. For when each piece was introduced, see the Steps page → Phase 4.

Confirmed — built and verified through Step 74
Phase 4 (RabbitMQ + Compliance/Findings Service) is complete. Compliance Service runs as a 10th container, real Trivy output flows in automatically from Jenkins, both Java services publish domain events, verified with a full green Jenkins build against main after merge. This phase hit more real gotchas than any other so far — every one is documented inline below and on Java, Spring & Maven / Python, FastAPI & scikit-learn.

Why this phase exists — the plain version

Phase 5 (done): Jenkins runs Trivy/ZAP → findings archived as a build artifact (a report sitting in a file, nobody reading it automatically) Phase 4 (this): Jenkins POSTs that same report → Compliance Service → stored + queryable → an alert event fires if it's bad

Two new pieces of infrastructure make that possible: MongoDB (where findings actually live) and RabbitMQ (how "a bad finding just got stored" gets announced to the rest of the system, without the Compliance Service needing to know who's listening).

RabbitMQ core concepts

Producer Exchange Queue Consumer │ │ │ │ │── publish(routing_key) ─►│── routes by key/rules ──►│── holds messages ─►│── consume() until read A producer never sends directly to a queue — it sends to an EXCHANGE, which decides (by routing key) which queue(s) actually get the message.
ConceptWhat it is
ProducerAnything that sends a message — Move & Entitlement, Claims, and Compliance are all producers in this phase
ExchangeReceives messages from producers and routes them to queue(s) based on rules — never stores anything itself
QueueWhere messages actually sit until a consumer reads them
BindingThe rule connecting an exchange to a queue — "route messages matching X to this queue"
ConsumerAnything that reads messages off a queue
Exchange typeRouting behavior
DirectExact routing-key match — e.g. only finding.detected messages go to a specific queue
TopicPattern match on the routing key (finding.*) — this project's likely choice, since move.created/claim.filed/finding.detected all share a dot-separated naming pattern
FanoutBroadcasts to every bound queue, ignoring the routing key entirely

Publishing from Python (pika)

import pika
import json

connection = pika.BlockingConnection(pika.ConnectionParameters(host="rabbitmq"))
channel = connection.channel()
channel.exchange_declare(exchange="movetrack_events", exchange_type="topic")

channel.basic_publish(
    exchange="movetrack_events",
    routing_key="finding.detected",
    body=json.dumps({"finding_id": "abc123", "severity": "HIGH"}),
)
connection.close()

Publishing from Java (Spring AMQP)

@Autowired
private RabbitTemplate rabbitTemplate;

public void publishMoveCreated(Move move) {
    rabbitTemplate.convertAndSend("movetrack_events", "move.created", move);
}

Same underlying concept as the Python version — an exchange name, a routing key, a message body — just Spring's higher-level RabbitTemplate wrapping the same AMQP protocol calls.

RabbitMQ vs. Kafka — a real comparison, since Kafka is coming in Phase 10
RabbitMQ (this phase)Kafka (Phase 10, not built yet)
ModelTraditional message queue — a message is typically removed once consumedDurable, replayable log — messages persist and can be re-read
Best fitBusiness/domain events needing routing logic (this phase's move.created, claim.filed, finding.detected)High-volume, ordered streams (Phase 10's shipment tracking telemetry)
ThroughputLower, but simpler routing modelMuch higher — built for firehose-scale data
Worth stating this contrast directly in an interview: this project deliberately uses both, for genuinely different traffic shapes — not "RabbitMQ because it's older" or "Kafka because it's trendier."

Why MongoDB for scan findings specifically, not another Postgres table
A Trivy finding and a ZAP finding look nothing alike — different fields, different nesting, different shapes entirely. Forcing both into fixed relational columns means either a huge sparse table (mostly NULL columns) or constant schema migrations as new scanner types get added later. A document store accepts whatever shape a finding actually has, no migration required.

How a real request actually flows — Move & Entitlement example

The concepts above are abstract until you trace one real click through the system. This is exactly what happens when a user submits the Move Requests form on the dashboard (Step 69):

Browser (localhost:3000) │ 1. Click Submit → fetch POST http://localhost:8082/api/move-requests ▼ move-entitlement-service : 8082 (Java/Spring, MoveRequestController) │ 2. calls EntitlementCalculationService.submitMoveRequest() ▼ PostgreSQL : 5432 (move_entitlement_db) │ 3. INSERT INTO move_requests — saved permanently ▼ RabbitMQ : 5672 (AMQP — the real data path) │ 4. rabbitTemplate.convertAndSend("compliance", "move.created", saved) │ message dropped into the "compliance" exchange, fire-and-forget ▼ back in the same Java method │ 5. calculateEntitlement(id) — reads weight_allowances table ▼ MoveRequestController │ 6. builds { entitlementLbs: 7000 } as JSON, HTTP 200 response ▼ Browser — Redux store updates, "Entitlement: 7000 lbs" renders Port 15672 (the RabbitMQ web UI) is NOT part of this path — it's a separate port for humans to look inside the exchange after the fact. The request above never touches 15672 at all.
What this proves, concretely
Steps 1-3 and 5-6 are the same request/response cycle every REST endpoint in this project already does. The only genuinely new thing Phase 4 adds is step 4 — one extra call, made after the database save succeeds, that announces the event without the caller waiting for or caring whether anyone is listening. That's the entire value RabbitMQ adds over a plain REST API: the announcement doesn't block the response, and any number of future listeners can react to it without this controller ever being changed.

Publishing JSON from Java — three stacked Jackson gotchas

Getting RabbitTemplate to publish a plain Java object as JSON (instead of Java's own binary serialization format) took three separate fixes — each one only became visible once the previous one was fixed, since each earlier failure crashed before the code ever reached the next issue.

#SymptomReal causeFix
1IllegalArgumentException: SimpleMessageConverter only supports String, byte[] and SerializableDefault converter can't turn a plain entity into bytes at allUse Jackson2JsonMessageConverter instead of the default
2NoClassDefFoundError: JsonMapper — whole app fails to startThe converter's zero-arg constructor calls a newer Jackson API than what's actually resolved on the classpathConstruct it with an explicit new ObjectMapper() instead of letting it build its own
3InvalidDefinitionException: Java 8 date/time type LocalDate not supportedPlain Jackson has no built-in support for java.time types — that needs a separate module, registered on this specific mappermapper.registerModule(new JavaTimeModule()), plus the jackson-datatype-jsr310 dependency
@Configuration
public class RabbitMQConfig {
    public static final String EXCHANGE = "compliance";

    @Bean
    public TopicExchange complianceExchange() {
        return new TopicExchange(EXCHANGE);
    }

    @Bean
    public Jackson2JsonMessageConverter jsonMessageConverter() {
        ObjectMapper mapper = new ObjectMapper();
        mapper.registerModule(new JavaTimeModule());
        return new Jackson2JsonMessageConverter(mapper);
    }

    @Bean
    public RabbitTemplate rabbitTemplate(ConnectionFactory connectionFactory,
                                          Jackson2JsonMessageConverter jsonMessageConverter) {
        RabbitTemplate template = new RabbitTemplate(connectionFactory);
        template.setMessageConverter(jsonMessageConverter);
        return template;
    }
}
Why JSON instead of Java's own serialization
Java's built-in Serializable format is Java-only and version-fragile — a consumer written in a different language (this project's own Python compliance-service, eventually) couldn't read it at all. JSON is what every language on this project's stack already speaks — the same format pika/requests use on the Python side.
A separate, unrelated compile error along the way
package com.fasterxml.jackson.databind does not exist — despite this exact app already returning JSON successfully elsewhere (via Spring's own auto-configured HTTP JSON handling), jackson-databind was never actually a direct or transitively-reachable compile dependency of this specific module. Fixed by adding it explicitly to pom.xml, version left unpinned so Spring Boot's parent BOM manages it (see Java, Spring & Maven → Reading a dependency vulnerability scan for what happened right after that).

Interview Q&A

Why use both RabbitMQ and Kafka in the same project instead of picking one?
They fit genuinely different traffic shapes. RabbitMQ suits routed business/domain events (a move was created, a claim was filed, a finding was detected) where a traditional queue's routing logic is the point. Kafka suits high-volume, ordered, replayable streams (shipment tracking telemetry) where durability and throughput matter more than per-message routing rules. Using both isn't indecision — it's matching each tool to the traffic it's actually good at.
Why store scan findings in MongoDB instead of a Postgres table?
Trivy and ZAP findings have genuinely different shapes from each other, and that shape can change as new scanners get added. A relational table would need either a wide, mostly-empty schema or constant migrations. A document store accepts whatever shape a finding actually has, with no schema migration required — the right tool for semi-structured, variable-shape data specifically.
What's the difference between an exchange and a queue in RabbitMQ?
A producer never sends directly to a queue — it publishes to an exchange, which routes the message to whichever queue(s) match its routing rules (a "binding"). The queue is just where messages wait until a consumer reads them; the exchange is what decides where a message goes at all. This indirection is what lets a producer stay ignorant of who's actually listening.
