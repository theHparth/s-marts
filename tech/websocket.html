Node.js & WebSockets Phase 9

Written from zero — assumes no prior Node.js or WebSocket experience. For when each piece was introduced, see the Steps page → Phase 9.

Confirmed — built and verified through Step 90
Phase 9 (WebSocket live feed) is complete. A live shipment feed renders on the dashboard with zero page refresh, fully inside Docker — the full chain (Go → Postgres + Kafka → Node consumer → WebSocket → React) verified working end to end. This phase's real gotchas were almost all one shape, in three different disguises — every one documented inline below.

Why this phase exists, what it does, where it fits

QuestionAnswer
Why does this project need this at all?Right now the dashboard only shows data at the moment the page loads — a new shipment ping published to Kafka is invisible until you manually refresh. This phase closes that gap: the browser gets told the instant something new happens.
What does it actually do?A small Node.js service subscribes to Kafka's shipment.tracking topic and, for every message, immediately pushes it out to every browser tab currently connected.
Where does it sit in the system?Between Kafka and the dashboard — a real consumer of the topic Phase 10 built, replacing the throwaway demo consumer with something the actual UI depends on.
When would you reach for a WebSocket instead of polling?When updates are frequent and unpredictable in timing — polling ("ask every 5 seconds, is there anything new?") wastes requests when nothing changed and feels laggy when something did. A WebSocket flips that: the server pushes the instant there's something to say.

The story, in plain terms

Every request you've built so far in this project follows the same shape: the browser asks a question, the server answers, the connection closes. That's HTTP — a REST call, a form submit, all of it. It works great when the browser is the one deciding when to ask.

A live feed is the opposite problem: the server knows something happened (a shipment moved) before the browser has any reason to ask. A WebSocket is a connection that, once opened, stays open — either side can send a message at any time, without a new request/response round trip for every single update.

HTTP (everything built so far in this project): Browser: "any updates?" -> Server: "here's the answer" -> connection closes Repeat that on every page load / manual refresh. Server can never speak first. WebSocket (this phase): Browser: "let's open a channel" -> Server: "OK, channel open" ... connection stays open ... Server: "new ping!" -> Browser (no request needed, arrives instantly) Server: "new ping!" -> Browser Either side can send, any time, without re-asking first.

What each piece is, in one line

TermPlain-language meaning
Node.jsA JavaScript runtime for running JS outside a browser — on a server. Same language your React frontend already uses, now on the backend too.
Event loopNode's core model — one thread, but it never sits idle waiting on I/O (a network read, a file read); it registers a callback and moves on, running that callback only once the result is ready. This is why Node handles many simultaneous slow connections (like open WebSockets) cheaply — the same class of reasoning as Go's goroutines, different mechanism.
WebSocketA protocol for a long-lived, two-way connection between browser and server, upgraded from an initial HTTP request.
wsThe most common, minimal Node.js library implementing the WebSocket protocol — this project's choice, no framework overhead beyond what's needed.
KafkaJSThe Node.js client library for talking to Kafka — this service's version of what kafka-go is for Go and kafka-python is for Python.

Why Node.js specifically, for this one service

Same reasoning shape as Go's Phase 6 justification, different mechanism
This service's whole job is holding open many simultaneous, mostly-idle connections (one per browser tab watching the dashboard) and occasionally pushing a message down each one. Node's single-threaded event loop handles that cheaply for the same underlying reason Go's goroutines did in Phase 6 — neither wastes a full OS thread per idle connection, unlike a traditional thread-per-request server (the Java services' model). Node is the more natural choice here specifically because this is also where the frontend team's skillset already lives — same language, both ends of this one feature.

A minimal WebSocket server

const { WebSocketServer } = require("ws");

const wss = new WebSocketServer({ port: 8095 });
const clients = new Set();

wss.on("connection", (socket) => {
  clients.add(socket);
  socket.on("close", () => clients.delete(socket));
});

function broadcast(message) {
  const payload = JSON.stringify(message);
  for (const client of clients) {
    if (client.readyState === client.OPEN) {
      client.send(payload);
    }
  }
}

module.exports = { broadcast };
PieceWhat it does
clients (a Set)Tracks every currently-open connection — a live feed with nobody to push to isn't useful, so this is how the service knows who's listening
socket.on("close", ...)Removes a disconnected tab from the set — without this, the set would grow forever with dead connections
readyState === client.OPENGuards against sending to a connection that's in the middle of closing — sending to a closed socket throws

Consuming Kafka from Node (KafkaJS)

const { Kafka } = require("kafkajs");
const { broadcast } = require("./wsServer");

const kafka = new Kafka({ clientId: "ws-live-feed", brokers: ["kafka:29092"] });
const consumer = kafka.consumer({ groupId: "ws-live-feed" });

async function start() {
  await consumer.connect();
  await consumer.subscribe({ topic: "shipment.tracking", fromBeginning: false });

  await consumer.run({
    eachMessage: async ({ message }) => {
      const ping = JSON.parse(message.value.toString());
      broadcast(ping);
    },
  });
}

start();

fromBeginning: false is a deliberate, different choice from Phase 10's demo consumer — a live feed only cares about what's happening now, not replaying every historical ping from the start of the topic every time this service restarts.

Real mistake — running the wrong file (twice, in two different disguises)
server.js only starts the WebSocket server — it never requires kafkaConsumer.js, so running node server.js means the Kafka consumer never starts at all. Since kafkaConsumer.js already pulls in server.js via require("./server") and then begins consuming, it's the correct single entry point — node kafkaConsumer.js locally, and (this is the part that repeated the mistake a second time) CMD ["node", "kafkaConsumer.js"] in the Dockerfile too, not CMD ["node", "server.js"]. Neither wrong version throws an error — the WebSocket server runs fine either way, it just has nothing to ever broadcast, which makes this a genuinely quiet failure mode: "nothing happened" with zero error output, rather than a crash pointing at the real cause.

Connecting from React

import { useEffect, useState } from "react";

function useLiveFeed(url: string) {
  const [pings, setPings] = useState([]);

  useEffect(() => {
    const socket = new WebSocket(url);

    socket.onmessage = (event) => {
      const ping = JSON.parse(event.data);
      setPings((prev) => [ping, ...prev].slice(0, 50));
    };

    return () => socket.close();
  }, [url]);

  return pings;
}

The browser's own built-in WebSocket class — no library needed on the frontend side, this is a native web API. .slice(0, 50) caps how much history the UI keeps in memory, since a live feed that never trims would grow unbounded over a long session.

Real mistake — a hook with nothing calling it produces zero errors
useLiveFeed.ts got built and committed, but no page component ever imported or called it, and no route/nav link existed to reach one — so the app ran perfectly, with nothing visibly broken, while genuinely doing nothing on screen. This wasn't caught until testing several steps later. A hook (or any function) nobody calls is indistinguishable from "working but idle" — worth checking directly whether something actually invokes new code, not just whether it compiles cleanly.

The same local-vs-Docker address problem, a third time

Same root cause as Kafka's own dual-listener gotcha (Kafka → Host vs. Docker-network listeners) — this service's kafkaConsumer.js still had localhost:9092 hardcoded from local testing. Once containerized, that produced ECONNREFUSED 127.0.0.1:9092 and crashed the whole Node process (an unhandled Kafka connection error is fatal by default). Fixed by switching to kafka:29092, the same Docker-network listener every other containerized client in this project uses.

The pattern worth internalizing
Any time a service gets built and tested locally first, then containerized later, expect at least one address that needs to flip from localhost to a Docker Compose service name. This is now the third time this exact category of bug has shown up in this project (the Go producer in Phase 10, the Python demo consumer in Phase 10, and this service) — worth checking for on sight whenever "it worked locally, then broke the moment it got containerized" shows up again.

Interview Q&A

Why not just have the dashboard poll a REST endpoint every few seconds instead of using a WebSocket?
Polling means picking a tradeoff you can't win: poll too slowly and updates feel laggy; poll too fast and you're making mostly-wasted requests (nothing changed most of the time) that scale badly with more open dashboard tabs. A WebSocket sidesteps the tradeoff entirely — the server only sends when there's actually something to say, and the connection itself is cheap to hold open.
Node.js is single-threaded — how does it handle many WebSocket connections at once without blocking?
The event loop never blocks waiting on I/O — a slow operation (a network read, in this case waiting on a WebSocket to have data) registers a callback and the loop moves on to other work immediately, running the callback only when the result is actually ready. Many idle connections cost almost nothing while they're idle; the model breaks down for CPU-heavy work, not I/O-heavy work like this.
Why does this service use its own Kafka consumer group instead of reusing Phase 10's demo-consumer group?
Two independent consumer groups reading the same topic don't interfere with each other at all — each group tracks its own separate offset. Reusing the demo group would tie this real, production-facing feature to a throwaway debugging tool; a dedicated group id keeps them fully independent, and either one can be stopped/restarted without affecting the other.
