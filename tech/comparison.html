Cross-Tech Comparison

Every stack this project uses, side by side, answering the same questions each time: what runs it, how dependencies are managed, how the API is built, where data lives, how tests work, and how data actually moves end to end. Each per-technology page (Git, Java/Spring, Docker, React/Redux) is the deep reference; this page is the quick side-by-side for comparing them. A new column gets added here the first time a new stack is introduced — Python/FastAPI (Phase 8) lands once that phase is finished and confirmed.

Stack overview

Question Java / Spring Boot React / Redux / TypeScript
Used for Move & Entitlement Service, Claims Service — the backend REST APIs The Dashboard — the browser-side single-page app
Server / runtime Apache Tomcat, embedded inside the app itself by Spring Boot — no separate server install. Started via mvn spring-boot:run in dev, or java -jar app.jar running the packaged executable JAR in prod/Docker. Vite's dev server (npm run dev) during development, hot-reloading on save. In prod/Docker, npm run build compiles to static files, and Nginx (a separate, general-purpose web server) serves them — React itself never runs a server.
Dependency file pom.xml — declarative XML listing every library and its version. mvn resolves and downloads them into ~/.m2. package.json (+ the auto-generated lockfile package-lock.json for exact versions). npm install resolves and downloads into node_modules/.
API framework Spring Web MVC (spring-boot-starter-webmvc). Routes are Java methods annotated @GetMapping/@PostMapping inside an @RestController class. JSON conversion is automatic, handled by Jackson. Not a server — a client. Calls the Java services' REST APIs using the browser's built-in fetch, wrapped in a small typed request<T> helper, dispatched from Redux Toolkit createAsyncThunk actions.
Database / data store PostgreSQL, accessed through Spring Data JPA/Hibernate — @Entity classes map to tables, JpaRepository interfaces give CRUD methods with no SQL written by hand. None directly. The Redux store holds a client-side, in-memory copy of whatever the REST APIs returned — the actual source of truth is still Postgres, reached indirectly through the Java services.
Testing framework JUnit 5 + Mockito. @Mock/MockitoExtension for plain unit tests, @WebMvcTest + @MockitoBean for controller slice tests, @SpringBootTest for full-context integration tests. Vitest (the Vite-native test runner) + React Testing Library for rendering components in tests and querying them the way a user would (by visible text/role, not internal implementation detail).
Data exchange / import-export flow Client sends JSON → Jackson deserializes it into a @RequestBody DTO → Controller hands it to a Service → Service maps it to/from an @Entity and persists via JPA → Jackson serializes the response DTO back to JSON on the way out. User action → thunk calls fetch → JSON response comes back → a TypeScript interface gives that JSON a compile-time-checked shape → extraReducers writes it into the Redux store → connected components re-render automatically via useSelector.
Why this page exists separately from the per-technology pages
The Git/Java-Spring/Docker/React-Redux pages are deep references for one stack at a time — good for looking something up while working in that stack. This page answers a different question: "how does Java's version of X compare to React's version of X" — the shape interviewers actually ask about, and the shape that's easy to forget once each stack's page is read in isolation.
