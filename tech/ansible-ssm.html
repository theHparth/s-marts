Why this phase exists, what it does, where it fits

QuestionAnswer
Why does this project need this at all?Terraform provisions infrastructure (a VPC exists, an EKS cluster exists, worker nodes exist) — it deliberately doesn't configure what runs inside those worker nodes after they boot. Ansible is the tool for that second job: real configuration management against real running machines.
What does it actually do?Runs a real Ansible playbook against the EKS cluster's worker node EC2 instances — not over SSH, but over AWS Systems Manager, so no bastion host, no open SSH port, and no SSH key to manage or leak.
Where does it sit in the system?After Terraform (Step 5 in this phase) has already created the worker nodes, and alongside SSM Parameter Store (this same phase) holding this project's secrets.
When would you reach for this pattern in a real job?Any time you need to configure real servers after they exist — patching, installing an agent, enforcing a config file — especially in an environment where opening SSH access to every instance is itself considered a security risk worth avoiding.

The story, in plain terms

Terraform and Ansible solve two genuinely different problems, and conflating them is a common early mistake:

Terraform (provisioning): "Does a VPC exist? Does an EKS cluster exist? Do 3 worker node EC2 instances exist?" Answers by creating/destroying whole AWS resources. Declarative — describes the end state. Ansible (configuration management): "Given these 3 EC2 instances already exist, what should be TRUE about what's running inside them?" — install a package, enforce a config file, restart a service. Also declarative in intent, but operates on the inside of machines Terraform already made. Normally: Ansible reaches a machine over SSH. This project: Ansible reaches it over AWS Systems Manager instead — no SSH at all.

Ansible fundamentals

TermPlain-language meaning
AgentlessNo permanent software needs to run on the target machine ahead of time — Ansible connects, runs what it needs, and disconnects. (Contrast with tools like Puppet/Chef, which need a persistent agent installed first.)
InventoryThe list of machines Ansible will manage — can be a static file, or generated dynamically (this project's case: pulled live from AWS, not hand-maintained).
PlaybookA YAML file describing what should be true on a set of hosts — a sequence of tasks, each one usually a single module call.
ModuleA single unit of work Ansible knows how to do — apt/yum (install a package), copy (put a file somewhere), service (start/stop/restart something), and hundreds more.
IdempotencyRunning the same playbook twice produces the same end state, with the second run reporting "nothing changed" rather than re-doing work or erroring — the same core idea as Terraform's plan/apply model, applied to configuration instead of infrastructure.

A minimal real playbook

- name: Confirm and label EKS worker nodes
  hosts: eks_worker_nodes
  tasks:
    - name: Confirm the container runtime is active
      ansible.builtin.service:
        name: containerd
        state: started

    - name: Write a node-identity marker file
      ansible.builtin.copy:
        content: "managed-by: movetrack-ops-ansible\n"
        dest: /etc/movetrack-node-info

hosts: eks_worker_nodes refers to a group name defined in the inventory — the actual list of which real EC2 instances that group means comes from the dynamic inventory below, not a hardcoded list in the playbook itself.

The real technique — Ansible over SSM, no SSH

AWS Notes already covers what Systems Manager Session Manager is (browser-based shell access, no SSH keys/bastion needed) — Ansible's aws_ssm connection plugin uses that exact same mechanism programmatically, instead of a human clicking into the console.

Traditional Ansible (SSH)This project (SSM)
ConnectionSSH, port 22 open on the targetAWS Systems Manager API — no inbound port needs to be open at all
CredentialsAn SSH key pair, distributed and kept secretThe IAM role already attached to the EC2 instance — nothing extra to distribute
Network requirementDirect network path to port 22 (often needs a bastion host for private-subnet instances)None — SSM works even for an instance with zero inbound rules, as long as it can reach the SSM API outbound
Audit trailWhatever the SSH server itself logsEvery session is logged in CloudTrail/SSM automatically
# inventory/aws_ec2.yml — dynamic inventory, queries AWS directly instead of a static host list
plugin: aws_ec2
regions: [us-east-1]
filters:
  tag:kubernetes.io/cluster/movetrack-ops: owned
keyed_groups:
  - key: tags
    prefix: tag
# ansible.cfg — the actual switch from SSH to SSM
[defaults]
inventory = inventory/aws_ec2.yml

[ssm_connection]
connection = aws_ssm
retries = 3
Why this matters beyond "it's more secure"
Every worker node in this project's EKS cluster sits in a private subnet with no public IP and no open SSH port at all — there is no bastion host to compromise, no SSH key that could leak. The IAM role already attached to each node (needed for it to function as an EKS worker in the first place) is the entire authentication mechanism Ansible relies on here — no separate credential to create, rotate, or protect.

Interview Q&A

What's the actual difference between Terraform and Ansible — don't they both do "infrastructure as code"?
Terraform provisions infrastructure itself — does a VPC/EKS cluster/EC2 instance exist at all. Ansible configures what's already running inside machines that already exist — install a package, enforce a config file, restart a service. They're often used together, in that order: Terraform creates the machine, Ansible configures what runs on it. Using Terraform for configuration management (or vice versa) is possible but fights against what each tool is actually designed for.
What does idempotency mean in Ansible, and why does it matter?
Running the same playbook twice produces the same end state both times — the second run reports "nothing changed" instead of erroring or redoing work. It matters because it makes a playbook safe to re-run at any time, for any reason (recovering from a partial failure, confirming current state matches intent), without needing to reason about whether it's "already been run before."
What does "agentless" mean for Ansible, and why is that a real advantage?
No persistent software needs to be pre-installed on a target machine before Ansible can manage it — it connects (via SSH, or here, via SSM), runs what's needed, and disconnects, leaving nothing permanently running. Tools like Puppet/Chef require an agent installed and running continuously on every managed machine, which is itself something to provision, update, and secure. Agentless removes that whole category of operational overhead.
Why connect Ansible over AWS Systems Manager instead of plain SSH?
SSM authenticates using the IAM role already attached to the EC2 instance — nothing extra to distribute, rotate, or leak, and no inbound port needs to be open on the target at all, even for instances in a fully private subnet with no bastion host. Every session is also automatically logged through CloudTrail, giving a real audit trail with no extra configuration. The tradeoff is that it only works for AWS-managed instances with the SSM agent present and the right IAM permissions — not a general-purpose replacement for SSH outside AWS.
