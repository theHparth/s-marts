React, Redux & TypeScript

Fundamentals + how the dashboard actually uses each one. For when each piece was introduced, see the Steps page.

What each one is, in one line

TermWhat it is
ReactA library for building UI out of reusable, self-contained components — you describe what the UI should look like for a given state, React handles updating the actual page when that state changes.
TypeScriptJavaScript with an optional type system layered on top — catches a whole category of bugs (wrong shape of data, typos in property names) at compile time instead of at runtime.
ViteThe build tool + dev server — fast because it serves native ES modules directly during development instead of bundling everything upfront first.
ReduxA single, centralized store for state that many different components need to share, instead of manually passing data down through many layers ("prop drilling").
Redux ToolkitThe modern, official way to write Redux — replaces old hand-written action types/creators/reducers with a few helper functions doing the same job in far less code.
React RouterClient-side routing — swaps what's displayed as the URL changes, without a full page reload from the server.
VitestThe test runner, built to integrate with Vite directly — same fast dev-server machinery, near-instant test startup.

Generating the project

npm create vite@latest dashboard -- --template react-ts
cd dashboard
npm install
npm install @reduxjs/toolkit react-redux
  • npm create vite@latest runs Vite's generator without installing it globally — same spirit as using curl for Spring Initializr, a one-time scaffold.
  • --template react-ts picks the React + TypeScript flavor — Vite supports many others (plain JS, Vue, Svelte — relevant later, Phase 11's micro-widget).

React hooks used so far

HookWhat it doesExample
useStateGives a component its own local, changeable value. Calling the setter re-renders the component with the new value.const [name, setName] = useState('')
useDispatchReturns the function used to actually trigger a Redux action or thunk.const dispatch = useDispatch<AppDispatch>()
useSelectorReads a value out of the Redux store; re-renders the component automatically whenever that specific value changes.useSelector((state: RootState) => state.moves)
Best way to remember
useState = this component's own private memory. useSelector = reading from the shared memory everyone can see. useDispatch = asking to change the shared memory (you never edit the store directly, only ever through a dispatched action).

Redux Toolkit concepts

ConceptWhat it is
configureStoreBuilds the actual store object from a map of reducers — one entry per feature slice.
Slice (createSlice)One self-contained piece of the store — its own state shape plus the logic that updates it. Generates the reducer and matching actions together.
createAsyncThunkWraps an async function (an API call) so it automatically fires pending/fulfilled/rejected actions as the promise progresses — no manual dispatching needed.
extraReducersWhere a slice handles actions that came from outside itself — e.g. the three automatic thunk actions, as opposed to reducers for actions the slice defines itself.
<Provider store={store}>Makes the store available to every component underneath it in the tree — without it, no component can reach the store at all.
Why reducers can "mutate" state directly
Normally illegal in Redux — state must be immutable. Redux Toolkit uses a library called Immer internally: code that looks like direct mutation (state.status = 'loading') actually produces a brand-new immutable state object behind the scenes. A deliberate convenience, not an exception to the rule.

TypeScript generics

async function request<T>(url: string, options?: RequestInit): Promise<T> {
  const response = await fetch(url, options);
  return response.json() as Promise<T>;
}
  • T is a placeholder type decided by whoever calls the function, not by the function itself.
  • request<MoveRequestResponse>(...) and request<ClaimResponse>(...) — same function, different concrete type each call.
  • unknown vs any: any turns off type-checking entirely; unknown still forces narrowing before most operations are allowed on it.

React Router basics

PieceWhat it does
<BrowserRouter>Wraps the app, turns on routing using the browser's real URL bar.
<Link to="/moves">Renders as a real <a>, but intercepts the click — swaps the page without a full reload. Use instead of a plain <a href> inside the app.
<Routes> / <Route path="..." element={...}>Declares which component renders for which URL path.

Form handling patterns used

  • e.preventDefault() — stops the browser's default form-submit behavior (a full page reload/navigation), which would otherwise happen before any of our JavaScript runs.
  • {condition && <jsx />} — common React pattern: renders the JSX only when condition is truthy, nothing otherwise.

Testing — Vitest + React Testing Library

npm install -D vitest @testing-library/react @testing-library/jest-dom jsdom
  • -D = dev dependency — needed to develop/test, not shipped to real users (contrast with react/react-redux, real runtime dependencies).
  • jsdom simulates a browser DOM inside Node, since tests run in Node, not an actual browser.
  • React Testing Library tests components the way a user would interact with them — finding a button by its visible text, not by reaching into internals.
/// <reference types="vitest/config" />
export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    globals: true,
    setupFiles: './src/test/setup.ts',
  },
})
jest-dom matchers (toBeInTheDocument()) need an explicit setup file
Installing @testing-library/jest-dom alone isn't enough — its extra assertions only get registered (both at runtime and for TypeScript's types) if the package is actually imported somewhere Vitest loads before running tests. Fix: a setup file containing just import '@testing-library/jest-dom';, referenced via test.setupFiles in vite.config.ts. Global once set up — individual test files don't need to import it themselves.

Test files use render() to mount a component into the simulated DOM, and screen.getByPlaceholderText(...)/getByRole(...) to find elements by what a real user would see. A component using useSelector/useDispatch needs a real <Provider> wrapped around it in the test too — usually a small throwaway store built just for that test, separate from the app's real one.

SPA routing behind nginx — why a page refresh can 404

npm run build produces exactly one real HTML file, index.html. Every other "page" (/moves, /claims) doesn't exist as a file at all — React Router fakes those URLs entirely with JavaScript, after index.html has already loaded.

Clicking a link inside the app: React's JS is already running -> intercepts the click -> swaps content client-side. Never asks the server for anything new. Typing a URL directly, or hitting refresh: Brand new request straight to the server, before any JS has run. nginx (by default) asks: "is there a real file called /moves?" -> no -> 404.

The stock nginx:alpine image (used with no custom config) has no rule telling it what to do with a path that isn't a real file — it needs to be told explicitly to fall back to index.html for anything it doesn't recognize, letting React Router take over from there.

server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
try_files argWhat it tries
$uriIs there a real file at this exact path?
$uri/Is there a real folder (with an index file) at this path?
/index.htmlGive up being literal — hand back index.html and let React Router figure out what the URL means
Where this file has to be copied in
Adding nginx.conf to the project does nothing on its own — the Dockerfile's final stage needs an explicit COPY nginx.conf /etc/nginx/conf.d/default.conf after the existing COPY --from=build /app/dist /usr/share/nginx/html line, replacing nginx's own default config with this one.

Interview Q&A

Why use Redux instead of just React's built-in state?
React's useState is local to one component — sharing that value with a distant, unrelated component means manually passing it down through every layer in between ("prop drilling"), which gets unmanageable fast. Redux gives any component direct access to shared state without that chain.
Why Vitest instead of Jest, the more well-known test runner?
Vitest is built specifically to integrate with Vite — it reuses the same fast dev-server machinery, so tests start almost instantly, and understands TypeScript/JSX with zero extra config. Jest predates Vite and needs additional configuration glue to work with a Vite project properly.
Why does an async API call need createAsyncThunk instead of a plain reducer?
Redux reducers must be synchronous, pure functions — no waiting, no side effects. An API call is inherently asynchronous. createAsyncThunk bridges the gap: give it a function returning a Promise, and it automatically dispatches pending/ fulfilled/rejected actions as that promise resolves, so the reducer only ever handles plain, synchronous action objects.
