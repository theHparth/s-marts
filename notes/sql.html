SQL Interview Notes

General SQL reference for interview prep — not tied to a specific Step, reorganized from personal study notes. This project actually uses SQL via PostgreSQL — through Spring Data JPA/Hibernate in the Java services (see Java, Spring & Maven → Seeding with data.sql), and hand-written SQL via Go's database/sql (see Go → Database, no ORM). Corrections/additions from the original notes are called out explicitly in boxes below.

SELECT basics

SELECT * FROM movies;

SELECT name, year FROM movies;

SELECT rankscore, name FROM movies;
  • A result-set is the set of rows a query returns, along with column names and metadata.
  • Row order in a plain SELECT (no ORDER BY) is not guaranteed — it happens to often match table order, but the query optimizer and index structures don't promise it.

LIMIT & OFFSET

SELECT name, rankscore FROM movies LIMIT 20;

SELECT name, rankscore FROM movies LIMIT 20 OFFSET 40;

OFFSET 40 skips the first 40 rows before returning the next LIMIT rows — the standard pattern for pagination.

ORDER BY

SELECT name, rankscore, year FROM movies ORDER BY year DESC LIMIT 10;

-- default direction is ASC
SELECT name, rankscore, year FROM movies ORDER BY year LIMIT 10;

SELECT * FROM movies ORDER BY year DESC, id ASC LIMIT 20;

Multi-column sort: rows are sorted by the first column; only rows that tie on that column get sorted by the second column as a tiebreaker.

DISTINCT

SELECT DISTINCT genre FROM movies_genres;

-- multi-column DISTINCT: treats the (first_name, last_name) pair as the unique unit
SELECT DISTINCT first_name, last_name FROM directors;

WHERE, comparison operators & NULL

SELECT name, year, rankscore FROM movies WHERE rankscore > 9;
SELECT * FROM movies_genres WHERE genre = 'Comedy';
SELECT * FROM movies_genres WHERE genre <> 'Horror';
OperatorMeaning
=Equal
<> or !=Not equal
<, <=, >, >=Less/greater than, inclusive variants
NULL means "unknown," not "empty" — = can't compare to it
-- always returns an empty result-set, never matches anything:
SELECT name FROM movies WHERE rankscore = NULL;

-- correct way to test for NULL:
SELECT name FROM movies WHERE rankscore IS NULL;
SELECT name FROM movies WHERE rankscore IS NOT NULL;
NULL represents "unknown," so unknown = unknown is itself unknown (not true) — = and <> simply never match a NULL. Only IS NULL/ IS NOT NULL test for it correctly.
Correction — matching an exact decimal like 9.8 is a floating-point issue, not a general SQL rule
The original note's WHERE rankscore = 9.8 "doesn't work" and suggests LIKE 9.8 as the fix. That's a MySQL-specific quirk (numeric-to-string coercion happens to let LIKE match), not standard practice, and it's fragile. The real cause: if rankscore is stored as a floating-point type (FLOAT/REAL), the value actually stored may not be exactly 9.8 due to binary floating-point representation — the same reason 0.1 + 0.2 != 0.3 in most programming languages. Two portable, correct fixes: 
-- 1. Round before comparing
SELECT * FROM movies WHERE ROUND(rankscore, 2) = 9.8;

-- 2. Better: store the column as DECIMAL/NUMERIC instead of FLOAT
--    when exact comparisons matter (money, ratings) — DECIMAL stores
--    the exact digits, not a binary approximation.

Logical operators & pattern matching

AND, OR, NOT, BETWEEN, IN, LIKE, EXISTS, ANY, ALL, SOME.

SELECT name, year, rankscore FROM movies WHERE rankscore > 9 AND year > 2000;
SELECT name, year, rankscore FROM movies WHERE rankscore > 9 OR year > 2007;
SELECT name, year, rankscore FROM movies WHERE NOT year <= 2000;

SELECT name, year, rankscore FROM movies WHERE year BETWEEN 1999 AND 2000;
-- inclusive: year >= 1999 AND year <= 2000. low value must be <= high value, else empty result.

SELECT director_id, genre FROM directors_genres WHERE genre IN ('Comedy', 'Horror');
-- same as genre = 'Comedy' OR genre = 'Horror'

SELECT name FROM movies WHERE name LIKE 'Tis%';   -- starts with "Tis"
SELECT first_name FROM actors WHERE first_name LIKE '%es';   -- ends with "es"
SELECT first_name FROM actors WHERE first_name LIKE '%es%';  -- contains "es"
SELECT first_name FROM actors WHERE first_name LIKE 'Agn_s'; -- '_' = exactly one character

% = zero or more characters, _ = exactly one character. To match a literal % or _, escape it: \%, \_. Reference: w3schools — LIKE.

Aggregate functions

SELECT MIN(year) FROM movies;
SELECT MAX(year) FROM movies;
SELECT COUNT(*) FROM movies;
SELECT COUNT(year) FROM movies;
COUNT(*) vs. COUNT(column)
COUNT(*) counts every row, including ones where a column is NULL. COUNT(column) counts only rows where that specific column is not NULL — a common source of off-by-some-N surprises.

GROUP BY & HAVING

SELECT year, COUNT(year) FROM movies GROUP BY year;

SELECT year, COUNT(year) AS year_count FROM movies GROUP BY year ORDER BY year_count;
-- year_count is a column alias

SELECT year, COUNT(year) AS year_count FROM movies GROUP BY year HAVING year_count > 1000;
WHEREHAVING
Applies toIndividual rowsGroups (post-aggregation)
RunsBefore groupingAfter grouping
Can reference an aggregate like COUNT(...)?NoYes
Logical order of execution — the precise version
The original mnemonic (SELECT * FROM WHERE G-H-O-L) is a solid memory aid, but the exact logical order a query is evaluated in (a common interview question on its own) is:
  1. FROM — identify the source table(s)/joins
  2. WHERE — filter individual rows
  3. GROUP BY — form groups
  4. HAVING — filter groups
  5. SELECT — compute the output columns/aggregates
  6. ORDER BY — sort the result
  7. LIMIT — cut down to the requested row count
This is why WHERE can't reference a column alias defined in SELECT (it hasn't been computed yet), but ORDER BY can (it runs after SELECT).

HAVING without GROUP BY behaves like WHERE, but isn't idiomatic — use WHERE for row-level filtering.

JOINs

SELECT m.name, g.genre FROM movies m JOIN movies_genres g ON m.id = g.movie_id;

-- natural join (same column name in both tables) — no need for ON
SELECT * FROM T1 JOIN T2 USING (C1);

SELECT m.name, g.genre FROM movies m LEFT JOIN movies_genres g ON m.id = g.movie_id;

-- 3-way join
SELECT a.first_name, a.last_name
FROM actors a
JOIN roles r ON a.id = r.actor_id
JOIN movies m ON m.id = r.movie_id AND m.name = 'Officer 444';
Join typeKeeps
JOIN / INNER JOIN (default)Only rows with a match on both sides
LEFT JOIN / LEFT OUTER JOINAll left-table rows, NULL for unmatched right-side columns
RIGHT JOIN / RIGHT OUTER JOINAll right-table rows, NULL for unmatched left-side columns
FULL JOIN / FULL OUTER JOINAll rows from both sides, NULL wherever there's no match
Conceptually: a join is a filtered cross product
A table with n rows joined against one with m rows produces a cross product of n × m rows before any filtering; the join condition (ON/USING) filters that down. This is also why joins on large, unindexed tables get expensive fast — worth naming directly if asked about query performance.

A self join (not in the original notes, common interview topic) joins a table to itself — e.g. finding pairs of actors who appeared in the same movie:

SELECT r1.actor_id AS actor_a, r2.actor_id AS actor_b
FROM roles r1
JOIN roles r2 ON r1.movie_id = r2.movie_id AND r1.actor_id < r2.actor_id;

The r1.actor_id < r2.actor_id avoids matching an actor with themselves and avoids duplicate reversed pairs.

Subqueries

SELECT first_name, last_name FROM actors WHERE id IN (
  SELECT actor_id FROM roles WHERE movie_id IN (
    SELECT id FROM movies WHERE name = 'Schindler''s List'
  )
);

SELECT * FROM movies WHERE rankscore >= ALL (SELECT MAX(rankscore) FROM movies);
  • The inner query runs first; its result feeds the outer query.
  • IN — value belongs to the set returned by the subquery.
  • EXISTS — true if the subquery returns one or more rows at all.
  • ANY — true if any value from the subquery satisfies the condition.
  • ALL — true only if every value from the subquery satisfies the condition.
  • A correlated subquery references a column from the outer query inside the inner one, so it re-runs once per outer row (more expensive) — see Correlated subquery.

Data Manipulation Language — INSERT, UPDATE, DELETE

INSERT INTO movies (id, name, year, rankscore) VALUES (412321, 'Thor', 2011, 7);

INSERT INTO movies (id, name, year, rankscore) VALUES
  (412321, 'Thor', 2011, 7),
  (412322, 'Iron Man', 2008, 7.9);

UPDATE movies SET rankscore = 9 WHERE id = 412321;

DELETE FROM movies WHERE id = 412321;
  • UPDATE/DELETE without a WHERE clause affects every row — always double-check the WHERE before running either interactively.
  • TRUNCATE TABLE movies; removes all rows — functionally similar to DELETE without a WHERE, but typically faster and doesn't fire row-level triggers.

PRIMARY KEY vs. UNIQUE — the nuance worth knowing (not in the original notes)
  • A table can have only one PRIMARY KEY, but multiple UNIQUE constraints.
  • PRIMARY KEY implies NOT NULL. A UNIQUE column, in most databases (including Postgres and MySQL), can still hold one NULL — since NULL <> NULL, multiple NULLs don't violate uniqueness.

CASE WHEN — conditional expressions

Not in the original notes, but a routine interview/day-to-day tool: inline conditional logic inside a query.

SELECT name, rankscore,
  CASE
    WHEN rankscore >= 9 THEN 'Excellent'
    WHEN rankscore >= 7 THEN 'Good'
    ELSE 'Average or below'
  END AS rating_bucket
FROM movies;

UNION vs. UNION ALL

Both stack the results of two SELECT queries (same number/type of columns required).

DuplicatesSpeed
UNIONRemovedSlower — has to de-duplicate
UNION ALLKeptFaster — no de-duplication pass

Use UNION ALL whenever duplicates are known to be impossible or acceptable — it's the more common real-world choice for that reason.

Common Table Expressions (CTEs) — WITH

Not in the original notes — very commonly asked now. A CTE names a subquery so it can be referenced like a temporary table, making complex queries far more readable than deeply nested subqueries.

WITH high_rated AS (
  SELECT id, name, rankscore FROM movies WHERE rankscore > 8
)
SELECT name FROM high_rated WHERE rankscore > 9;

A recursive CTE references itself, used for hierarchical/graph-like data (org charts, category trees):

WITH RECURSIVE subordinates AS (
  SELECT id, manager_id, name FROM employees WHERE id = 1        -- anchor
  UNION ALL
  SELECT e.id, e.manager_id, e.name
  FROM employees e
  JOIN subordinates s ON e.manager_id = s.id                      -- recursive step
)
SELECT * FROM subordinates;

Window functions

Not in the original notes — one of the most commonly asked SQL interview topics at any mid-to-senior level. Unlike GROUP BY, a window function computes a value per row while still having access to a set ("window") of related rows — you don't lose the individual row detail.

SELECT name, year, rankscore,
  ROW_NUMBER() OVER (PARTITION BY year ORDER BY rankscore DESC) AS rank_in_year
FROM movies;
FunctionWhat it does
ROW_NUMBER()1, 2, 3... — always unique, even for tied values
RANK()Ties share the same rank; the next rank skips (1, 1, 3)
DENSE_RANK()Ties share the same rank; the next rank doesn't skip (1, 1, 2)
LAG(col) / LEAD(col)Value from the previous / next row in the window — e.g. comparing a row to the one before it, no self-join needed
The classic interview framing
"Find the top 3 highest-rated movies per year" is a textbook window-function question — GROUP BY alone can't do it (it collapses rows instead of ranking them). PARTITION BY resets the ranking for each group (each year here), the same way GROUP BY groups rows, but without collapsing them into one row per group.

Transactions & ACID

Not in the original notes. A transaction groups multiple statements so they succeed or fail together.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- or ROLLBACK; to undo both if something went wrong
ACID propertyWhat it guarantees
AtomicityAll statements in the transaction succeed, or none do
ConsistencyThe database moves from one valid state to another — constraints always hold
IsolationConcurrent transactions don't see each other's uncommitted changes
DurabilityOnce committed, changes survive a crash/power loss

Normalization

Not in the original notes — a very standard interview question ("what's 3NF?"). The goal: reduce data redundancy and avoid update anomalies by splitting data into related tables.

FormRule
1NFEvery column holds atomic (indivisible) values — no comma-separated lists in one cell
2NF1NF, plus every non-key column depends on the whole primary key, not just part of it (relevant for composite keys)
3NF2NF, plus no non-key column depends on another non-key column (no "transitive" dependency)

This project's movies / movies_genres split (a movie can have many genres) is a real example of normalization in action — genres live in their own table rather than as a comma-separated column on movies, avoiding exactly the 1NF violation above.

SQL injection & parameterized queries

Not in the original notes — a security fundamental, and directly relevant to this project's own code. Never build a query by concatenating raw user input into a SQL string:

-- NEVER do this — a value like ' OR '1'='1 breaks out of the string entirely
query := "SELECT * FROM movies WHERE name = '" + userInput + "'"

Interview Q&A

What's the difference between WHERE and HAVING?
WHERE filters individual rows before grouping happens; HAVING filters groups after GROUP BY has run, and can reference aggregate functions like COUNT(...) that don't exist yet at the WHERE stage.
What's the logical order SQL clauses actually execute in?
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. This is why WHERE can't use a column alias defined in SELECT (it hasn't run yet), but ORDER BY can.
How do window functions differ from GROUP BY?
GROUP BY collapses multiple rows into one row per group. A window function (ROW_NUMBER(), RANK(), etc. with OVER (...)) computes a value per row while still having access to a related set of rows — you keep every original row and get a ranking/running-total/comparison alongside it, instead of losing row-level detail.
When would you use UNION ALL instead of UNION?
Whenever duplicate rows across the two result sets are known to be impossible, or are acceptable — UNION ALL skips the de-duplication pass UNION does, so it's faster. Default to UNION ALL unless you specifically need duplicates removed.
How do parameterized queries prevent SQL injection?
The query structure and the user-supplied value are sent to the database separately — the database never parses the value as part of the SQL text, so a malicious string like ' OR '1'='1 is treated as a literal value to search for, not executable SQL. String concatenation is what allows injection in the first place, by letting user input become part of the query's actual syntax.
