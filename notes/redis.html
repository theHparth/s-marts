Redis Interview Notes

The original notes covered only strings (SET/GET), key expiration, and Docker setup — expanded here to cover every core data type, transactions, pub/sub commands, persistence, replication/clustering, and eviction policies. Language target: Python, using the redis-py client — the same library this project already uses in Python, FastAPI & scikit-learn → Caching predictions, so every command below has a real, already-working counterpart in this codebase.

What Redis actually is

QuestionAnswer
What kind of database?In-memory key-value store — data lives in RAM, not on disk (with optional disk persistence, see below)
Why so fast?RAM access is orders of magnitude faster than disk; Redis is also single-threaded for command execution, which avoids lock-contention overhead for most operations
What's it usually used for?Caching, session storage, rate limiting, leaderboards, pub/sub messaging, real-time counters
Redis vs. a "real" databaseRedis is not a system of record for this project — see Python notes: it caches predictions, Postgres remains the source of truth

redis-cli vs. a real client library
redis-cli is for humans poking around interactively — exactly like psql for Postgres. An actual application (like this project's FastAPI service) uses a client library instead (redis-py for Python) — see the Python section below.

Every Redis data type — the big gap in the original notes

Expiration & eviction policies

CommandWhat it does
EXPIRE key 60Set (or reset) a 60-second TTL on an existing key
TTL keySeconds remaining — -1 means no expiration set, -2 means the key doesn't exist
PERSIST keyRemove a key's expiration, make it permanent again
Eviction policies — what happens when Redis's memory limit is hit? Not in the original notes.
Redis doesn't grow memory forever — maxmemory-policy decides what gets deleted when the configured memory limit is reached:
PolicyBehavior
noevictionReject new writes once full — errors instead of losing data (Redis's default)
allkeys-lruEvict the Least Recently Used key, from any key — typical cache behavior
volatile-lruSame, but only considers keys that have a TTL set
allkeys-lfuEvict the Least Frequently Used key — better than LRU when "popular" and "recent" diverge
This project's usage (predictions cached with a 5-minute TTL) is exactly the volatile-* policies' target case — every key it writes already has an expiration.

Transactions — not in the original notes

MULTI
SET a 1
INCR a
EXEC          # runs both commands atomically, back to back

WATCH a       # abort the transaction if "a" changes before EXEC runs
MULTI
...
EXEC
Redis transactions aren't like SQL transactions
MULTI/EXEC queues commands and runs them without any other client's commands interleaving in between — but there's no rollback if one command in the middle fails logically. WATCH adds optimistic locking: if the watched key changes before EXEC, the whole transaction is aborted, and the client can retry.

Pub/Sub — commands added, concept kept from the original notes

The original notes described pub/sub conceptually ("event driven way of communicating between processes") but had no actual commands. Here they are:

Publisher Redis Subscriber(s) │ │ │ │── PUBLISH channel msg ─►│ │ │ │── delivers to every ─────────►│ │ │ current subscriber │ │ │ of "channel" │ Subscribers must already be listening — Redis pub/sub does NOT queue messages for offline subscribers.
SUBSCRIBE channel1          # blocks, waiting for messages
PUBLISH channel1 "hello"    # sent to every current subscriber of channel1
Pub/Sub messages are fire-and-forget — not durable
If nobody is subscribed when PUBLISH runs, the message is simply gone — Redis pub/sub is not a durable message queue. For "must not lose this message" needs, use Redis Streams (XADD/ XREAD) instead, or a dedicated queue like SQS/RabbitMQ (this project's own Phase 4, not built yet).

Persistence — RDB vs. AOF not in the original notes

Redis is in-memory, but data can survive a restart two different ways:

RDB (snapshotting)AOF (Append-Only File)
How it worksPeriodic full snapshot of the dataset written to diskEvery write command logged to a file, replayed on restart
Data loss on crashEverything since the last snapshotMuch less — depends on fsync frequency (can be near-zero)
File sizeCompactLarger, grows continuously (compacted periodically)
Restart speedFast — just load the snapshotSlower — replay the whole log

Both can be enabled together — RDB for fast restarts/backups, AOF for minimal data loss. This project's use of Redis as a pure cache (Postgres is the real source of truth) means persistence is largely optional here — worth explicitly naming that reasoning if asked why.

Replication & clustering not in the original notes

ConceptWhat it solves
Master-Replica replicationOne or more read-only replicas copy a master's data — scales reads, provides a failover copy
Redis SentinelMonitors master/replicas, automatically promotes a replica to master if the master fails — high availability without manual intervention
Redis ClusterShards data across multiple nodes by hashing the key — scales writes and total dataset size beyond one machine's RAM

Python — using Redis from code (redis-py)

The exact library this project's Claims Triage ML service uses — see Python, FastAPI & scikit-learn → Caching predictions for the real, running version of this pattern. Every command above has a direct Python method:

import redis

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

# Strings
r.set("name", "tech")
r.get("name")                       # "tech", or None if missing
r.setex("session:123", 300, "active")  # SET ... EX 300 in one call
r.incr("counter")

# Lists
r.lpush("queue", "task1", "task2")
r.lrange("queue", 0, -1)

# Sets
r.sadd("tags", "python", "redis")
r.smembers("tags")

# Hashes
r.hset("user:1", mapping={"name": "Parth", "age": "25"})
r.hgetall("user:1")

# Sorted sets
r.zadd("leaderboard", {"alice": 100, "bob": 90})
r.zrange("leaderboard", 0, -1, withscores=True)

# Expiration
r.expire("name", 60)
r.ttl("name")

# Transactions — a pipeline is redis-py's MULTI/EXEC
pipe = r.pipeline()
pipe.set("a", 1)
pipe.incr("a")
pipe.execute()

# Pub/Sub
pubsub = r.pubsub()
pubsub.subscribe("channel1")
r.publish("channel1", "hello")

HSET key f1 v1 f2 v2r.hset(key, mapping={"f1": "v1", "f2": "v2"})

This project's actual cache key pattern, for reference
app/cache.py doesn't cache under a raw key like "name" — it hashes the whole request payload into a deterministic key (hashlib.sha256 of the sorted JSON), so identical prediction requests always map to the same Redis key. Interview Q&A

Why is Redis so much faster than a traditional database?
Data lives in RAM, not on disk — RAM access is orders of magnitude faster. Redis also executes commands single-threaded, which avoids the lock-contention overhead a multi-threaded database pays for concurrent access to the same data, at the cost of not parallelizing CPU-bound work across cores for a single instance.
What's the difference between RDB and AOF persistence?
RDB takes periodic full snapshots — compact, fast to restart from, but can lose everything since the last snapshot on a crash. AOF logs every write command and replays it on restart — much less data loss, but a larger file and slower restart. They can run together: RDB for fast recovery, AOF for minimal loss.
Is Redis Pub/Sub a reliable message queue?
No — it's fire-and-forget. If no client is subscribed when PUBLISH runs, the message is simply lost, with no delivery guarantee or replay. For durable message delivery, use Redis Streams instead, or a dedicated message queue.
Why shouldn't you use the KEYS command in production?
KEYS * scans the entire keyspace in one blocking operation — on a large dataset this can freeze every other client's commands for the duration. SCAN does the same job incrementally, in small non-blocking batches, and is the production-safe choice.
When would you reach for a Sorted Set instead of a plain Set?
Whenever ranking or ordering matters — a leaderboard, a priority queue, "top N most recent/highest-scored" queries. A plain Set only tracks unique membership with no order; a Sorted Set keeps every member ordered by its score, so range queries like "top 10" are a single fast command instead of fetching everything and sorting client-side.
