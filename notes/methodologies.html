Agile & SDLC Methodologies Interview Notes

The original source file only covered Agile/Waterfall/Scrum basics — expanded here to cover every SDLC methodology worth knowing for an interview: Waterfall, V-Model, Spiral, Agile, Scrum, Kanban, Lean, XP, and DevOps, with a diagram and comparison table for each. Diagrams are plain-text so they render consistently everywhere.

SDLC — the umbrella

SDLC (Software Development Life Cycle) is the general process any of these methodologies fills in differently: specification → development → validation → evolution. Every methodology below is one specific answer to "in what order, and how repeatedly, do we move through those stages?"

ModelShapeBest for
WaterfallStrictly sequential, one passFixed, well-understood requirements (e.g. hardware-tied systems)
V-ModelSequential, but each dev stage pairs with a matching test stageSafety-critical / highly regulated systems
SpiralRepeated risk-analysis loops, growing in scope each passLarge, high-risk, poorly-understood projects
AgileShort, repeated iterations, continuous feedbackEvolving requirements, fast market feedback needed
ScrumAgile + fixed-length sprints, defined roles/ceremoniesTeams that want Agile with real structure
KanbanAgile + continuous flow, no fixed iteration lengthOngoing support/maintenance work, unpredictable arrival of tasks

Waterfall

Requirements │ ▼ Design │ ▼ Implementation │ ▼ Verification │ ▼ Maintenance Each phase must fully finish before the next starts — no going back once you move on.
DisadvantageWhy it hurts
Hard to change directionRequirements are locked in early; a late discovery means redoing already-finished phases
High cost of failureA mistake found in Verification can trace back to a bad decision made in Requirements, months earlier
Late customer feedbackThe customer often doesn't see working software until Implementation is nearly done

Still genuinely appropriate when requirements really are stable and well understood up front — e.g. systems tightly coupled to fixed hardware, where redesigning mid-project is prohibitively expensive.

V-Model not in the original notes

Waterfall's structure, but every development stage is explicitly paired with a verification stage — the "V" shape comes from drawing development stages going down the left side and their matching test stages going up the right side.

Requirements ───────────────────────────── Acceptance Testing │ │ ▼ │ System Design ─────────────────────────────── System Testing │ │ ▼ │ Architecture Design ───────────────────── Integration Testing │ │ ▼ │ Module Design ───────────────────────────────── Unit Testing \ / \ / ──────── Coding ────────── Left side = build it. Right side = prove that side of the V was built correctly.

Requirements pairs with Acceptance Testing, System Design pairs with System Testing, and so on down to Coding at the bottom of the V — test planning happens at the same time as the matching design stage, not as an afterthought once coding is done.

Spiral Model not in the original notes

Repeats four activities every cycle, growing the amount of working software each time around — risk analysis happens every single loop, not just once at the start.

1. Determine objectives & alternatives │ 4. Plan next ▼ cycle ◄──[ SPIRAL ]──► 2. Identify & (grows resolve risks each loop) ▲ │ 3. Develop & test this cycle's piece Each full loop around produces a more complete, more validated version of the system.

Chosen for large, high-risk, poorly-understood projects where the cost of a wrong early decision is severe enough to justify explicit risk analysis on every iteration — heavier process than Agile, but with Waterfall's up-front planning discipline built in per cycle.

The values are "X over Y," not "X instead of Y" — a common misread
The Manifesto explicitly says the items on the right still have value — the point is the left side is valued more when the two are in tension. "Working software over documentation" doesn't mean "no documentation," it means don't let documentation become the bottleneck to shipping.

Scrum

The most common way teams actually implement Agile — Agile is the philosophy, Scrum is one concrete framework for doing it, with defined roles, artifacts, and a fixed rhythm.

Roles

RoleResponsible for
Product OwnerWhat gets built, and in what priority order — owns the Product Backlog
Scrum MasterRemoving blockers, protecting the team's process, facilitating ceremonies — not a project manager telling people what to do
Development TeamHow the work actually gets built — self-organizing, cross-functional

Artifacts

ArtifactWhat it is
Product BacklogEverything that could ever be built, ranked by priority — never "done," constantly refined
Sprint BacklogThe slice of the Product Backlog committed to for this one sprint

Story points & velocity — not in the original notes
Story points estimate relative effort/complexity of a task (not hours directly) — typically Fibonacci-like values (1, 2, 3, 5, 8, 13...) so the team is forced to distinguish "clearly small" from "clearly big" rather than false-precision hour estimates. Velocity is how many story points a team completes per sprint on average — used to forecast how much backlog a future sprint can realistically hold, not as an individual performance metric.
Definition of ReadyDefinition of Done
Applies toA backlog item, before it enters a sprintA backlog item, before it's considered complete
AnswersIs this well-understood enough to start work on?Does "complete" mean the same thing to everyone — coded, tested, reviewed, deployed?

Kanban not in the original notes

Agile, but continuous — no fixed-length sprints. Work flows through columns, and each column has a hard cap on how many items can sit in it at once (a WIP limit), which is Kanban's core mechanism for surfacing bottlenecks immediately instead of at a retrospective two weeks later.

Lean & Extreme Programming (XP) not in the original notes

Lean — 7 wastes to eliminate

WasteSoftware example
Partially done workHalf-finished features sitting in branches, never merged
Extra featuresBuilding something nobody asked for "just in case"
RelearningUndocumented tribal knowledge that has to be rediscovered repeatedly
HandoffsWork passed between teams/people, losing context each time
Task switchingSplitting focus across too many things at once
DelaysWaiting on approvals, code review, environment access
DefectsBugs caught late cost far more to fix than bugs caught immediately

Extreme Programming (XP) — engineering-practice-focused Agile

  • Pair programming — two developers, one keyboard, continuous real-time code review.
  • Test-Driven Development (TDD) — write the failing test first, then the code that makes it pass.
  • Continuous Integration — merge and test against main frequently, never let a branch drift far from it.
  • Small, frequent releases — ship in small batches instead of one large release.

DevOps not in the original notes

Extends Agile's "ship fast, get feedback fast" philosophy past the development team and into operations — the same team that builds the software also owns deploying and running it, closing the loop that Waterfall (and even plain Scrum) leaves open between "code is done" and "code is actually live."

Plan → Code → Build → Test → Release → Deploy → Operate → Monitor ▲ │ └──────────────────────── feedback loop ──────────────────────┘

This project's own workflow already lives inside that loop — GitHub Flow (issue → branch → PR → merge) is the Plan/Code/Build/Test slice; see Git & GitHub for how it's actually practiced here. The automated CI/CD security-gate piece (Jenkins/Trivy/ZAP) is Phase 5 on the Architecture page — not built yet, but the same DevOps loop this section describes.

Interview Q&A

When would you choose Waterfall over Agile, if Agile is generally more flexible?
When requirements are genuinely stable and well understood up front, and the cost of mid-project change is severe — e.g. systems tightly coupled to fixed hardware, or heavily regulated environments where every change needs formal sign-off. Agile's advantage (cheap, continuous change) is wasted effort if change was never going to happen anyway, and Waterfall's upfront planning rigor can be a genuine asset in that specific situation.
How do you decide between Scrum and Kanban for a team?
Scrum fits work that can be planned into fixed-length chunks with a clear "done" per sprint — typical product development. Kanban fits continuous, unpredictable work where tasks arrive at any time and priorities can shift immediately — typical of a support/maintenance team, where a 2-week sprint commitment doesn't match how the work actually shows up.
What is velocity actually used for in Scrum?
Forecasting how much backlog a team can realistically commit to in a future sprint, based on their historical average story points completed per sprint. It's a planning tool for the team, not a performance metric to compare between teams or individuals — velocity is relative to one team's own estimation habits, not an absolute measure of output.
How does DevOps relate to Agile?
Agile is about how a development team plans and builds software in short, feedback-driven iterations. DevOps extends that same philosophy past "code is done" into deployment and operations — the same team owns running the software in production too, closing the feedback loop between writing code and seeing how it actually behaves live, instead of handing that off to a separate ops team.
