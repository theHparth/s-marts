AWS Interview Notes

General AWS reference for interview prep — not tied to a specific Step, reorganized and merged from two personal study files (~5-7 years old). Corrections and additions are called out explicitly in boxes below — AWS moves fast, and a few things in the original notes are now renamed, deprecated, or missing entirely.

Read this first — what's actually changed since these notes were written
  • Amazon ElasticSearch Service is now Amazon OpenSearch Service (renamed 2021, after AWS forked Elasticsearch over an Elastic N.V. licensing dispute). If an interviewer says "OpenSearch," that's the same service the original notes call "ElasticSearch."
  • AWS Single Sign-On (SSO) is now AWS IAM Identity Center (renamed 2022) — same service, and now the recommended default way to manage workforce access across accounts, ahead of manually federating IAM roles.
  • Savings Plans exist now (launched 2019) — a more flexible alternative to Reserved Instances (commit to a $/hour spend instead of a specific instance type/family). The original notes only cover Reserved Instances; Savings Plans are usually the better default answer in 2026.
  • "NLB is out of courses, no exam question" in the original notes is simply wrong — Network Load Balancer is a core, heavily-tested service. That was likely a note about one specific exam version at one point in time, not a lasting AWS fact.
  • Graviton (ARM-based) instances aren't mentioned at all in the original notes but are a real, frequently-asked cost/performance topic now — see the EC2 section.
  • Several genuinely important services/topics were missing entirely from the originals — added below: a proper IAM fundamentals section, CloudFront (mentioned once, never actually explained), API Gateway, a real DynamoDB section, CloudFormation basics, current S3 storage features (Intelligent-Tiering, Object Lock, Access Points), and generative AI on AWS (Bedrock, Amazon Q) — essentially nonexistent as an AWS product category when the originals were written, now a routine interview topic.

3. Data & compute models — Databases → Serverless & containers → Sample reference architecture (puts tiers 1-3 together into one real picture — the moment this page stops being a list of services and starts being a system).

IAM fundamentals not in the original notes

Almost every other AWS service's security question comes back to IAM — worth understanding this before anything else below.

ConceptWhat it is
UserA person or application with long-term credentials (password and/or access keys)
GroupA collection of users — attach a policy once, every member inherits it
RoleA set of permissions assumed temporarily — by a user, an AWS service (e.g. EC2, Lambda), or an external identity. No long-term credentials; issues short-lived tokens via STS.
PolicyA JSON document listing what's allowed/denied — attached to a user, group, or role
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
Policy elementMeaning
EffectAllow or Deny
ActionWhich API call(s) this statement covers
ResourceWhich specific resource(s) (by ARN) this applies to
Principal(Resource-based policies only) who the policy applies to
Identity-based vs. resource-based policies — a common point of confusion
An identity-based policy is attached to a user/group/role ("this role can read this bucket"). A resource-based policy is attached to the resource itself (an S3 bucket policy: "this account can read this bucket"). They can grant access from either direction — a resource can be reachable because the identity's policy allows it, OR because the resource's own policy allows it — but an explicit Deny anywhere always wins over any Allow.

Principle of least privilege — grant only the specific actions/resources actually needed, nothing broader "just in case." The most commonly cited IAM best practice in interviews, and the reason wildcard ("Action": "*", "Resource": "*") policies are a red flag.

Why use a role instead of embedding long-term access keys in an application: an EC2 instance/Lambda function assumes a role and gets automatically-rotated temporary credentials — nothing hardcoded to leak, nothing to manually rotate.

CLI/SDK vs. Console — a real interview framing
The Console is for humans clicking around. The CLI (and the SDK, for code) is for anything that needs to be scripted or automated — CI/CD pipelines, cron jobs, Infrastructure as Code tooling. "Which would you use to integrate AWS directly into an application" → SDK, not CLI, not Console.

EC2 & purchasing options

  • EC2 = Elastic Compute Cloud — IaaS. More expensive than S3 for equivalent workloads; best suited to predictable workloads (unpredictable/spiky → Lambda instead).
  • Instance data on the root volume (if instance-store backed, not EBS) is lost on stop/termination.
  • Reverse proxy pattern: used when the EC2 instance sits in a private subnet with no direct internet access.
Purchase optionBest for
On-DemandShort/unpredictable workloads, no commitment, highest per-hour price
Reserved Instances (1-3 yr)Long, steady workloads with known instance type/family
Savings Plans (not in original notes)Same idea as RIs but commit to a $/hour spend instead of a specific instance type — more flexible, generally the better default recommendation now
Spot InstancesFault-tolerant, interruptible workloads (batch, CI, data analysis) — up to 90% off, can be reclaimed with 2-min warning
Dedicated InstancesHardware dedicated to your account, may still share with other instances in your account, no placement control
Dedicated HostsWhole physical server, full placement control, visible sockets/cores — for BYOL licensing or strict compliance

Hotel analogy (kept from the original notes, it's a genuinely good one): On-Demand = walk-in, pay full price. Reserved = book ahead for a discount. Spot = bid on empty rooms, can get kicked out. Dedicated Host = book the entire building.

Graviton instances — not in the original notes, worth knowing
AWS's own ARM-based Graviton processors (Graviton2/3/4) power instance families like m7g, c7g, r7g — typically 20-40% better price/performance than the equivalent x86 instance for workloads that support ARM. A real, commonly-asked cost-optimization talking point now.

Disaster recovery basics

  • RPO (Recovery Point Objective) — how much data you can afford to lose (drives backup frequency).
  • RTO (Recovery Time Objective) — how long recovery is allowed to take (drives downtime tolerance).

Storage

Durability rankPerformance rank
Ordering (from original notes)S3 > EFS > EBSEBS is the maximum-performance option

EBS (Elastic Block Store)

  • A network-attached block volume (not a file system) — root volumes for EC2 can be EBS or instance-store.
  • Instance store: physically attached, better raw I/O, but lost on stop/terminate, can't be resized.
  • Snapshots restored from S3-backed storage need "pre-warming" (a full read pass) for best performance on first access.

EFS & FSx

  • EFS — managed NFS, mountable by many EC2 instances across multiple AZs simultaneously. Linux only.
  • FSx — managed 3rd-party file systems. FSx for Windows File Server = Windows/SMB. FSx for Lustre = high-performance computing.

S3

  • Object storage via REST API — not a relational database, not attachable to EC2 as a volume.
  • Max object size: 5TB. Uploads >100MB should, and >5GB must, use multi-part upload.
  • Versioning — bucket-level; overwriting the same key increments a version number instead of replacing data.
Encryption typeWho manages the key
SSE-S3AWS (AES-256, header: x-amz-server-side-encryption: AES256)
SSE-KMSAWS KMS (adds audit trail + user-level key control)
SSE-CYou supply the key per-request over HTTPS; AWS never stores it
Client-sideYou encrypt/decrypt entirely yourself before/after S3
S3 features missing entirely from the original notes
  • S3 Intelligent-Tiering (2018) — automatically moves objects between access tiers based on actual usage patterns, no manual lifecycle rule needed. A very commonly asked "which storage class" answer now.
  • S3 Object Lock — true object-level WORM (Write Once Read Many), with Governance/Compliance retention modes. More precise than the original notes' "Vault Lock" (which is actually a Glacier-specific feature).
  • S3 Access Points — named network endpoints with their own policy, for simplifying access management on buckets shared by many applications.
  • S3 Object Lambda — run a Lambda function to transform data as it's retrieved from S3, without a separate copy.
  • Lifecycle rules — transition actions (move to a cheaper class after N days) and expiration actions (delete after N days), can target a prefix or object tag.
  • Security: IAM policies (user-based) + Bucket Policies/ACLs (resource-based). A principal can access an object if IAM allows it OR the resource policy allows it, AND there's no explicit Deny.
  • CORS matters for cross-origin browser requests to a bucket (a popular exam question).

CloudFront named once, never explained in the originals

Amazon's CDN (Content Delivery Network) — caches content at edge locations physically close to users, so repeat requests don't have to travel back to the origin server every time.

ConceptWhat it means
OriginWhere the real content lives — an S3 bucket (static files) or a custom origin (ALB, EC2, any HTTP server)
Edge locationA CloudFront cache point close to end users — far more of these than there are AWS regions
Cache behaviorPer-path-pattern rules for what to cache, for how long, and which origin to use
Signed URL / Signed CookieTime-limited, authenticated access to private content (e.g. a paid video service)
CloudFront vs. Global Accelerator — a real interview question, and a typo in the original notes ("Global Accelerate")
Both use AWS's global network to improve performance, but for different traffic:
  • CloudFront — caches HTTP/HTTPS content at the edge. Best for static/cacheable content (websites, video, APIs with cacheable responses).
  • AWS Global Accelerator — doesn't cache anything; it proxies TCP/UDP traffic over AWS's private backbone network to the nearest healthy endpoint, using static anycast IPs. Best for non-HTTP protocols, or applications needing fast regional failover without a DNS change.

Networking — VPC

  • A CIDR block has a base IP + subnet mask (e.g. /24) defining the address range.
  • AWS reserves 5 IPs per subnet — a subnet needing 29 usable IPs needs at least a /26 (64 - 5 = 59 ≥ 29), not a /27 (32 - 5 = 27 < 29). A classic exam-style sizing question.
ComponentRole
Internet GatewayVPC-level, gives IPv4/IPv6 internet access
NAT GatewayManaged, gives private-subnet instances outbound internet access (IPv4 only)
NAT InstanceLegacy, self-managed equivalent of NAT Gateway — must disable source/destination check
Egress-Only Internet GatewaySame idea as NAT Gateway, but for IPv6 (all IPv6 addresses are public by nature)
Route TablesMust be edited to actually route subnet traffic to any of the above
Network ACLSecurity Group
Stateless/statefulStateless — must define both inbound and outbound rules explicitly, including ephemeral return portsStateful — return traffic automatically allowed
Applies atSubnet levelEC2 instance (ENI) level
Can block a specific IP?YesNo — Security Groups only support Allow rules, no explicit Deny/block of an individual IP
  • VPC Peering — connects two VPCs over AWS's private network, non-transitive (A↔B and B↔C doesn't give A↔C).
  • VPC Endpoints — private connectivity to AWS services without traversing the public internet. Gateway type (S3, DynamoDB — uses a route table entry) vs. Interface type (most other services — provisions an ENI).
  • Transit Gateway — hub-and-spoke connectivity for thousands of VPCs/on-prem networks, region-bound, supports transitive routing (unlike plain VPC Peering).
  • PrivateLink — exposes a specific service from one VPC to many others without full peering; needs an NLB on the provider side and an ENI on the consumer side.
  • Bastion Host — a public instance used purely as an SSH jump box into private-subnet instances.

Load balancing & Auto Scaling

Load balancerLayerKey notes
Application Load Balancer (ALB)7 (HTTP/HTTPS/WebSocket)Routes by path, hostname, query string/headers. Great fit for microservices/containers (ECS). Multiple SSL certs via SNI.
Network Load Balancer (NLB)4 (TCP/TLS/UDP)Extreme performance, millions of req/sec, ~100ms latency. One static IP per AZ — supports Elastic IP for whitelisting. Still a core, actively-tested service despite what the original notes claimed.
Gateway Load Balancer (GWLB)3 (Network)For inserting third-party security/inspection appliances transparently into traffic flow
Classic Load Balancer (CLB)4 & 7Legacy — one SSL cert only. AWS steers new workloads toward ALB/NLB; still worth recognizing for exam/legacy-system purposes only.
  • Health checks: ALB checks happen at the target group level, not the load balancer.
  • Load balancers distribute connections across existing instances — they do not themselves add/remove instances. That's Auto Scaling's job.

Auto Scaling Groups (ASG)

  • Free — you only pay for the underlying EC2 instances.
  • Scale out (add) / scale in (remove) based on CloudWatch alarms.
  • Lifecycle hooks run extra steps before an instance goes into service (pending state) or before it's terminated (terminating state) — e.g. install software, or extract logs before shutdown.
  • ASG launches a replacement for an unhealthy instance — it does not reboot the unhealthy one for you.
  • High availability needs a multi-AZ ASG — at least 2 instances across 2 AZs.
Scalability typeWhat it meansExample
Vertical (scale up/down)Bigger/smaller instance — limited by hardware, used in non-distributed systemsRDS, ElastiCache
Horizontal (scale out/in)More/fewer instances — used in distributed systems, easier to achieveEC2 behind an ASG

Databases

RDS & Aurora

  • Managed service: automated backups, automatic OS/DB patching, Multi-AZ for DR, read replicas for read scaling, point-in-time restore.
  • You cannot access the underlying OS to run scripts — that's the whole point of "managed."
  • Compute scaling is manual (change instance type); storage auto-scaling is available.
  • Aurora: 6 copies of data across 3 AZs — needs 4/6 for writes, 3/6 for reads.
  • Read replicas: up to 5, asynchronous replication, can be promoted to their own standalone DB. Same-region replication is free; cross-region is paid.
Not in the original notes: Aurora Serverless v2 & RDS Proxy
Aurora Serverless v2 scales database capacity automatically based on load, billed per fine-grained capacity unit — good for variable/unpredictable database workloads without managing instance sizing. RDS Proxy pools and manages database connections, protecting against connection exhaustion from spiky serverless/Lambda-heavy workloads.

DynamoDB — barely covered in the original notes, expanded here

  • A fully managed, serverless NoSQL key-value/document database — not relational, no SQL joins.
  • Every table needs a partition key (required) and optionally a sort key (composite primary key) — the partition key determines which physical partition an item lives on.
  • Capacity modes: On-Demand (pay per request, scales automatically) vs. Provisioned (set read/write capacity units ahead of time, cheaper at steady, predictable load).
  • DAX (DynamoDB Accelerator) — an in-memory cache in front of DynamoDB for microsecond read latency.
  • Global Tables — multi-region, multi-active replication for low-latency global access.
  • DynamoDB Streams — a time-ordered change log of table item modifications, commonly used to trigger a Lambda function on every write.

Renamed in 2021. Same purpose — combined with a database for search operations, supports partial matches, provisioned cluster, Multi-AZ, used heavily in log analytics/Big Data pipelines.

Serverless & containers

Lambda — thin in the original notes, expanded here

  • Max execution time: 15 minutes, then it's force-terminated.
  • Best for unpredictable/event-driven workloads — genuinely cost-effective since you pay only for actual invocation time, not idle capacity.
  • Triggers (not in original notes): S3 events, API Gateway, DynamoDB Streams, EventBridge, SQS, and more — Lambda is almost always wired to something else, rarely invoked standalone.
  • Cold starts — the first invocation after idle time pays a startup penalty (especially with a VPC-attached Lambda or a large deployment package); a real interview topic around latency-sensitive Lambda design.
  • Layers — share common code/dependencies across multiple Lambda functions without bundling them into every deployment package.
  • Concurrency — reserved concurrency guarantees capacity for a function; without it, a traffic spike across all your functions can throttle each other.

API Gateway — missing entirely from the original notes

  • The front door for exposing Lambda functions (or any backend) as a REST/HTTP API — handles routing, auth, throttling, request/response transformation.
  • REST API — full feature set (request validation, API keys, usage plans). HTTP API — newer, cheaper, lower-latency, fewer features — the default recommendation for a simple Lambda-backed API today.
  • A Lambda function behind an ALB receives its HTTP request translated into a JSON event — same underlying pattern as API Gateway's integration.

Synchronous vs. asynchronous application communication
Synchronous (app → app directly) can cascade failure if one service gets overwhelmed by a traffic spike. Asynchronous/event-based (app → queue → app, e.g. via SQS) lets each side scale independently and absorbs spikes in the queue instead of failing outright.

Interview Q&A

What is Amazon OpenSearch Service, and how does it relate to "Amazon ElasticSearch"?
Same service — Amazon ElasticSearch Service was renamed to Amazon OpenSearch Service in 2021, after AWS forked the open-source Elasticsearch project due to a licensing dispute with Elastic N.V. Functionally it's the same managed search/analytics engine, commonly paired with a database for search or used for log analytics at scale.
What's the difference between Reserved Instances and Savings Plans?
Reserved Instances commit to a specific instance type/family/region for a discount. Savings Plans (launched 2019) commit to a dollar-per-hour spend instead, and automatically apply across any instance type/family/region/even compute service (EC2, Fargate, Lambda) — more flexible, and generally the recommended default over RIs for new commitments today.
When would you choose an NLB over an ALB?
NLB when you need raw TCP/UDP performance, extremely low latency, millions of requests per second, or a static IP per AZ. ALB when you need Layer 7 features — path/host-based routing, WebSocket support, and it's the natural fit for microservices/container-based (ECS) applications routing to multiple target groups.
Can a Security Group block a specific malicious IP address?
No — Security Groups only support Allow rules, not explicit Deny, so they can't block one specific IP. Use a Network ACL at the subnet level instead, which supports both Allow and Deny rules.
When would you choose DynamoDB over RDS?
DynamoDB when the access pattern is simple key-value/document lookups at very high, elastic scale with single-digit-millisecond latency and you don't need SQL joins or complex relational queries. RDS/Aurora when you need relational integrity, joins, transactions across multiple tables, or existing SQL-based tooling. DynamoDB's schema is defined by query patterns, not by the data's natural relational shape — a real design-time tradeoff, not just a performance one.
What's the difference between CloudFront and Global Accelerator?
CloudFront caches HTTP/HTTPS content at edge locations — best for cacheable web content. Global Accelerator doesn't cache; it proxies TCP/UDP traffic over AWS's private backbone to the nearest healthy endpoint using static anycast IPs — best for non-HTTP protocols or fast regional failover without waiting on DNS propagation.
What's the principle of least privilege, and why does it matter in IAM policy design?
Grant only the specific actions and resources an identity actually needs, nothing broader "just in case." It limits the blast radius if credentials are ever compromised — a wildcard ("Action": "*") policy that works is not the same as a correct policy; it's usually a sign permissions weren't scoped deliberately.
Explain the Shared Responsibility Model for RDS specifically.
AWS is responsible for patching the underlying OS and database engine, managing the instance, and guaranteeing infrastructure durability. You're responsible for everything inside that boundary — database user accounts and permissions, whether the DB is publicly accessible, enforcing SSL connections, and encryption configuration. You never get OS-level shell access to an RDS instance — that boundary is the whole point of a managed service.
What's the difference between Amazon Bedrock and Amazon SageMaker?
SageMaker is for building, training, and deploying your own custom ML models — you manage the training data and process. Bedrock gives managed API access to pre-built foundation models from multiple providers (Anthropic, Meta, Amazon, and others) — no training or infrastructure management, pay per request. Bedrock is the faster path when an existing foundation model already solves the problem; SageMaker is for when you need a model trained on your own proprietary data/task.
